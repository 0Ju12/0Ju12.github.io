설계 판단 · 트레이드오프

ThRead: LLM에는 '어떤 댓글이 부적절한가' 같은 판단(번호)만 맡기고, 삭제·채택은 코드가 원본에서 처리 — LLM이 직접 고쳐 쓰는 방식보다 유연성은 줄지만 원본 보존과 개수 보장을 얻음
국보 가이드: 근거 번호를 검색 단계에서 고정하고 LLM은 가리키기만 하게 함 — 답변 표현의 자유는 줄지만 인용 검증이 단순한 집합 비교가 됨
VQA 챌린지: 새 후보를 정확도 대신 고친 문제와 새로 틀린 문제(fixes−breaks)·유형별 회귀로 채택 — 점수 상승 폭만 보는 것보다 느리지만 '믿을 수 있게 오른' 제출만 남김
테스트: 외부 API 대신 mock·가짜 LLM으로 결정적인 테스트를 만듦 — 빠르고 매번 같은 결과가 나오는 대신, 실제 모델의 답변 품질은 측정하지 않음

돌아보면 · 남은 과제

가짜 LLM 테스트는 규칙(인용 검증·예외 처리)을 보장하지만 답변 품질 자체는 재지 못함 — 실제 모델로 질문 세트를 만들어 검색 적중·인용 정확도를 평가하는 것이 다음 단계
배운 것: 실패했을 때의 기본값(JSON이 깨지면, 선별이 실패하면, 인용이 없으면)을 먼저 정해 두니 LLM 응답이 흔들려도 서비스는 안정적으로 동작함
