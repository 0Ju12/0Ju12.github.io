What I did

  1. Earthquake pipeline: incremental collection from the USGS FDSN API with per-region minimum magnitude and start date (re-fetching the last 3 days so runs are idempotent); only newer revisions replace an event; events without magnitude, out of range or non-earthquake are quarantined and counted; CSV (source) and SQLite (query) storage; Mc and b-value (Aki–Utsu, Shi & Bolt error); a Leaflet dashboard refreshed daily by GitHub Actions
  2. Equipment anomaly detection: 136 cycle features from 2,205 cycles × 17 sensors of the UCI hydraulic rig; per-component normal models (Ledoit-Wolf Mahalanobis, 1% false-alarm threshold) with a k-consecutive alert rule; RandomForest vs LDA diagnosis under random and time-block splits
  3. Power demand forecasting: day-ahead 24-hour forecasts from KPX 2025 national hourly demand and Open-Meteo temperature — features use only values at least 24 hours old (with a leakage test), holidays included; baseline, linear, GBM and ensemble tested on October–December
  4. DART data mart: OpenDART collection (status-code handling, rate-limit waits), standardised accounts, pivot/LAG/RANK SQL views, and evidence search over business-report paragraphs with character-bigram BM25, returned with sources (API key only via Secrets)
  5. Analysis warehouse: eight questions on power demand, temperature, solar irradiance and data-job postings, each answered by dbt analysis tables — a two-segment temperature model on weekdays (breakpoints found by a 0.5 °C grid search), day types re-classified with a holiday seed to compare days off and long holidays, peak hour by season, the spring midday dip and a test of its cause (a month-fixed-effect regression gives −2,704 MW of midday demand per 100 W/m² of irradiance, while the 20:00–23:00 placebo shows +11 MW, i.e. no effect — consistent with unmetered solar), and skill mentions by data role. Sources are modelled in dbt (DuckDB) as staging → intermediate → marts → analysis, with the hour's start time as key so '24:00' never slips into the next day · the Airflow DAG, CLI and tests share the same functions
  6. Power-transition analysis: Ember monthly generation and Our World in Data energy data (keyless open data) analysed with seven SQL queries — Korea's 25-year electricity mix, coal decline vs 11 other countries, solar growth and seasonality, carbon intensity — published as a D3 dashboard with an animated year scatter; coal 46.3% (2009) → 31.1% (2025), solar share peaks in May (7.6%) vs December (3.4%), the same direction as the warehouse's spring midday dip
  7. API monitoring (API Watch): checks 22 public APIs on a regular schedule — beyond HTTP 200 it flags stale data, empty results, duplicates and type changes, stores the first healthy schema to tell added fields from removed or retyped ones, and groups repeated failures into one issue (includes a Django admin and Docker Compose version)
  8. Wildfire risk map: compares the Fosberg fire weather index with NASA satellite fire detections daily — most detections are persistent heat sources such as steelworks, so rules filter them out
  9. Data agent: an MCP server that lets an LLM query these results in SQL — read-only SQL guards and a check that numbers in the answer match the query results

Case study · Why 0.99 accuracy was hard to trust — how the evaluation split changed an equipment diagnosis

0.99 → 0.81Valve diagnosis accuracy (RandomForest) · random split vs time-series cross-validation that trains on the past and tests on the future (5-fold forward chaining)
  1. ProblemDiagnosing component condition from 2,205 cycles × 17 sensors of a hydraulic rig, every component scored above 0.99 with a random split — too good to trust
  2. HypothesisNeighbouring cycles are nearly identical, so 'twins' of test cycles leak into training. If so, scores should fall sharply when training on the past and testing on the future
  3. MethodSplit cycles into 10 blocks and test on blocks 5–9 in turn, training only on earlier blocks (5-fold forward chaining), against a random split; 8 per-cycle statistics per sensor (136 features); RandomForest vs standardised LDA, with moving-block bootstrap 95% intervals on the single split
  4. ResultRandomForest fell to 0.81 ± 0.10 (valve), 0.93 (pump), 0.35 (accumulator), while LDA held 0.99 ± 0.02 (valve) and 1.00 (pump) across test windows — the evaluation changed which model to choose. Cross-validation also showed the first single split (valve 0.46) overstated the drop
  5. LimitsThe accumulator tops out at 0.47 (LDA, time-series CV), suggesting features such as the pressure build-up time constant are needed · per-component unsupervised detection raises many false alarms when faults overlap (valve 48%, pump 54%), so it needs label-based diagnosis alongside

Case study · Day-ahead power demand — half the baseline error without leakage

3.23%Hourly MAPE on the Oct–Dec test period (linear + GBM average chosen by rolling CV) · same-hour-last-week baseline 6.17% · 3.44% without a temperature forecast
  1. ProblemForecast all 24 hours of next-day national demand the day before, with only one public year (2025, 8,760 hours)
  2. SetupBecause the forecast is made on D-1, demand features use only values at least 24 hours old (checked by a leakage test); train Jan–Sep, test Oct–Dec including the Chuseok holiday
  3. MethodLinear and GBM models on hour × day type, month, lags and heating/cooling temperature terms, each with and without temperature — observed temperature stands in for a perfect forecast. The model is chosen from 10 candidates by 6-fold rolling-origin CV inside Jan–Sep only; the test period is scored once at the end
  4. ResultThe CV-selected average of the two models scored 3.23% on test (2.64% daily peak); the best candidate without temperature scored 3.44%. On public holidays the linear model without temperature stayed stable at 3.99% versus 8%+ for GBM
  5. LimitsObserved temperature as a perfect forecast means real operation would be worse · one year means no season is seen twice · 3.23% beats a naive baseline, not the grid operator's official forecast

Case study · Does weekday midday demand really drop on sunny days?

−2,704 MWChange in weekday midday (11:00–14:00) demand per 100 W/m² of irradiance · 95% CI −2,986 to −2,422 · R² 0.91
  1. ProblemOn 14 of 22 April weekdays, midday demand fell below that day's overnight minimum; in summer it never did
  2. HypothesisSmall-scale solar that the grid operator does not meter cuts midday demand on sunny days. If so, (1) sunny middays should be lower even within the same month, and (2) there should be no gap after sunset
  3. MethodHourly irradiance for four cities (Open-Meteo) aligned to demand by interval end; regression with month intercepts, overnight minimum and heating/cooling temperature terms; 20:00–23:00 demand as a placebo
  4. ResultSunny middays were lower in all 12 months, while the same model on evening demand gives +11 MW (95% CI −151 to 173), indistinguishable from zero — both predictions held
  5. LimitsExtra lighting on cloudy days is not separated out; irradiance is horizontal so the coefficient is not read as installed capacity; not yet compared with the operator's own estimate

Decisions I made & trade-offs

What I chose, and what I gave up for it

Evaluation split: in time series where neighbouring points are nearly identical, random splits inflate scores, so both the sensor diagnosis and the demand forecast default to time-ordered splits (train on the past, test on the future), with random-split results reported alongside.
Earthquake storage: a human-readable, diff-able CSV is the source of truth and SQLite is rebuilt for queries — slightly larger files, but every change stays visible in the repository history.
DART evidence search returns source paragraphs instead of generated answers — less fluent, but no risk of a wrong summary.

Looking back · open questions

What I would change, and what is still open

Accumulator diagnosis (0.47 under time-series CV) seems to need features such as the time constant of pressure build-up more than a different model.
Only one year of demand data is public, so no season is seen twice; I plan to re-evaluate with several years and real temperature forecasts.
The current reference is a naive same-hour-last-week baseline — 3.23% is an improvement over that baseline, not a claim of beating the grid operator's official day-ahead forecast. Comparing against the official forecast over the same period is the next step.
