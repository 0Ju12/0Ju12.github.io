한끼 — 냉장고 재고 기반 식단⁠·​운동 코치 Agent (LangGraph · FastAPI · Android)

냉장고 재고(중량⁠·​소비기한)를 기준으로 메뉴⁠·​부족한 재료⁠·​조리 후 남는 시간을 계산하고, 상황 문장 하나로 추천부터 장바구니⁠·​조리 모드까지 이어 주는 한국어 웹⁠·​Android 앱

삼성 청년 SW⁠·​AI 아카데미 (SSAFY) 16기 · AI 코어 프로젝트 3 (개인) → 최종 프로젝트로 확장 중 · 개인 · 기획⁠·​설계⁠·​Agent⁠·​백엔드⁠·​화면

핵심모델은 해석⁠·​도구 선택⁠·​문장만, 재고⁠·​분량 판정은 코드가 — 등록 안 된 도구는 버리고 모델이 실패해도 규칙 계획으로 계속

문제

냉장고에 두부가 있어도 2인분에 충분한지, 이번 주 안에 써야 하는지, 조리 뒤 운동할 시간이 남는지는 각각 따로 확인해야 함 — SSAFY AI 코어 프로젝트 3(개인)에서 그 중심인 Agent를 만들고 최종 프로젝트로 확장 중

역할

개인 프로젝트로 기획⁠·​설계(유스케이스⁠·​시스템⁠·​ERD)부터 Agent, FastAPI 백엔드, 웹 화면, Android 셸까지 담당. 모델이 틀려도 재고⁠·​분량 같은 숫자는 틀리지 않게 만드는 것이 목표

성과 수치의 의미와 평가 조건

110개

대역 모델⁠·​고정 제공처 응답을 이용한 자동 테스트 수 (실제 계정이 필요한 4개는 선택 실행)

2026-11-20 최종 제출본 재실행 기준(압축을 푼 폴더에서도 동일). 대표 시나리오 6/6⁠·​대화형 11/11 기대 동작 일치. Agent 흐름⁠·​판정 규칙 검증이며 실제 모델의 해석 품질⁠·​응답 시간⁠·​사용자 지표가 아님. 대표 시나리오 6개의 기대값/실제값은 검증 기록 참조.

평가 근거 ↗

한 일

  1. Agent 흐름: LangGraph로 분석(모델: 자연어 → 조건) → 계획(규칙이 핵심 작업을 정하고, 모델은 도구 목록을 보고 구조화 출력 Plan으로 보조 도구만 고름) → 실행(Worker) → 판정(재고⁠·​소비기한⁠·​부족 g⁠·​조리 시간, 코드) ⟲ 재계획(최대 3회) → 검증 → 응답(확인된 값만으로 문장)
  2. 안전장치: 등록되지 않은 도구⁠·​중복 작업은 코드가 버리고, 모델 호출이 실패하면 규칙 계획만으로 계속 진행 · 외부 제공처 키가 없으면 MISSING_KEY로 구분하고 직접 검색 링크를 남김 · 키와 원문 예외는 사용자 응답⁠·​실행 로그에서 제외
  3. 작업 연결: '김치찌개 먹고 싶은데 뭐 사야 해?' → 레시피 조회 → 냉장고 재고와 비교 → 없는 재료만 쇼핑 검색에 넘김. '둘이 먹을 거고 있는 재료로만'처럼 말하면 인분을 적용하고 장바구니는 건드리지 않음 · 한 일은 되돌리기 버튼과 함께 표시
  4. 실행 기록: 이벤트 버스 → 로깅 Agent(모델 미사용) → SQLite 구독 구조로 분석⁠·​계획⁠·​실행⁠·​판정⁠·​응답과 도구 인자⁠·​지연⁠·​재계획 사유를 기록하고, 중복 호출⁠·​계획 밖 호출⁠·​같은 도구 연속 실패⁠·​재계획 상한 도달을 판정 — 기록 쪽 오류가 대화를 막지 않게 분리
  5. 근거 검색(RAG): 영양 섭취기준⁠·​식품 안전⁠·​운동 지침 등 공개 자료를 요약한 안내 문서 31편(출처 링크 포함)을 Chroma에 색인, 외부 API로 확인할 수 없는 질문에 근거 문단과 출처를 붙여 답하고 관련 근거가 없으면 '찾지 못했어요'로 답함
  6. 도메인: 직접 작성한 1인분 레시피 110종(USDA 영양 참조로 열량⁠·​단백질 계산), 포장 단위 재고와 소비기한, 인분을 바꾸면 부족한 g를 다시 계산하는 조리 모드, 숙련도별 운동 루틴⁠·​세트 타이머, 일정 겹침 확인과 조리 시작 시각 역산
  7. 결함 수정: 응답을 잃은 뒤 '다시 보내기'를 하면 물⁠·​섭취 기록이 두 번 쌓일 수 있던 경로 → 첫 요청 ID를 재사용해 서버 합계가 한 번만 늘도록 수정 · 식물성 식단에서 소고기가 후보에 남던 문제 → 재료 분류를 보강하고, 원재료를 검증할 수 없는 외부 레시피는 자동 후보에서 제외
  8. 화면⁠·​배포: 모바일 하단 탭⁠·​데스크톱 사이드바 웹, Android WebView 셸(알림⁠·​Health Connect 일일 합계 미리보기), 디버그 APK⁠·​미서명 AAB 빌드, Docker 운영 모드 이미지에서 브라우저별 기록 분리 확인
  9. 테스트: 대역 모델(가짜 LLM)과 고정 제공처 응답으로 키 없이 도는 pytest, GitHub Actions로 실행

결과

  • 대표 시나리오 6개(재료 충분⁠·​후보 재계획⁠·​재계획 상한⁠·​제공처 키 누락⁠·​도구 불필요⁠·​시간 제약)에서 기대값과 실제값, 도구 호출 수, 재계획 횟수가 일치
  • 자동 테스트 110개 통과, 실제 계정이 필요한 4개는 선택 실행 (2026-11-20 최종 제출본 재실행) · 모바일 390×844⁠·​데스크톱 1440×940 브라우저에서 재료 등록 → 조리 → 섭취 → 기록 흐름을 직접 조작해 확인
  • 남은 검증: 실제 발급 키로 모델⁠·​식약처⁠·​YouTube 전 구간, Android 실기기의 Health Connect 권한 철회⁠·​알림, 계정 단위 저장

직접 내린 설계 판단 · 트레이드오프

무엇을 고르고, 그 대신 무엇을 포기했는지

한끼: 핵심 작업은 규칙이 정하고 모델은 보조 도구만 고르게 함 — 모델에게 계획 전체를 맡기는 것보다 유연성은 줄지만, 모델이 틀리거나 실패해도 재고⁠·​분량 계산과 기본 추천은 그대로 동작
실행 기록: 로깅 Agent는 모델을 쓰지 않고 이벤트 규칙(중복⁠·​계획 밖 호출⁠·​연속 실패⁠·​재계획 상한)으로 판정 — 미묘한 이상은 놓칠 수 있지만, 기록이 빠르고 매번 같은 결과가 나오며 비용이 들지 않음
테스트: 대역 모델과 고정 제공처 응답으로 키 없이 돌게 함 — 매번 같은 결과를 얻는 대신 실제 모델의 해석 품질과 응답 시간은 이 테스트로 측정하지 않음

돌아보면 · 남은 과제

다시 한다면 바꿀 것, 아직 남은 것
