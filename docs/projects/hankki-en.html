Problem

Having tofu in the fridge doesn't tell you whether it's enough for two, whether it must be used this week, or whether there's time to work out after cooking. In SSAFY AI core project 3 (solo) I built the agent at the centre of this, and I'm extending it into the final project.

My role

Solo, from planning and design (use cases, system, ERD) to the agent, FastAPI backend, web UI and Android shell. Goal: even when the model is wrong, numbers like stock and portions must not be.

Evidence ↗

What I did

  1. Agent flow: LangGraph analyse (model: natural language → conditions) → plan (rules fix the core tasks; the model only picks helper tools from the tool list via a structured Plan output) → execute (worker) → judge (stock, use-by date, missing grams, cooking time — in code) ⟲ replan (max 3) → verify → respond (sentences from confirmed values only)
  2. Safeguards: unregistered tools and duplicate tasks are dropped in code; if the model call fails the rule plan carries on alone · a missing provider key is reported as MISSING_KEY with a direct search link · keys and raw exceptions never reach user replies or run logs
  3. Task chaining: 'I want kimchi stew — what do I need to buy?' → recipe lookup → compare with fridge stock → pass only the missing ingredients to shopping search. 'Two of us, only what we have' applies servings and leaves the cart alone · every action is shown with an undo button
  4. Run records: event bus → logging agent (no LLM) → SQLite subscription stores analyse/plan/execute/judge/respond with tool arguments, latency and replan reasons, and flags duplicate calls, off-plan calls, repeated failures of one tool and the replan cap — logging errors never block the conversation
  5. Grounded answers (RAG): 31 guide documents summarising public sources (nutrient intake standards, food safety, exercise guidelines, with source links) indexed in Chroma; questions no API can answer get evidence paragraphs and sources, or 'not found' when nothing relevant exists
  6. Domain: 110 hand-written single-serving recipes (calories and protein from USDA references), package-level stock with use-by dates, a cooking mode that recomputes missing grams when servings change, skill-level workout routines with set timers, schedule-overlap checks and back-calculated cooking start times
  7. Fixed defects: re-sending after a lost response could double water/intake records → the first request ID is reused so the server total rises once · beef stayed in plant-based candidates → ingredient categories were tightened and external recipes whose ingredients can't be verified are excluded from automatic candidates
  8. UI and delivery: web with mobile bottom tabs and a desktop sidebar, Android WebView shell (notifications, Health Connect daily totals preview), debug APK and unsigned AAB builds, per-browser data isolation checked in the Docker production image
  9. Tests: pytest with a stand-in model (fake LLM) and fixed provider responses, so it runs without keys; run on GitHub Actions

Results

  • Six representative scenarios (enough ingredients, candidate replan, replan cap, missing provider key, no tool needed, time limit) match expected values, tool-call counts and replan counts
  • 110 automated tests passing, 4 real-account checks run on demand (final submission re-run 2026-11-20) · ingredient entry → cooking → intake → records exercised by hand in mobile 390×844 and desktop 1440×940 browsers
  • Still to verify: the full path with real model, food-safety and YouTube keys; Health Connect permission revocation and notifications on a real Android device; account-level storage

Decisions I made & trade-offs

What I chose, and what I gave up for it

Hankki: rules fix the core tasks and the model only picks helper tools — less flexible than letting the model plan everything, but stock/portion maths and the basic recommendation keep working when the model is wrong or down.
Run records: the logging agent uses event rules (duplicates, off-plan calls, repeated failures, replan cap) instead of an LLM — subtle anomalies can slip through, but logging is fast, deterministic and free.
Tests: a stand-in model and fixed provider responses let tests run without keys — deterministic, but they do not measure the real model's interpretation quality or latency.

Looking back · open questions

What I would change, and what is still open

Next: re-run the representative scenarios with real keys to record latency (target under 5 s) and failure rate, and measure how many recommendations turn into actual cooking, split by stock-entry style and diet goal.
