파인튜닝 vs 프롬프트 vs RAG — 모델을 바꿀지, 입력을 바꿀지

같은 문제를 프롬프트로 풀지, 검색(RAG)으로 풀지, 파인튜닝으로 풀지를 정하는 기준을 정리했습니다. 세 방법은 각각 지시·지식·행동을 바꾸고, 고르는 순서보다 평가 기준을 먼저 세우는 것이 중요합니다.

파인튜닝RAG프롬프트

한 줄 요약 — 지난 회차에서 작은 모델을 좁은 과제에 맞추는 방법으로 "미세조정"을 미뤄 두었습니다. 모델이 원하는 대로 답하지 않을 때 손댈 수 있는 곳은 세 군데입니다. 지시를 바꾸거나(프롬프트), 보여 주는 자료를 바꾸거나(RAG), 모델 자체를 바꾸는(파인튜닝) 것입니다. 문제의 원인이 어디에 있는지에 따라 고를 곳이 달라집니다.

핵심 개념

  • 프롬프트: 모델의 가중치는 그대로 두고 지시문·예시·출력 형식을 바꿉니다. 고치고 확인하는 데 몇 분이면 됩니다.
  • RAG: 질문할 때마다 관련 자료를 찾아 입력에 붙입니다(#7). 모델이 모르는 사실, 자주 바뀌는 사실, 사내 문서처럼 학습에 없던 지식을 다룰 때 씁니다.
  • 파인튜닝: 예시 데이터로 모델의 가중치를 조금 바꿉니다. 지식을 넣기보다는 말투·형식·판단 기준 같은 행동을 일관되게 만들 때 맞습니다. LoRA·QLoRA처럼 일부 가중치만 학습하는 방법이 흔합니다.
  • 비유: 신입 직원에게 일을 맡기는 경우와 같습니다. 업무 지시서를 고쳐 주는 것이 프롬프트, 참고할 자료철을 책상에 놓아 주는 것이 RAG, 몇 주 동안 같은 일을 반복해 몸에 익히게 하는 것이 파인튜닝입니다. 자료철이 없어서 틀리는 사람을 몇 주 훈련시켜도 자료에 없는 내용은 여전히 모릅니다.

지금 무슨 일이 일어나고 있나

  • "프롬프트부터, 평가 세트와 함께"가 공통 권고입니다. OpenAI의 정확도 최적화 가이드는 프롬프트로 시작해 평가 세트로 기준선을 잡고, 문제가 지식 부족이면 RAG, 행동 불일치면 파인튜닝으로 가라고 정리합니다. 다만 이 순서를 한 번 지나가는 직선이 아니라 반복하는 과정으로 설명합니다.
  • 2026년의 실무 정리들도 같은 구분을 씁니다. "프롬프트는 지시를, RAG는 모델이 볼 수 있는 지식을, 파인튜닝은 모델의 행동을 바꾼다"는 식의 정리가 여러 글에 반복됩니다. 셋을 함께 쓰는 구성(파인튜닝으로 형식, RAG로 지식, 프롬프트로 조율)도 흔하다고 소개됩니다. 다만 비용·기간 수치는 글마다 크게 다르고 출처가 없는 경우가 많아 이 글에서는 인용하지 않습니다.
  • 연구 결과는 한쪽으로 모이지 않습니다. 의료 분야 리뷰는 RAG를 비용 대비 효과가 좋은 방법으로, 파인튜닝을 데이터가 충분할 때 정확도가 높은 방법으로 정리합니다. 물류 분야의 한 연구는 검색으로 고른 예시를 프롬프트에 넣는 방식이 전통적인 파인튜닝보다 나았다고 보고합니다. 과제와 데이터 양에 따라 결과가 달라진다는 뜻으로 읽는 것이 맞습니다.
  • 파인튜닝이 RAG를 돕기도 합니다. OpenAI의 예제(오래된 자료)는 RAG 위에 파인튜닝을 더해 "자료에 답이 없을 때 모른다고 하기"를 개선한 사례를 보입니다. 지식이 아니라 행동을 학습시킨 경우입니다.

동작 구조

모델 답이 기대와 다르다
   │
   ├─ 지시가 모호하다 / 형식이 흔들린다 ─────▶ 프롬프트 수정 (예시·출력 형식)
   │
   ├─ 모델이 모르는 사실이다 / 자주 바뀐다 ───▶ RAG (검색 품질부터 확인)
   │
   └─ 프롬프트로 고쳐도 행동이 일관되지 않다 ─▶ 파인튜닝 (좋은 예시 데이터가 있을 때)
                 │
           모든 단계에서 같은 평가 세트로 비교

def choose(evalset):
    base = score(prompt_v1, evalset)                  # 기준선
    errs = classify_errors(prompt_v1, evalset)        # 틀린 이유를 직접 분류
    if errs.most_common == "instruction":
        return improve_prompt()                       # 몇 분~몇 시간
    if errs.most_common == "missing_knowledge":
        return add_retrieval(), check_recall()        # 검색이 맞는 문서를 가져오는지부터
    if errs.most_common == "inconsistent_behavior" and has_good_examples():
        return finetune(examples), compare(base)      # 같은 평가 세트로 다시 측정
프롬프트 RAG 파인튜닝
바꾸는 것 지시·예시 입력에 붙는 자료 모델 가중치
잘 고치는 문제 모호한 지시, 형식 모르는 사실, 최신 정보 일관된 행동·말투·판단
준비물 평가 세트 문서·검색 파이프라인 질 좋은 학습 예시
수정 속도 빠름 문서만 바꾸면 반영 다시 학습해야 함
출처 제시 어려움 가능(검색된 문서) 어려움

왜 중요한가 / 한계

  • 원인을 잘못 짚으면 비용만 듭니다. 지식이 없어서 틀리는 문제를 파인튜닝으로 풀려고 하면, 학습 데이터에 없던 질문에서는 여전히 틀리고 그럴듯한 답만 늘 수 있습니다.
  • 한계 1 — 오류 분류가 먼저입니다. 위 의사코드의 classify_errors는 사람이 틀린 답을 직접 보고 나누는 단계입니다. 이걸 건너뛰면 어느 방법이 맞는지 판단할 근거가 없습니다(#10의 평가와 이어집니다).
  • 한계 2 — RAG의 실패는 검색에서 많이 납니다. 생성 단계만 고쳐서는 맞는 문서를 못 가져오는 문제가 해결되지 않습니다. 검색 재현율을 따로 재야 합니다.
  • 한계 3 — 파인튜닝은 유지 비용이 따라옵니다. 기반 모델이 바뀌면 다시 학습해야 하고, 학습 순서에 따라 앞서 배운 것을 잊는 문제도 생깁니다.
  • 한계 4 — 섞을수록 원인 추적이 어려워집니다. 셋을 다 쓰면 어디서 틀렸는지 나누기 어려워지므로, 단계마다 따로 평가할 수 있게 만들어야 합니다.

내 프로젝트와 연결

  • 국보 입문 가이드는 RAG를 택한 사례입니다. 국보 설명은 모델이 정확히 알 것이라고 기대할 수 없는 지식이라 검색으로 자료를 붙였고, 답에 붙은 근거 번호가 실제 검색 결과에 있는지 코드로 확인했습니다. 지식 문제를 검색으로, 출처 문제를 코드 검증으로 나눠 다룬 것입니다.
  • POSPEAK(KILL KONG) 에서는 FLAN-T5에 LoRA를 붙여 콩글리시 교정이라는 좁은 행동을 학습시켰고, 학습 전략에 따라 F1이 0.32에서 0.74로 달라졌습니다. 같은 파인튜닝이라도 데이터 구성과 학습 순서가 결과를 크게 바꾼다는 것을 본 사례이고, 앞서 배운 것을 잊는 문제도 겪었습니다.
  • AI 챌린지 VQA에서는 QLoRA 미세조정과 여러 관점의 확률 앙상블을 함께 썼습니다. 무엇을 채택할지는 정확도 평균이 아니라 고친 문항과 망친 문항 수(fixes−breaks)로 판단했습니다. 위에서 말한 "같은 평가 세트로 비교"를 실제로 적용한 방식입니다.
  • 관통 4·5에서는 모델을 바꾸지 않고 프롬프트와 출력 검증 코드로 LLM 판단을 다뤘습니다. 파인튜닝을 하지 않은 대신 형식이 깨진 출력을 코드에서 걸러 냈습니다.

면접 질문

Q. 파인튜닝, RAG, 프롬프트 개선 중 무엇을 먼저 하겠습니까?

먼저 평가 세트를 만들고 지금 프롬프트로 기준선을 잡은 뒤, 틀린 답을 직접 보고 원인을 나누겠습니다. 지시가 모호해서 틀리면 프롬프트를, 모델이 모르는 사실이라서 틀리면 RAG를, 프롬프트로도 행동이 일관되지 않고 좋은 예시 데이터가 있으면 파인튜닝을 고르겠습니다. 국보 가이드는 지식 문제라 RAG를 택했고, POSPEAK은 교정이라는 좁은 행동이라 LoRA 파인튜닝을 했습니다. 어느 경우든 같은 평가 세트로 전후를 비교했고, VQA 챌린지에서는 고친 문항과 망친 문항을 세어 채택 여부를 정했습니다.

다른 글비용·지연 최적화 — 캐싱·라우팅·배치로 같은 답을 더 싸고 빠르게LLM 서비스의 비용과 지연을 줄이는 세 가지 장치, 프롬프트 캐싱·모델 라우팅·배치 처리를 정리했습니다. 공식 문서의 캐시 수명과 가격 배수, 그리고 캐시가 맞지 않는 구조를 봅니다.소형·온디바이스 모델 — 작은 모델로 충분한 일은 얼마나 되나수십억 개 이하 파라미터의 작은 모델을 기기 안에서 돌리는 흐름을 정리했습니다. 양자화가 무엇을 줄이는지, 큰 모델과 작은 모델을 섞어 쓰는 구조, 그리고 '작아도 된다'는 주장의 조건을 봅니다.추론 모델과 test-time compute — 더 오래 생각하게 하면 무엇이 달라지나답하기 전에 생각하는 데 계산을 더 쓰는 추론 모델의 원리와, '생각 예산'을 조절할 때 생기는 비용·지연·과잉 사고 문제를 정리했습니다.컴퓨터 사용 에이전트 — 화면을 보고 클릭하는 모델API가 없는 프로그램을 사람처럼 화면으로 다루는 에이전트를 정리했습니다. 화면 캡처 → 좌표 → 행동의 루프, 벤치마크 점수가 사람 기준선을 넘었다는 보고와 그 점수를 그대로 믿기 어려운 이유를 봅니다.코딩 에이전트 — 코드를 쓰는 것보다 확인하는 것이 일이다자동 완성에서 '저장소를 읽고, 고치고, 테스트를 돌리는' 에이전트로 넘어온 흐름을 정리했습니다. 벤치마크 점수가 출처마다 엇갈리는 이유와, 사람의 일이 작성에서 검증으로 옮겨 가는 지점을 봅니다.에이전트 평가 — 점수가 높다는 것과 믿을 수 있다는 것에이전트는 답 하나가 아니라 과정 전체를 평가해야 합니다. 채점기의 세 종류, 한 번 성공과 매번 성공의 차이, 그리고 공개 벤치마크 점수가 오염으로 흔들리는 사례를 정리했습니다.가드레일과 프롬프트 인젝션 방어 — 모델이 읽는 모든 글이 공격 경로다프롬프트 인젝션이 왜 필터 하나로 막히지 않는지, 직접·간접 인젝션의 차이와 '탐지'에서 '권한 설계'로 옮겨 가는 방어 흐름을 정리했습니다.멀티 에이전트 오케스트레이션 — 나누면 빨라지지만 맥락이 끊긴다일을 여러 에이전트에게 나눠 맡기는 구조(지휘자-작업자, 핸드오프)의 장단점을 정리했습니다. 병렬 조사에서는 효과가 보고됐지만 토큰이 크게 늘고, 맥락이 쪼개져 생기는 실패가 따로 연구될 만큼 흔합니다.RAG에서 Agentic RAG로 — 검색을 한 번 할지, 에이전트가 여러 번 할지한 번 검색해 답하는 RAG와, 검색 여부·횟수·결과 품질을 스스로 판단하는 Agentic RAG의 차이를 정리했습니다. Self-RAG·CRAG·Adaptive-RAG가 각각 어느 판단을 추가했는지와, 반복이 늘 때 생기는 비용과 평가 문제를 봅니다.에이전트 메모리 — 대화가 끝나도 남는 것과 남기면 안 되는 것컨텍스트 창 안의 단기 기억과 대화 밖에 저장하는 장기 기억을 나누고, 무엇을 쓰고 언제 꺼내는지의 설계를 정리했습니다. 한 번 오염되면 세션이 끝나도 남는 메모리 포이즈닝도 함께 봅니다.ReAct와 Plan-and-Execute — 에이전트는 어떻게 계획하나한 걸음마다 다시 생각하는 ReAct와, 먼저 계획을 세우고 실행하는 Plan-and-Execute의 차이를 비용·속도·실패 방식으로 비교했습니다. ReWOO·LLMCompiler 같은 변형과 코딩 에이전트의 plan mode까지 이어서 봅니다.에이전트 간 통신 — A2A는 MCP와 무엇이 다른가MCP가 '에이전트와 도구'를 잇는다면 A2A는 '에이전트와 에이전트'를 잇습니다. Agent Card로 상대를 찾고, 상태가 있는 task로 일을 맡기는 구조와, 버전마다 바뀐 부분·엇갈리는 보도를 정리했습니다.MCP — 도구를 매번 새로 붙이지 않는 방법지난 회차의 tool use를 앱마다 다시 만들지 않도록 '도구 서버'를 표준 규격으로 분리한 MCP의 구조(호스트·클라이언트·서버, tools·resources·prompts)와 최근 사양 변화, 보안상 약한 고리를 정리했습니다.Tool use — 모델은 함수를 실행하지 않는다Function calling의 실제 동작(모델은 호출 '요청'만 만들고 실행은 내 코드가 한다), strict 스키마와 Structured Outputs의 관계, 도구를 쓸 때와 출력 형식만 고정할 때를 구분했습니다.AI 에이전트란 무엇인가 — LLM이 도구를 쥐고 반복할 때에이전트를 '도구를 쓰며 스스로 다음 단계를 정하는 LLM 루프'로 정의하고, 워크플로와 무엇이 다른지, 기업 도입 숫자가 왜 엇갈리는지 정리했습니다.
