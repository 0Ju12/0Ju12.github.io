수집만 하던 자료를 웨어하우스로 — '24시'와 고쳐지는 지진, 그리고 처음 실행에서만 나는 실패

매일 모으기만 하던 지진·전력 수요 자료를 dbt로 3단 모델링하고 Airflow DAG로 묶으면서 정한 것들. 시간 키를 시작 시각으로 잡은 이유, 고쳐진 값의 이력을 쌓는 법, 증분 집계를 믿기 위한 대조 테스트.

dbt데이터 웨어하우스Airflow데이터 품질

공개 데이터 프로젝트로 지진 목록과 전력 수요를 매일 모으고 있었습니다. 수집과 예측까지는 했지만, 모은 자료를 질문하기 좋은 표로 정리하고 그 품질을 계속 확인하는 일은 하지 않았습니다. 데이터 엔지니어 직무에서 가장 먼저 묻는 부분이 비어 있었던 셈입니다.

그래서 같은 자료 위에 작은 웨어하우스를 올렸습니다. dbt(DuckDB)로 원본 → 정제 → 집계 3단을 만들고, Airflow DAG로 실행 순서를 묶었습니다. 자료는 작습니다(지진 약 2,500건, 수요 8,760행). 그래서 성능 이야기는 할 수 없고, 이 글은 구조를 정하면서 실제로 걸린 지점 네 곳만 적습니다.

1. "24시"는 다음 날 0시가 아니다

전력거래소 시간별 수요는 하루가 한 줄이고 열이 1시부터 24시까지 있습니다. N시는 그 시각에 끝나는 한 시간의 평균입니다. 그러니 24시는 그날 23:00~24:00 구간입니다.

이 표를 시간별 행으로 풀 때 가장 쉬운 방법은 "날짜 + N시간"으로 시각을 만드는 것입니다. 처음에 그렇게 해 봤고, 행 수도 8,760으로 맞았고, 중복도 없었습니다. 문제는 24시 행이 다음 날 00:00이 된다는 점입니다. 시각만 보면 틀린 값이 아니지만, 그 시각으로 날짜를 뽑아 일별 집계를 하면 매일 마지막 한 시간이 다음 날로 넘어갑니다. 하루 최대 수요가 밤늦게 나는 날은 값이 달라집니다.

그래서 키를 끝나는 시각이 아니라 시작 시각으로 잡았습니다.

cast("날짜" as date) + to_hours(hour_ending - 1) as hour_start_kst   -- '24시' → 그날 23:00

그리고 이 결정을 테스트로 고정했습니다. 행 수와 중복 검사는 잘못된 방식에서도 통과했기 때문에, 그 둘로는 부족했습니다.

-- 하루는 정확히 24행
select demand_date, count(*) from fct_demand_hourly group by 1 having count(*) <> 24

-- 이웃한 두 행의 간격은 항상 1시간
select * from (select hour_start_kst, lag(hour_start_kst) over (order by hour_start_kst) as prev from fct_demand_hourly)
where prev is not null and hour_start_kst - prev <> interval 1 hour

기온 자료는 반대로 그 시각의 순간값이라, 수요의 시작 시각에 맞춰 붙였습니다. 한 시간 평균과 순간값을 붙이는 것이라 정확히 같은 양은 아닙니다. 이 부분은 근사입니다.

2. 고쳐지는 값은 덮어쓰지 않고 판을 쌓는다

지진은 발생 직후 자동 산정값(automatic)으로 목록에 올라오고, 검토를 거치며 규모·위치·깊이가 바뀝니다. 기존 수집 파이프라인은 같은 ID면 더 늦은 수정본으로 교체했습니다. 최신 값만 필요하면 그걸로 충분합니다.

하지만 "그날 우리는 이 지진을 얼마로 알고 있었나"는 답할 수 없습니다. 그래서 dbt snapshot으로 변경 이력을 쌓았습니다. 수정 시각이 바뀐 행은 이전 판을 닫고 새 판을 추가합니다.

quake_id mag status valid_from valid_to
a1 4.5 automatic 03-01 03-05
a1 4.8 reviewed 03-05 (열려 있음)

여기서 걸린 것은 dbt가 아니라 실행 환경이었습니다. 매일 실행은 GitHub Actions에서 도는데, 매번 빈 DB에서 시작합니다. 이력 표는 "어제의 표" 위에 쌓여야 하는데 어제의 표가 없습니다. 그대로 두면 매일 "모든 지진이 오늘 처음 생긴" 이력 한 판만 만들어집니다.

DB 파일을 통째로 저장소에 넣는 대신, 이력 표만 정렬해 Parquet 한 파일로 남기고 실행 전에 되살리도록 했습니다. 내용이 같으면 파일도 같아서, 바뀐 게 없는 날은 커밋이 생기지 않습니다.

한계도 분명합니다. 이력은 이 작업을 시작한 날부터만 쌓입니다. 그 전에 고쳐진 값은 알 수 없습니다.

3. 증분 집계는 "대조"가 있어야 믿을 수 있다

월 × 지역 지진 수 집계를 증분 모델로 바꿨습니다. 지난 실행 뒤에 달라진 묶음만 다시 계산해 바꿔 넣는 방식입니다.

먼저 정해야 했던 것은 무엇을 기준으로 "달라졌다"고 볼 것인가입니다. 발생 시각이 최근인 것만 다시 계산하면, 석 달 전 지진의 규모가 오늘 고쳐진 경우를 놓칩니다. 그래서 기준을 수정 시각으로 잡았습니다.

{% if is_incremental() %}
, touched as (
    select distinct month_kst, region from src
    where updated_at > (select max(last_updated_at) from {{ this }})
)
{% endif %}

테스트는 "증분으로 이어 쌓은 결과가, 같은 원본으로 처음부터 다시 만든 결과와 같은가"로 썼습니다. 예전 지진 하나를 고치고 새 달의 지진을 하나 넣은 뒤 두 결과를 비교합니다.

그런데 증분에는 구조적인 약점이 있습니다. "안 바뀐 묶음은 그대로 둔다"는 가정에 기대기 때문에, 원본에서 지진이 아예 빠지면(발파로 재분류되는 경우 등) 다시 계산할 계기가 없어 옛 값이 남습니다. 이건 증분 조건을 아무리 다듬어도 못 잡습니다.

그래서 매 실행마다 집계의 합계를 원본에서 다시 센 값과 맞춰 보는 테스트를 넣었습니다.

with a as (select sum(quakes) n from fct_quakes_monthly),
     b as (select count(*) n from stg_quakes where event_type = 'earthquake')
select * from a, b where a.n <> b.n

지진 하나를 원본에서 지우고 돌리면 이 테스트가 실패하고, --full-refresh로 다시 만들면 통과하는 것까지 pytest로 확인했습니다. 증분을 쓴다는 것은 빠르게 계산한다는 뜻이기도 하지만, 틀어졌을 때 알 수 있는 장치를 같이 둔다는 뜻이라고 정리했습니다.

정직하게 적자면, 매일 실행은 빈 DB에서 시작하므로 이 모델은 실제로는 매번 전체로 만들어집니다. 증분 경로는 지금 테스트에서만 돕니다.

4. 처음 실행에서만 나는 실패

Airflow DAG는 얇게 만들었습니다. 작업은 원본 확인 → dbt 실행 → 날짜 파티션 내보내기 → 실행 기록 → 보고서이고, 실제 일은 일반 파이썬 함수가 합니다. 그래서 명령줄, 테스트, Airflow가 같은 코드를 씁니다.

내 환경에서는 DAG가 끝까지 돌았는데, CI에서는 dbt 작업이 실패했습니다. 원인은 단순했습니다. 이력을 되살리는 함수가 DB 파일을 여는데, DB를 둘 폴더가 아직 없었습니다. 내 환경에는 앞선 실행이 만든 폴더가 남아 있어서 드러나지 않았습니다. 명령줄 경로에는 폴더를 만드는 코드가 있었고, DAG 경로에는 없었습니다.

고치는 것은 한 줄이었지만 배운 점은 두 가지입니다.

  • 깨끗한 상태에서 돌려 봐야 한다. 산출물 폴더를 지우고 다시 돌렸다면 바로 나왔을 실패입니다. 이후로는 확인할 때 산출물부터 지웁니다.
  • 같은 일을 하는 경로가 둘이면 한쪽만 고쳐진다. 폴더를 만드는 일을 부르는 쪽이 아니라 함수 안으로 옮겼고, "폴더가 없는 처음 실행"을 테스트에 추가했습니다.

재시도 간격도 이때 손봤습니다. 실패가 재시도로 해결될 종류가 아닌데 3분씩 두 번을 기다리느라 원인을 보는 데 6분이 걸렸습니다.

재실행해도 같은 결과

마지막으로 지킨 것은 멱등성입니다. 같은 날짜를 몇 번 돌려도 결과가 같아야 과거 날짜를 마음 놓고 다시 채울 수 있습니다.

  • 날짜 파티션 내보내기는 임시 파일에 쓴 뒤 바꿔치기하고, 정렬과 압축을 고정했습니다. 같은 날짜를 다시 돌리면 해시가 같은 파일이 나옵니다.
  • 실행 기록은 같은 날짜 줄을 바꿔 씁니다. 다시 돌려도 줄이 늘지 않습니다.
  • 자료에 없는 날짜는 빈 파일을 만들지 않고 0행으로 보고합니다.

아직 하지 못한 것도 있습니다. Airflow는 DAG가 한 번 실행되는 것만 확인했고 스케줄러를 며칠 띄워 운영해 보지는 않았습니다. 클라우드 웨어하우스로도 옮기지 않았습니다. 수요 자료는 2025년 한 해뿐이라 새 자료가 매일 들어오는 진짜 증분 적재도 아닙니다. 다음에 채울 부분입니다.

다른 글모델 호출을 프록시 한곳에 모으고, 모델의 대답부터 의심하기관통 7에서 Django와 AI 모델 사이에 FastAPI 프록시를 두며 정한 것들 — Guardrail이 고장 나면 막는 쪽으로, API마다 다른 이미지 응답을 한 모양으로, 로그에는 구조만 남기기.책·쓰레드·댓글을 하나의 관계형 모델로 묶기관통 6에서 회원·도서·쓰레드·댓글 관계를 설계하며 정한 것들 — 순환 참조 마이그레이션, 지워질 때 남길 것과 지울 것, 남의 글에 404를 주는 이유, 외부 도서 정보를 서명 토큰으로 묶은 방법.겹쳐 있는 두 신호를 위상으로 가르기 — 파수 상관 필터링 석사 연구 정리중력과 자력 데이터를 같은 주파수 성분끼리 비교해, 함께 움직이는 성분과 반대로 움직이는 성분을 나눴다. 임계값을 감으로 정하지 않으려고 한 일들.점수를 지키면서 올리기 — VQA 챌린지에서 앙상블 후보를 고른 기준정확도가 조금 올라도 원래 맞히던 문제를 많이 틀리면 불안정한 개선이다. fixes와 breaks로 순기여를 따져 0.94608에서 시작한 점수를 쌓아 올린 과정.LLM이 붙인 [근거 N]을 코드로 다시 검사하기 — 국보 RAG 가이드의 인용 설계근거를 인용하라고 프롬프트에 써도 LLM은 없는 번호를 붙입니다. 근거 번호를 검색 단계에서 고정하고, 답변의 인용을 코드로 파싱해 없는 번호는 지우고 실제로 인용한 근거만 보여 주는 구조를 만든 기록.YAML 파일 하나로 포트폴리오·이력서·비공개 페이지까지 — 이 사이트를 만든 방식내용은 한 곳에만 쓰고, 웹 페이지·PDF 이력서·노션 문서는 빌드로 만든다. 공개하면 안 되는 내용은 저장소에 평문으로 남기지 않는다.데이터를 해석하기 전에 그 데이터가 만들어진 역사를 본다 — 학부 제1저자 논문 회고해외 대규모 CO2 저장소 8곳을 판구조 형성사와 탄성파 영상으로 비교했다. 처리 결과를 '그럴듯한지' 판단하는 기준을 어디서 가져올 것인가에 대한 이야기.길찾기에서 의사결정으로 — 배틀싸피 자동 플레이 봇을 세 번 고친 기록목표까지 가는 BFS 한 줄짜리 봇이, 사거리·장애물·탄약·보급·암호 해독까지 판단하는 봇이 되기까지. 매 턴 다시 계획하는 구조로 바꾼 이유.산불 4건으로 시공간 딥러닝 학습하기데이터가 35개 시점뿐일 때 어떻게 학습시켰고, 다시 보니 무엇이 부족했는지. U-LSTM 산불 확산 예측 모델 회고.LLM 응답을 믿지 않는 파이프라인 설계LLM에는 판단만 맡기고, 결과는 코드로 검증한다. 댓글 분석 파이프라인과 AI 도서 추천을 만들며 정한 네 가지 원칙.순차 학습이 성능을 떨어뜨린 이유 — catastrophic forgetting 실험기단어 단위 → 문맥 단위로 차례로 학습하면 더 좋아질 줄 알았는데, BERTScore가 0.47에서 0.32로 떨어졌다.
