전력 수요와 채용 공고로 세운 질문 7개 — 표를 만든 다음에 한 일

웨어하우스에 자료를 정리해 두기만 하고 분석은 하지 않았습니다. 2025년 시간별 전력 수요⁠·​기온과 데이터 직무 채용 공고로 질문 7개를 세우고, 질문마다 dbt 표 하나로 답한 기록입니다.

데이터 분석SQLdbt

지난 글에서 지진⁠·​전력 수요 자료를 dbt로 정리하고 품질 테스트를 붙였습니다. 그런데 돌아보니 표를 깔끔하게 만드는 데서 멈춰 있었습니다. 대시보드에는 하루 최대 수요 그래프와 월×시간 색칠 표가 있었지만, 그 그래프로 무엇을 알게 됐는지는 적혀 있지 않았습니다.

데이터 분석가의 관점을 가져가고 싶어서, 이번에는 순서를 바꿨습니다. 질문을 먼저 적고, 질문 하나에 분석 표 하나를 만들고, 답과 함께 "이 답을 어디까지 믿어도 되는가"를 적었습니다. 자료는 전력거래소 2025년 시간별 전국 수요(8,760시간), 같은 시간의 기온(서울⁠·​부산⁠·​대전⁠·​광주 평균), 11월 13일부터 매일 모으는 해외 채용 공고입니다.

질문 1. 기온이 1℃ 바뀌면 수요는 얼마나 바뀌나

평일 하루 평균 기온과 하루 평균 수요를 점으로 찍으면 U자가 나옵니다. 먼저 2℃ 구간별 평균표를 만들어 가장 낮은 구간이 12~16℃인 것을 확인했습니다. 그다음 꺾이는 기온 두 개를 0.5℃ 간격으로 모두 대 보면서 "난방 직선 + 냉방 직선" 모형을 맞췄습니다.

구간 꺾이는 기온 1℃당 수요 변화
난방 13.0℃ 아래 내려갈 때마다 +969 MW
냉방 17.5℃ 위 오를 때마다 +1,636 MW

평일 244일, R² 0.83입니다. 냉방 쪽이 난방 쪽의 1.7배입니다.

쉬는 날은 빼고 맞췄습니다. 같이 넣으면 같은 기온에서 점이 두 줄로 갈라져, 기울기가 날 종류의 차이까지 떠안습니다. 그리고 이 기울기를 "기온 1℃의 순수한 효과"라고 부르지는 않았습니다. 여름과 겨울은 기온만 다른 게 아니라 일조 시간과 생활 패턴도 다르고, 그 차이가 기울기에 섞여 있습니다.

질문 2. 쉬는 날에는 얼마나 줄어드나

여기서 날짜 차원에 문제가 있다는 걸 알았습니다. 처음 만든 날짜 차원에는 주말 표시만 있었습니다. 그래서 3월 3일, 5월 6일, 10월 8일 같은 대체공휴일과 6월 3일 대통령선거일이 평일로 들어가 평일 평균을 끌어내리고 있었습니다. 2025년 관공서 공휴일 19일을 seed로 넣고, 날 종류를 평일 · 토요일 · 일요일⁠·​공휴일 셋으로 다시 나눴습니다. 그 결과는 이렇습니다.

날 종류 일수 평균 수요 평일 대비
평일 244 67,701 MW —
토요일 51 60,364 MW −10.8%
일요일⁠·​공휴일 70 56,372 MW −16.7%

긴 연휴는 앞뒤 14일 안의 평일, 쉬는 날과 각각 비교했습니다. 설 연휴(1/25~30)는 평일보다 21.6%, 추석 연휴(10/3~9)는 18.7% 낮았고, 둘 다 보통 쉬는 날보다도 8~9% 더 낮았습니다. 같은 자료로 만든 하루 전 수요 예측에서 모든 모델이 크게 틀린 날이 연휴 직후 첫 평일이었습니다. 전날 값이 연휴 수요라서, 어제 값을 쓰는 모델은 틀릴 수밖에 없습니다. 이 표가 그 크기를 숫자로 보여 줍니다.

질문 3⁠·​4. 최대 수요는 언제, 어떤 날에 나오나

월마다 평일 최대 수요가 가장 자주 나온 시각을 셌습니다. 12~2월에는 오전 8~9시대, 3~11월에는 오후 5~7시대였습니다. 계절별로 평일 하루 모양을 그려 보면 겨울에는 출근 무렵 한 번 솟고, 여름에는 오후 내내 올라 저녁 6시대에 가장 높습니다.

1년 중 하루 최대 수요 상위 10일은 모두 평일이었고, 7월 7~9일과 8월 18~29일 두 기간에 몰려 있었습니다. 1위는 8월 25일(월) 17시대 95,951 MW입니다. 무더위가 며칠 이어진 주였는데, 같은 기온이라도 더위가 이어진 날이 더 높은지는 아직 확인하지 않았습니다.

질문 5. 한낮 수요가 새벽보다 낮아지는 날

시간대 그래프를 보다가 12시대에 모든 계절에서 수요가 한 번 꺼지는 것을 봤습니다. 점심시간입니다. 그런데 봄에는 이 골이 유난히 깊었습니다. 그래서 "평일 12~13시 수요가 그날 새벽(0~7시) 최저보다 낮은 날"을 월별로 셌습니다. 4월은 22일 중 14일, 3월은 8일, 11월은 6일이었고, 6~9월과 12~1월에는 한 번도 없었습니다. 여름에는 한낮이 새벽보다 21~33% 높습니다.

냉난방이 적은 계절에, 전력망에 잡히지 않는 자가용 태양광이 낮 수요를 줄이는 현상과 맞는 모양입니다. 하지만 일사량을 붙여 "맑은 봄날일수록 더 깊은가"를 보기 전에는 원인이라고 쓰지 않기로 했습니다. 다음에 할 분석으로 남겼습니다.

질문 6⁠·​7. 데이터 직무 공고는 무엇을 요구하나

채용 공고는 Remote OK와 Arbeitnow 공개 피드에서 매일 받습니다. 공고 제목으로 데이터 엔지니어⁠·​분석가⁠·​사이언티스트를 나누고, 직무별로 기술 이름이 나온 공고의 비율을 냈습니다(11/13~20, 107건).

직무 공고 많이 나온 기술 공고당 기술 수
데이터 엔지니어 40 SQL 90%, Python 85%, Spark 68%, Databricks 63%, Airflow 50% 8.4개
데이터 분석가 37 SQL 51%, Python 35%, Tableau 27%, Power BI 24% 2.2개
데이터 사이언티스트 30 Python 83%, SQL 80%, Machine Learning 47% 3.9개

이 표는 읽을 때 조심할 점이 결과만큼 많습니다. - 1주일치 107건이라 공고 몇 건에 비율이 크게 움직입니다. 순위는 몇 주 더 쌓아 보고 판단합니다. - 대부분 독일어권 중심 피드의 공고라 국내 시장과 다릅니다. - 기술 사전 50개에 Excel⁠·​통계⁠·​A/B 테스트가 없습니다. 분석가 공고의 기술 수가 적게 나온 데는 사전의 빈틈도 섞여 있습니다. - 급여를 적은 데이터 직무 공고가 0건이라 급여는 다루지 않았습니다.

이번에 바꾼 것

  • 분석 표를 층으로 만들었습니다. dbt에 analysis 폴더를 두고 질문 하나에 표 하나(9개)를 만들었습니다. 대시보드의 '분석 요약' 문장도 매일 이 표에서 다시 계산합니다. 답을 손으로 옮겨 적으면 자료가 바뀔 때 문장이 틀린 채 남기 때문입니다.
  • 분석 표에도 테스트를 붙였습니다. (계절, 날 종류)마다 24시각이 다 있는지, 날 종류별 일수 합이 1년 일수와 같은지, 비율이 0~100 안인지 봅니다. 그래프는 자료가 빠져도 오류 없이 이상한 모양으로 그려지기 때문입니다.
  • 기온 모형은 numpy 없이 직접 풀었습니다. 매일 실행 환경의 의존성을 dbt 하나로 유지하려는 선택입니다. 알려진 기울기를 넣은 가짜 자료에서 같은 값을 다시 찾는지 테스트로 확인합니다.
  • 대시보드 탭을 질문 순서로 바꿨습니다. 분석 요약 → 전력 분석 → 채용 공고 분석 → 데이터 품질 순서이고, 지진⁠·​재해⁠·​시세는 '부가 자료'로 뺐습니다.

다른 글수집만 하던 자료를 웨어하우스로 — '24시'와 고쳐지는 지진, 그리고 처음 실행에서만 나는 실패매일 모으기만 하던 지진⁠·​전력 수요 자료를 dbt로 3단 모델링하고 Airflow DAG로 묶으면서 정한 것들. 시간 키를 시작 시각으로 잡은 이유, 고쳐진 값의 이력을 쌓는 법, 증분 집계를 믿기 위한 대조 테스트.겹쳐 있는 두 신호를 위상으로 가르기 — 파수 상관 필터링 석사 연구 정리중력과 자력 데이터를 같은 주파수 성분끼리 비교해, 함께 움직이는 성분과 반대로 움직이는 성분을 나눴다. 임계값을 감으로 정하지 않으려고 한 일들.점수를 지키면서 올리기 — VQA 챌린지에서 앙상블 후보를 고른 기준정확도가 조금 올라도 원래 맞히던 문제를 많이 틀리면 불안정한 개선이다. fixes와 breaks로 순기여를 따져 0.94608에서 시작한 점수를 쌓아 올린 과정.LLM이 붙인 [근거 N]을 코드로 다시 검사하기 — 국보 RAG 가이드의 인용 설계근거를 인용하라고 프롬프트에 써도 LLM은 없는 번호를 붙입니다. 근거 번호를 검색 단계에서 고정하고, 답변의 인용을 코드로 파싱해 없는 번호는 지우고 실제로 인용한 근거만 보여 주는 구조를 만든 기록.YAML 파일 하나로 포트폴리오⁠·​이력서⁠·​비공개 페이지까지 — 이 사이트를 만든 방식내용은 한 곳에만 쓰고, 웹 페이지⁠·​PDF 이력서⁠·​노션 문서는 빌드로 만든다. 공개하면 안 되는 내용은 저장소에 평문으로 남기지 않는다.데이터를 해석하기 전에 그 데이터가 만들어진 역사를 본다 — 학부 제1저자 논문 회고해외 대규모 CO2 저장소 8곳을 판구조 형성사와 탄성파 영상으로 비교했다. 처리 결과를 '그럴듯한지' 판단하는 기준을 어디서 가져올 것인가에 대한 이야기.길찾기에서 의사결정으로 — 배틀싸피 자동 플레이 봇을 세 번 고친 기록목표까지 가는 BFS 한 줄짜리 봇이, 사거리⁠·​장애물⁠·​탄약⁠·​보급⁠·​암호 해독까지 판단하는 봇이 되기까지. 매 턴 다시 계획하는 구조로 바꾼 이유.산불 4건으로 시공간 딥러닝 학습하기데이터가 35개 시점뿐일 때 어떻게 학습시켰고, 다시 보니 무엇이 부족했는지. U-LSTM 산불 확산 예측 모델 회고.순차 학습이 성능을 떨어뜨린 이유 — catastrophic forgetting 실험기단어 단위 → 문맥 단위로 차례로 학습하면 더 좋아질 줄 알았는데, BERTScore가 0.47에서 0.32로 떨어졌다. FLAN-T5 LoRA 학습 전략 비교.
