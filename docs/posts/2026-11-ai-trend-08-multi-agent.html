AI 트렌드 노트 #8 · 2026-11-12 · 6분 읽기

멀티 에이전트 오케스트레이션 — 나누면 빨라지지만 맥락이 끊긴다

일을 여러 에이전트에게 나눠 맡기는 구조(지휘자-작업자, 핸드오프)의 장단점을 정리했습니다. 병렬 조사에서는 효과가 보고됐지만 토큰이 크게 늘고, 맥락이 쪼개져 생기는 실패가 따로 연구될 만큼 흔합니다.

멀티 에이전트오케스트레이션에이전트

한 줄 요약 — #4의 A2A가 다른 조직의 에이전트와 일을 주고받는 규격이었다면, 이번에는 내 시스템 안에서 한 가지 일을 여러 에이전트로 나누는 설계입니다. 지난 회차의 Agentic RAG가 한 에이전트의 반복이었다면, 여기서는 그 반복을 여러 개 동시에 돌립니다. 나누면 병렬로 빨라지고 각자의 컨텍스트가 가벼워지지만, 서로가 무엇을 알고 있는지는 끊깁니다.

핵심 개념

  • 지휘자-작업자(orchestrator-worker): 지휘 에이전트가 일을 쪼개 하위 에이전트에게 나눠 주고, 돌아온 결과를 합칩니다. 하위 에이전트는 각자 깨끗한 컨텍스트에서 일하고 요약만 돌려줍니다. #5의 Plan-and-Execute에서 실행 단계를 에이전트로 바꾼 형태입니다.
  • 핸드오프(handoff): 지휘자 없이, 지금 일하는 에이전트가 "이건 환불 담당에게"처럼 대화를 통째로 다음 에이전트에게 넘깁니다. 상담 창구처럼 한 번에 한 에이전트만 사용자와 대화하는 구조에 맞습니다.
  • 비유: 혼자 보고서를 쓰면 처음부터 끝까지 맥락이 이어집니다. 팀으로 쓰면 빨리 끝나지만, 한 사람은 표를 만 원 단위로, 다른 사람은 달러로 만들어 오는 일이 생깁니다. 나눠 준 사람이 전제를 충분히 전달하지 않았기 때문입니다.
  • 나누는 이유는 둘입니다. 서로 무관한 조사를 동시에 하려는 것과, 한 에이전트의 컨텍스트 창을 아끼려는 것입니다. 역할 놀이처럼 직함만 붙인 분업은 이 둘에 해당하지 않으면 이득이 불분명합니다.

지금 무슨 일이 일어나고 있나

  • 효과가 보고된 영역은 폭넓은 조사입니다. Anthropic은 자사 리서치 기능의 구조를 공개하면서, 지휘 에이전트가 하위 에이전트를 병렬로 돌리는 방식이 단일 에이전트보다 내부 평가에서 약 90% 높았다고 밝혔습니다. 같은 글에서 이 방식이 일반 대화의 약 15배 토큰을 쓴다고도 했습니다. 두 수치 모두 2차 보도를 통해 확인한 것이고, 내부 평가 기준입니다.
  • 반대 의견도 구체적입니다. Cognition은 2025년 「Don't Build Multi-Agents」에서, 맥락을 쪼개면 하위 에이전트가 전제를 모른 채 서로 맞지 않는 결과를 만든다고 주장했습니다. 2026년 4월 후속 글에서는 실제로 동작하는 멀티 에이전트를 배포하기 시작했다고 하면서도, 여러 에이전트가 동시에 쓰는(write) 구조에는 앞선 지적이 여전히 유효하다고 했습니다. LangChain은 두 입장이 "읽기는 나누기 쉽고 쓰기는 어렵다"는 점에서 겹친다고 정리했습니다.
  • 실패가 연구 대상이 되었습니다. UC Berkeley 등의 논문 「Why Do Multi-Agent LLM Systems Fail?」은 여러 프레임워크의 실행 기록을 분석해 실패 유형 14가지를 세 묶음(시스템 설계, 에이전트 간 어긋남, 작업 검증)으로 분류했습니다(MAST). 저자들은 이런 실패가 모델 성능만의 문제가 아니어서 프롬프트 수정으로는 부족하고 구조를 고쳐야 한다고 주장합니다.

동작 구조

사용자 질문 ───▶ │ ① 일 쪼개기 (목표·범위·출력 형식 명시) │
                 └───┬──────────────┬──────────────┬─────┘
                     ▼              ▼              ▼            ← 병렬, 각자 새 컨텍스트
               하위 A (조사)   하위 B (조사)   하위 C (조사)
                     │              │              │
                     └──── 요약 + 출처만 반환 ──────┘
                                    ▼
                 ② 합치기 ─▶ ③ 검증(중복·모순·출처) ─▶ 답

def orchestrate(question):
    tasks = lead.plan(question)                 # [{"goal":…, "scope":…, "format":…}]
    for t in tasks:
        t["context"] = shared_facts(question)   # 공통 전제(단위·기간·용어)를 모두에게 같게
    results = run_parallel(worker, tasks, max_workers=4, budget_tokens=LIMIT)
    results = [r for r in results if schema_ok(r) and has_sources(r)]   # 형식·출처는 코드로
    draft = lead.merge(question, results)
    return verify(draft, results)               # 합친 답이 하위 결과에 근거하는지 확인

왜 중요한가 / 한계

  • 쓸 곳이 분명할 때는 효과가 큽니다. 서로 독립이고 각각 많은 자료를 읽어야 하는 조사는 병렬로 나누면 빨라지고, 지휘자의 컨텍스트에는 요약만 쌓입니다.
  • 한계 1 — 맥락 단절: 하위 에이전트는 지휘자가 적어 준 지시문만 압니다. 목표, 범위, 출력 형식, 공통 전제를 지시문에 명시하지 않으면 서로 어긋난 결과가 돌아옵니다.
  • 한계 2 — 비용: 토큰이 여러 배로 늘어납니다. 위 사례에서도 과제의 가치가 비용을 감당할 때만 쓰라고 권합니다.
  • 한계 3 — 동시에 쓰는 작업: 여러 에이전트가 같은 코드나 문서를 동시에 고치면 서로의 결정이 충돌합니다. 읽기는 나누고 쓰기는 한곳에서 하는 구성이 안전하다는 것이 양쪽 글의 공통점입니다.
  • 한계 4 — 디버깅과 검증: 어디서 틀렸는지 찾으려면 에이전트별 기록을 이어 붙여야 합니다. MAST가 '작업 검증'을 독립된 실패 묶음으로 둔 것처럼, 합친 결과를 확인하는 단계를 따로 두어야 합니다.

내 프로젝트와 연결

  • 멀티 에이전트 시스템을 만든 적은 없습니다. 가장 가까운 경험은 AI 챌린지 VQA의 앙상블입니다. 여러 모델의 답을 합칠 때, 새 모델을 단독 정확도가 아니라 기존 결과를 고친 문항 수와 망친 문항 수(fixes−breaks)로 채택했습니다. 에이전트를 하나 더 붙일 때도 "전체 결과가 실제로 나아지는가"를 같은 방식으로 따질 수 있다고 봅니다. 추가할수록 비용은 확실히 늘기 때문에 이 확인이 더 필요합니다.
  • 관통 7에서 Django, FastAPI 프록시, 외부 LLM을 나누고 서비스 사이를 JSON Schema 계약으로만 주고받았습니다. 형식이 깨진 응답은 통과시키지 않았습니다. 위 의사코드의 schema_ok와 같은 자리이고, 한계 1의 "출력 형식을 명시한다"를 사람이 만든 서비스 사이에서 해 본 것입니다.
  • 관통 4·5의 파이프라인은 단계를 나누되 한 흐름으로 이었습니다. 단계 사이에 전달되는 값을 코드로 검증했기 때문에 어느 단계에서 틀렸는지 찾기 쉬웠습니다. 에이전트로 나눴다면 이 추적이 더 어려워졌을 것입니다.

면접 질문

Q. 멀티 에이전트 구조를 도입할지 어떻게 판단하겠습니까?

먼저 단일 에이전트로 되는지 봅니다. 나눌 이유는 두 가지뿐이라고 생각합니다. 서로 독립인 일을 동시에 하려는 것과, 한 에이전트의 컨텍스트를 아끼려는 것입니다. 폭넓은 조사처럼 읽기 위주의 일은 나누기 좋고, 여러 에이전트가 같은 결과물을 동시에 고치는 일은 맥락이 끊겨 충돌하므로 나누지 않습니다. 도입한다면 하위 에이전트에게 목표, 범위, 출력 형식, 공통 전제를 명시하고, 돌아온 결과의 형식과 출처는 코드로 검사하고, 합친 답을 다시 확인하는 단계를 둡니다. 토큰이 여러 배로 늘기 때문에, 에이전트를 추가했을 때 결과가 실제로 나아지는지를 고친 수와 망친 수로 확인하겠습니다. VQA 앙상블에서 모델을 그렇게 골랐습니다.

Agent Card로 상대를 찾고, 상태가 있는 task로 일을 맡기는 구조와, 버전마다 바뀐 부분·엇갈리는 보도를 정리했습니다.MCP — 도구를 매번 새로 붙이지 않는 방법지난 회차의 tool use를 앱마다 다시 만들지 않도록 '도구 서버'를 표준 규격으로 분리한 MCP의 구조(호스트·클라이언트·서버, tools·resources·prompts)와 최근 사양 변화, 보안상 약한 고리를 정리했습니다.Tool use — 모델은 함수를 실행하지 않는다Function calling의 실제 동작(모델은 호출 '요청'만 만들고 실행은 내 코드가 한다), strict 스키마와 Structured Outputs의 관계, 도구를 쓸 때와 출력 형식만 고정할 때를 구분했습니다.AI 에이전트란 무엇인가 — LLM이 도구를 쥐고 반복할 때에이전트를 '도구를 쓰며 스스로 다음 단계를 정하는 LLM 루프'로 정의하고, 워크플로와 무엇이 다른지, 기업 도입 숫자가 왜 엇갈리는지 정리했습니다.
