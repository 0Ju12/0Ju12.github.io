코딩 에이전트 — 코드를 쓰는 것보다 확인하는 것이 일이다

자동 완성에서 '저장소를 읽고, 고치고, 테스트를 돌리는' 에이전트로 넘어온 흐름을 정리했습니다. 벤치마크 점수가 출처마다 엇갈리는 이유와, 사람의 일이 작성에서 검증으로 옮겨 가는 지점을 봅니다.

코딩 에이전트테스트개발 도구

한 줄 요약 — 지난 회차에서 본 SWE-bench 논란은 코딩 에이전트의 점수를 둘러싼 것이었습니다. 이번에는 그 에이전트 자체를 봅니다. 코딩 에이전트는 #5의 루프를 저장소 안에서 돌립니다. 파일을 읽고, 고치고, 명령을 실행해 결과를 보고, 다시 고칩니다. 코드를 만드는 속도가 빨라질수록, 그 코드가 맞는지 확인하는 장치가 병목이 됩니다.

핵심 개념

  • 세 단계의 변화: 자동 완성(다음 줄 제안) → 대화형 수정(선택한 코드를 설명·고침) → 에이전트(목표를 주면 여러 파일을 읽고 고치고 테스트까지 실행). 앞의 둘은 사람이 매 단계 받아들이지만, 셋째는 여러 단계를 스스로 이어 갑니다.
  • 에이전트가 쓰는 도구: 파일 읽기·검색, 편집, 셸 명령 실행(테스트·빌드·린트), 버전 관리. #2에서 본 도구 호출이 개발 환경에 연결된 형태입니다.
  • 되먹임이 품질을 정합니다. 에이전트는 테스트 실패 메시지, 컴파일 오류, 린트 경고를 읽고 다음 수정을 정합니다. 이런 신호가 없는 저장소에서는 맞는지 모른 채 "완료했다"고 말하게 됩니다.
  • 비유: 손이 매우 빠른 신입 개발자와 같습니다. 지시가 분명하고 테스트가 있으면 많은 일을 해내지만, 요구가 모호하거나 확인 수단이 없으면 그럴듯하게 틀린 코드를 빠르게 많이 만듭니다.

지금 무슨 일이 일어나고 있나

  • 주요 도구가 모두 에이전트 방식을 기본으로 삼았습니다. 터미널에서 도는 것(Claude Code, Codex CLI), 편집기에 들어간 것(Cursor), 클라우드에서 따로 돌며 변경 요청을 올리는 것으로 형태가 나뉩니다. 한 사람이 여러 에이전트에 일을 나눠 맡기는 방식(#8)도 제품에 들어왔습니다.
  • 점수는 출처마다 엇갈립니다. 이번 조사에서 SWE-bench 계열 점수를 여러 2차 자료로 봤는데, 같은 시기의 "1위"와 수치가 글마다 달랐습니다. 측정 날짜, 변형 벤치마크(Verified·Pro), 붙인 실행 틀이 다르기 때문입니다. #10에서 본 대로 Verified는 오염 논란이 있어, 이 글에서는 특정 수치를 인용하지 않습니다. 순위를 인용하려면 벤치마크 운영 측의 순위표에서 날짜와 조건을 함께 확인해야 합니다.
  • 생산성 효과도 한 방향이 아닙니다. METR의 2025년 무작위 대조 실험은 익숙한 오픈소스 저장소에서 일하는 숙련 개발자들이 AI 도구를 쓸 때 작업 시간이 오히려 약 19% 길어졌다고 보고한 것으로 알려져 있습니다. 참가자들은 자신이 빨라졌다고 느꼈다는 점이 함께 보고됐습니다. 이 실험은 당시 도구와 특정 조건의 결과이고, 이번 조사에서는 2차 자료로만 확인했습니다.

동작 구조

목표 ("결제 취소 시 재고가 복구되지 않는 버그 수정")
   │
   ▼
① 탐색: 관련 파일 검색 · 읽기 ─────────────┐
② 계획: 어디를 어떻게 고칠지              │  컨텍스트 창에 들어가는 것은
③ 편집: 파일 수정                          │  읽은 파일 일부 + 명령 출력
④ 확인: 테스트 · 빌드 · 린트 실행 ◀── 되먹임 │
   ├─ 실패 → 출력 읽고 ③으로
   └─ 통과 → ⑤ 변경 요약 + 사람 검토

def coding_agent(goal, repo, max_steps=40):
    notes = repo.read("AGENTS.md")              # 저장소 규칙: 빌드·테스트 방법, 건드리면 안 되는 곳
    for _ in range(max_steps):
        action = model.next(goal, notes, history)
        if action.kind == "edit" and not repo.allowed(action.path):
            history.add("거부: 허용되지 않은 경로")   # 권한은 코드가 정함 (#9)
            continue
        result = run(action)                    # 읽기 · 편집 · 셸
        history.add(action, result)
        if action.kind == "finish":
            break
    return repo.diff(), run("pytest -q")        # 끝났다는 말이 아니라, 테스트 결과로 판단
사람의 일 에이전트 이전 에이전트 이후
요구 정리 머릿속에 두고 바로 작성 글로 분명히 적어야 함
코드 작성 대부분의 시간 일부
확인 작성하며 자연히 따로 시간을 내서: 테스트, 검토, 실행
저장소 정비 선택 필요: 테스트·린트·문서가 되먹임이 됨

왜 중요한가 / 한계

  • 작성 비용이 내려가면 병목이 옮겨 갑니다. 무엇을 만들지 정하는 일과, 만든 것이 맞는지 확인하는 일이 남습니다.
  • 한계 1 — 그럴듯한 오답: 테스트가 없는 부분의 변경은 확인되지 않은 채 남습니다. 에이전트가 테스트를 고쳐서 통과시키는 경우도 있어, 테스트 변경은 따로 봐야 합니다.
  • 한계 2 — 이해의 공백: 직접 쓰지 않은 코드는 덜 이해하게 됩니다. 장애가 났을 때 고칠 사람이 그 코드를 모르는 상태가 됩니다.
  • 한계 3 — 권한과 보안: 에이전트는 셸을 실행합니다. 저장소의 문서나 의존성 안의 글이 지시로 읽히면(#9) 원치 않는 명령이 실행될 수 있어, 실행 범위와 비밀값 접근을 제한해야 합니다.
  • 한계 4 — 측정의 어려움: 위에서 본 대로 벤치마크 점수는 엇갈리고, 체감 속도와 실제 속도가 다를 수 있습니다. 자기 팀의 과제로 재야 합니다(#10).

내 프로젝트와 연결

  • 확인 장치를 먼저 만든 경험이 있습니다. 포트폴리오 사이트는 빌드할 때 국문·영문 항목 수 일치, 깨진 링크, 화면 넘침(46개 페이지를 두 가지 폭으로)을 스크립트로 점검하고, 통과하지 못하면 배포하지 않습니다. 최근 통계 페이지를 추가했을 때 링크 표기 하나가 이 점검에 걸려 배포가 막혔고, 고친 뒤에 올라갔습니다. 누가 코드를 썼든 같은 기준으로 걸러 내는 장치입니다.
  • 깨끗한 환경에서만 드러나는 실패도 겪었습니다. 데이터 웨어하우스 프로젝트에서 Airflow 작업이 내 환경에서는 통과하고 CI에서만 실패했는데, 원인은 처음 실행 때 폴더가 없다는 것이었습니다. 이후 "산출물을 지우고 다시 돌리기"와 그 경우의 테스트를 추가했습니다. 에이전트가 "통과했다"고 말해도 CI 결과로 판단해야 하는 이유와 같습니다.
  • SWEA 풀이 저장소를 정리하며 풀이 36개에 테스트 37개를 붙였고, 그 과정에서 버그 6개를 찾아 고쳤습니다. 테스트를 붙이기 전에는 "맞게 푼 줄 알았던" 코드였습니다.
  • 관통 4·5의 원칙인 "LLM에는 판단만 맡기고 결과는 코드로 검증한다"는 코딩 에이전트에도 그대로 적용됩니다. 다만 팀 단위로 코딩 에이전트를 운영해 본 경험은 없습니다.

면접 질문

Q. AI 코딩 도구를 어떻게 쓰고, 품질은 어떻게 보장합니까?

작성은 맡기되 확인은 사람이 책임지는 구조로 씁니다. 먼저 요구를 글로 분명히 적고, 테스트와 린트처럼 에이전트가 스스로 결과를 볼 수 있는 장치를 저장소에 갖춥니다. 완료 여부는 에이전트의 말이 아니라 CI 결과로 판단하고, 테스트 파일이 바뀐 변경은 따로 검토합니다. 실행 권한과 비밀값 접근은 최소로 둡니다. 포트폴리오 사이트에서 빌드 때 링크와 화면 넘침을 자동 점검해 통과하지 못하면 배포를 막는 것, 웨어하우스 프로젝트에서 내 환경에서는 통과했지만 CI에서 실패한 경우를 테스트로 추가한 것이 이 방식입니다. 벤치마크 점수는 출처마다 엇갈리므로, 도구 선택은 우리 과제로 직접 재서 정하겠습니다.

다른 글AI 규제·안전 — EU AI Act와 한국 AI 기본법은 개발자에게 무엇을 요구하나2026년 실제로 시행되거나 일정이 바뀐 EU AI Act와 한국 AI 기본법을 개발자 관점에서 정리했습니다. 위험도에 따라 의무가 달라지는 구조, 생성물 표시, 그리고 일정이 출처마다 엇갈리는 부분을 봅니다.멀티모달 생성 — 이미지·음성·영상을 만드는 모델은 무엇이 다른가글자 대신 이미지·음성·영상을 만들어 내는 생성 모델의 구조와 2026년의 흐름(소리까지 함께 만드는 영상 모델, 여러 입력을 섞는 모델)을 정리했습니다. 평가와 출처 표시가 텍스트보다 어려운 이유도 봅니다.비용·지연 최적화 — 캐싱·라우팅·배치로 같은 답을 더 싸고 빠르게LLM 서비스의 비용과 지연을 줄이는 세 가지 장치, 프롬프트 캐싱·모델 라우팅·배치 처리를 정리했습니다. 공식 문서의 캐시 수명과 가격 배수, 그리고 캐시가 맞지 않는 구조를 봅니다.파인튜닝 vs 프롬프트 vs RAG — 모델을 바꿀지, 입력을 바꿀지같은 문제를 프롬프트로 풀지, 검색(RAG)으로 풀지, 파인튜닝으로 풀지를 정하는 기준을 정리했습니다. 세 방법은 각각 지시·지식·행동을 바꾸고, 고르는 순서보다 평가 기준을 먼저 세우는 것이 중요합니다.소형·온디바이스 모델 — 작은 모델로 충분한 일은 얼마나 되나수십억 개 이하 파라미터의 작은 모델을 기기 안에서 돌리는 흐름을 정리했습니다. 양자화가 무엇을 줄이는지, 큰 모델과 작은 모델을 섞어 쓰는 구조, 그리고 '작아도 된다'는 주장의 조건을 봅니다.추론 모델과 test-time compute — 더 오래 생각하게 하면 무엇이 달라지나답하기 전에 생각하는 데 계산을 더 쓰는 추론 모델의 원리와, '생각 예산'을 조절할 때 생기는 비용·지연·과잉 사고 문제를 정리했습니다.컴퓨터 사용 에이전트 — 화면을 보고 클릭하는 모델API가 없는 프로그램을 사람처럼 화면으로 다루는 에이전트를 정리했습니다. 화면 캡처 → 좌표 → 행동의 루프, 벤치마크 점수가 사람 기준선을 넘었다는 보고와 그 점수를 그대로 믿기 어려운 이유를 봅니다.에이전트 평가 — 점수가 높다는 것과 믿을 수 있다는 것에이전트는 답 하나가 아니라 과정 전체를 평가해야 합니다. 채점기의 세 종류, 한 번 성공과 매번 성공의 차이, 그리고 공개 벤치마크 점수가 오염으로 흔들리는 사례를 정리했습니다.가드레일과 프롬프트 인젝션 방어 — 모델이 읽는 모든 글이 공격 경로다프롬프트 인젝션이 왜 필터 하나로 막히지 않는지, 직접·간접 인젝션의 차이와 '탐지'에서 '권한 설계'로 옮겨 가는 방어 흐름을 정리했습니다.멀티 에이전트 오케스트레이션 — 나누면 빨라지지만 맥락이 끊긴다일을 여러 에이전트에게 나눠 맡기는 구조(지휘자-작업자, 핸드오프)의 장단점을 정리했습니다. 병렬 조사에서는 효과가 보고됐지만 토큰이 크게 늘고, 맥락이 쪼개져 생기는 실패가 따로 연구될 만큼 흔합니다.RAG에서 Agentic RAG로 — 검색을 한 번 할지, 에이전트가 여러 번 할지한 번 검색해 답하는 RAG와, 검색 여부·횟수·결과 품질을 스스로 판단하는 Agentic RAG의 차이를 정리했습니다. Self-RAG·CRAG·Adaptive-RAG가 각각 어느 판단을 추가했는지와, 반복이 늘 때 생기는 비용과 평가 문제를 봅니다.에이전트 메모리 — 대화가 끝나도 남는 것과 남기면 안 되는 것컨텍스트 창 안의 단기 기억과 대화 밖에 저장하는 장기 기억을 나누고, 무엇을 쓰고 언제 꺼내는지의 설계를 정리했습니다. 한 번 오염되면 세션이 끝나도 남는 메모리 포이즈닝도 함께 봅니다.ReAct와 Plan-and-Execute — 에이전트는 어떻게 계획하나한 걸음마다 다시 생각하는 ReAct와, 먼저 계획을 세우고 실행하는 Plan-and-Execute의 차이를 비용·속도·실패 방식으로 비교했습니다. ReWOO·LLMCompiler 같은 변형과 코딩 에이전트의 plan mode까지 이어서 봅니다.에이전트 간 통신 — A2A는 MCP와 무엇이 다른가MCP가 '에이전트와 도구'를 잇는다면 A2A는 '에이전트와 에이전트'를 잇습니다. Agent Card로 상대를 찾고, 상태가 있는 task로 일을 맡기는 구조와, 버전마다 바뀐 부분·엇갈리는 보도를 정리했습니다.MCP — 도구를 매번 새로 붙이지 않는 방법지난 회차의 tool use를 앱마다 다시 만들지 않도록 '도구 서버'를 표준 규격으로 분리한 MCP의 구조(호스트·클라이언트·서버, tools·resources·prompts)와 최근 사양 변화, 보안상 약한 고리를 정리했습니다.Tool use — 모델은 함수를 실행하지 않는다Function calling의 실제 동작(모델은 호출 '요청'만 만들고 실행은 내 코드가 한다), strict 스키마와 Structured Outputs의 관계, 도구를 쓸 때와 출력 형식만 고정할 때를 구분했습니다.AI 에이전트란 무엇인가 — LLM이 도구를 쥐고 반복할 때에이전트를 '도구를 쓰며 스스로 다음 단계를 정하는 LLM 루프'로 정의하고, 워크플로와 무엇이 다른지, 기업 도입 숫자가 왜 엇갈리는지 정리했습니다.
