AI 트렌드 노트 #7 · 2026-11-12 · 6분 읽기

RAG에서 Agentic RAG로 — 검색을 한 번 할지, 에이전트가 여러 번 할지

한 번 검색해 답하는 RAG와, 검색 여부·횟수·결과 품질을 스스로 판단하는 Agentic RAG의 차이를 정리했습니다. Self-RAG·CRAG·Adaptive-RAG가 각각 어느 판단을 추가했는지와, 반복이 늘 때 생기는 비용과 평가 문제를 봅니다.

RAG에이전트검색

한 줄 요약 — 지난 회차의 메모리는 에이전트가 스스로 쓰고 꺼내는 기억이었습니다. RAG는 사람이 준비한 문서를 꺼내 쓰는 쪽입니다. 기본 RAG는 질문마다 검색 한 번, 생성 한 번으로 끝나고, Agentic RAG는 #5의 루프를 검색에 적용해 검색할지, 무엇으로 다시 검색할지, 결과가 쓸 만한지를 단계마다 판단합니다.

핵심 개념

  • 기본 RAG: 질문을 임베딩해 비슷한 문서 조각 k개를 찾고, 그것을 프롬프트에 넣어 답합니다. 흐름이 고정돼 있어 싸고 추적하기 쉽습니다. 검색이 빗나가면 틀린 근거로 그럴듯한 답을 만든다는 것이 약점입니다.
  • Agentic RAG: 검색을 도구로 두고, 모델이 판단을 끼워 넣습니다. 추가되는 판단은 크게 네 가지입니다. 검색이 필요한가, 질문을 어떻게 고쳐 쓸까, 가져온 문서가 관련 있는가, 답이 문서에 근거하는가.
  • 비유: 기본 RAG는 사서에게 쪽지를 한 번 건네고 받은 책으로 답하는 방식입니다. Agentic RAG는 받은 책을 훑어 보고 "이건 다른 주제네요, 이 키워드로 다시 찾아 주세요"라고 되묻는 방식입니다. 답은 좋아질 수 있지만 사서를 여러 번 부르는 만큼 시간이 듭니다.

지금 무슨 일이 일어나고 있나

  • 판단을 하나씩 추가한 연구들이 뼈대가 되었습니다. Self-RAG(2023)는 모델이 검색이 필요한지와 자기 답이 근거에 맞는지를 나타내는 특수 토큰(reflection token)을 내도록 학습시켰습니다. CRAG(2024)는 가져온 문서의 품질을 매기는 가벼운 평가기를 두고, 점수가 낮으면 웹 검색으로 보충하는 것으로 소개됩니다. Adaptive-RAG(2024)는 질문의 난이도를 먼저 분류해 검색 없이 답할지, 한 번 검색할지, 여러 단계로 검색할지를 고르는 방식으로 알려져 있습니다. CRAG와 Adaptive-RAG의 세부는 2차 자료로 확인했습니다.
  • 정리하는 논문이 여럿 나왔습니다. Singh 외의 서베이(arXiv 2501.09136, 2026년 4월 개정)는 Agentic RAG를 에이전트 수, 제어 구조, 자율성 등으로 분류합니다. 2026년 ACL Findings에는 데이터 관점의 서베이가 실렸고, 다른 논문은 기존의 BLEU·ROUGE 같은 정적 지표로는 Agentic RAG를 평가하기에 부족하다고 지적합니다.
  • 프레임워크에서는 그래프로 구현합니다. LangChain은 검색 → 문서 채점 → (부족하면) 질문 재작성 → 생성 → 답 점검을 노드와 조건 분기로 엮는 예제를 공개했습니다. 판단은 모델이 하되, 어느 판단 뒤에 어디로 갈 수 있는지는 코드가 정합니다.

동작 구조

기본 RAG:     질문 ─▶ 검색(k개) ─▶ 생성 ─▶ 답

Agentic RAG:  질문 ─▶ ① 검색이 필요한가? ──아니오──▶ 바로 답
                         │ 예
                         ▼
                      ② 검색 ─▶ ③ 문서가 관련 있나? ──아니오──▶ ④ 질문 다시 쓰기 ─┐
                         ▲              │ 예                                      │
                         └──────────────┼──────────────────────────────────────────┘
                                        ▼
                                     ⑤ 생성 ─▶ ⑥ 답이 문서에 근거하나? ──아니오──▶ ②로 (횟수 제한)
                                                       │ 예
                                                       ▼
                                                       답 + 인용

def agentic_rag(question, max_rounds=3):
    query = question
    for _ in range(max_rounds):                      # 반복 횟수는 코드가 제한
        docs = retriever.search(query, k=4)
        docs = [d for d in docs if grade(question, d) == "relevant"]   # ③ 문서 채점
        if not docs:
            query = rewrite(question, tried=query)   # ④ 질문 재작성
            continue
        answer = generate(question, docs)
        if cited_all_exist(answer, docs):            # ⑥ 인용 번호는 코드로 검사
            return answer
    return "자료에서 확인되지 않습니다."              # 끝까지 못 찾으면 거절

왜 중요한가 / 한계

  • 검색 실패를 스스로 알아챌 기회가 생깁니다. 기본 RAG는 빗나간 문서를 받아도 그대로 답을 만듭니다. 문서 채점과 재검색이 그 지점을 끊습니다.
  • 한계 1 — 비용과 지연: 판단마다 모델 호출이 붙습니다. 채점, 재작성, 점검을 모두 넣으면 호출 수가 몇 배가 되고, 대부분의 쉬운 질문에는 과합니다. Adaptive-RAG처럼 쉬운 질문을 먼저 걸러 내는 이유입니다.
  • 한계 2 — 판단도 모델이 합니다. "문서가 관련 있다"는 채점 자체가 틀릴 수 있습니다. 코드로 확인할 수 있는 것(인용 번호가 실제로 있는가, 숫자가 원문에 있는가)은 코드로 확인하는 편이 안전합니다.
  • 한계 3 — 평가가 어려워집니다. 경로가 질문마다 달라져서, 최종 답만 채점해서는 어디가 문제인지 알 수 없습니다. 검색 재현율, 인용 정밀도, 거절 정확도, 호출 수를 따로 재야 합니다.
  • 한계 4 — 끝나지 않는 재검색: 자료에 답이 없는 질문은 몇 번을 다시 찾아도 없습니다. 반복 횟수 제한과 "확인되지 않습니다"라는 출구가 필요합니다.

내 프로젝트와 연결

  • 국보 RAG 가이드는 위 구조 가운데 일부만 넣은 형태입니다. LangGraph로 검색 → 생성 → 근거 번호 검증을 노드로 나누었고, 답에 붙은 [근거 N]이 실제 검색 결과에 있는 번호인지는 모델이 아니라 코드로 검사했습니다. 자료에 없는 질문에는 "확인되지 않습니다"로 답하게 했습니다. 문서 채점이나 질문 재작성 같은 반복은 넣지 않았으므로, Agentic RAG라고 부르기보다는 검증이 붙은 기본 RAG에 가깝습니다.
  • 같은 프로젝트의 평가 도구는 검색 방식(similarity, MMR)과 k를 바꿔 가며 인용 정밀도, 문장 인용률, 거절 정확도, 검색 재현율을 표로 비교합니다. 한계 3에서 말한 "단계별로 따로 재기"를 작은 규모로 해 본 것입니다. 정답셋이 9문항이라 수치로 결론을 내기에는 작습니다.
  • 최근 만든 data-agent는 문서 대신 SQL로 데이터를 꺼내는 경우인데, 답 속 숫자가 조회 결과에 있는지 코드로 대조합니다. 위 그림의 ⑥을 숫자에 적용한 것입니다. 실제 LLM을 붙인 평가는 아직 하지 않았습니다.

면접 질문

Q. 기본 RAG로 충분한 경우와 Agentic RAG가 필요한 경우를 어떻게 구분하나요?

질문이 한 번의 검색으로 답할 수 있는 형태이고 문서가 잘 정리돼 있으면 기본 RAG가 맞습니다. 싸고 빠르고 추적하기 쉽습니다. 여러 문서를 이어 봐야 하거나 첫 검색이 자주 빗나가는 경우에 문서 채점과 재검색을 추가합니다. 다만 판단이 늘수록 호출 수와 지연이 늘고, 그 판단도 모델이 하므로 틀릴 수 있습니다. 그래서 인용 번호나 숫자처럼 코드로 확인할 수 있는 부분은 코드로 검사하고, 반복 횟수를 제한하고, 못 찾으면 거절하게 합니다. 국보 RAG 가이드에서 근거 번호를 코드로 검증하고, 검색 방식별로 인용 정밀도와 거절 정확도를 따로 잰 것이 같은 생각입니다.
