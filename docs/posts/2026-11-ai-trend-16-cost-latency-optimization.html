비용⁠·​지연 최적화 — 캐싱⁠·​라우팅⁠·​배치로 같은 답을 더 싸고 빠르게

LLM 서비스의 비용과 지연을 줄이는 세 가지 장치, 프롬프트 캐싱⁠·​모델 라우팅⁠·​배치 처리를 정리했습니다. 공식 문서의 캐시 수명과 가격 배수, 그리고 캐시가 맞지 않는 구조를 봅니다.

프롬프트 캐싱모델 라우팅비용

한 줄 요약 — 지난 회차는 모델을 바꿀지 입력을 바꿀지의 문제였습니다. 이번에는 같은 품질의 답을 더 싸고 빠르게 받는 방법입니다. 매번 반복해서 보내는 긴 앞부분은 캐시로 다시 읽고, 쉬운 요청은 작은 모델로 라우팅하고(#13⁠·​#14), 급하지 않은 작업은 배치로 모아 보냅니다.

핵심 개념

  • 프롬프트 캐싱: 시스템 프롬프트⁠·​도구 설명⁠·​긴 문서처럼 요청마다 똑같은 앞부분(prefix) 을 제공자 쪽에 잠깐 저장해 두고, 다음 요청에서는 처음부터 계산하지 않고 다시 읽습니다. 다시 읽은 토큰은 훨씬 싸게 과금되고 첫 토큰까지의 시간도 줄어듭니다.
  • 모델 라우팅: 요청의 난이도나 종류를 보고 작은 모델과 큰 모델 중 하나로 보냅니다. #13의 생각 예산 조절, #14의 소형 모델 분기와 같은 자리입니다.
  • 배치 처리: 즉시 답이 필요 없는 대량 작업(분류, 요약, 평가)을 모아서 보내고 몇 시간 안에 결과를 받습니다. 대신 할인을 받습니다.
  • 비유: 도서관 열람실에서 매번 같은 참고서를 서고에서 꺼내 오지 않고 책상 옆 선반에 잠깐 두는 것이 캐싱입니다. 선반에 둔 책은 일정 시간 안 보면 서고로 돌아갑니다. 간단한 질문은 안내 데스크에서, 어려운 질문은 전문 사서에게 보내는 것이 라우팅입니다.

지금 무슨 일이 일어나고 있나

  • 캐시 수명과 가격이 공식 문서에 명시돼 있습니다. Anthropic 문서 기준으로 캐시는 기본 5분 동안 유지되고, 다시 쓸 때마다 수명이 무료로 갱신됩니다. 1시간 수명도 고를 수 있습니다. 캐시를 쓰는 요청은 기본 입력 가격의 1.25배(5분) 또는 2배(1시간), 캐시를 읽는 요청은 대부분의 모델에서 0.1배이고 모델에 따라 더 낮습니다.
  • 제공자마다 기본값이 다릅니다. OpenAI 문서는 기본 캐시 수명을 30분으로 두고, 일부 API에서 12시간 수명을 더 높은 쓰기 가격에 제공한다고 적고 있습니다. 같은 "프롬프트 캐싱"이라도 수명⁠·​가격⁠·​최소 길이가 다르므로 쓰는 제공자의 문서를 직접 확인해야 합니다.
  • 2차 자료의 수치는 믿기 어렵습니다. 캐싱 가격을 비교한다는 글이 많지만, 같은 사이트의 비슷한 글이 반복되거나 확인할 수 없는 주장이 섞여 있었습니다. 이 글의 가격 배수는 공식 문서에서 확인한 것만 적었고, 금액은 모델⁠·​시기에 따라 바뀌므로 쓰지 않았습니다.
  • 비용 최적화 안내서에서 캐싱⁠·​라우팅⁠·​배치는 함께 다뤄집니다. Anthropic의 비용⁠·​지능 최적화 문서는 모델 선택, 캐싱, 배치 처리를 같은 문서에서 다룹니다. 라우팅은 별도 제품이 아니라 애플리케이션이 직접 설계하는 부분입니다.

동작 구조

요청 = [시스템 프롬프트 · 도구 설명 · 긴 문서]  +  [이번 질문]
        └──────── 매번 같음 → 캐시 ────────┘     └ 매번 다름 ┘

첫 요청:  앞부분 계산 + 캐시에 쓰기 (쓰기 가격: 기본 입력보다 비쌈)
5분 안:   앞부분 캐시에서 읽기 (읽기 가격: 기본 입력보다 훨씬 쌈) → 수명 갱신
5분 넘게 안 쓰면: 캐시 사라짐 → 다음 요청은 다시 쓰기

def handle(req):
    if not req.urgent:
        return batch_queue.add(req)                  # 할인 · 몇 시간 안에 결과
    model = "small" if is_easy(req) else "large"     # 라우팅 기준은 규칙 · 분류기 · 실패 시 승격
    messages = [
        {"role": "system", "content": SYSTEM, "cache": True},   # 바뀌지 않는 앞부분
        {"role": "user", "content": DOCS, "cache": True},
        {"role": "user", "content": req.question},              # 바뀌는 부분은 맨 뒤
    ]
    out = call(model, messages)
    log(model=model, cache_read=out.usage.cache_read, latency=out.latency)
    return out
장치 줄이는 것 맞는 경우 안 맞는 경우
캐싱 입력 비용, 첫 토큰 지연 긴 앞부분이 반복되고 요청 간격이 수명보다 짧음 앞부분이 매번 바뀜, 요청이 드묾
라우팅 출력⁠·​입력 비용, 생성 지연 쉬운 요청 비중이 큼 난이도 분류가 자주 틀림
배치 비용 몇 시간 기다려도 되는 대량 작업 사용자가 기다리는 요청

왜 중요한가 / 한계

  • 에이전트에서 효과가 큽니다. 에이전트는 한 작업에서 같은 시스템 프롬프트와 도구 설명을 수십 번 다시 보냅니다(#3⁠·​#11). 이 앞부분이 캐시되면 호출 수가 많아도 입력 비용이 덜 늘어납니다.
  • 한계 1 — 순서가 바뀌면 캐시가 깨집니다. 캐시는 앞부분이 글자 단위로 같아야 맞습니다. 시스템 프롬프트 안에 현재 시각이나 사용자 이름을 넣으면 매번 달라져 캐시가 맞지 않습니다. 바뀌는 내용은 뒤로 보내야 합니다.
  • 한계 2 — 드문 요청에서는 오히려 비쌉니다. 쓰기 가격이 기본보다 비싸기 때문에, 수명 안에 다시 읽히지 않으면 손해입니다. 캐시 적중률을 기록해 봐야 압니다.
  • 한계 3 — 라우팅은 품질 위험을 옮깁니다. 작은 모델로 보낸 요청이 틀리면 비용은 줄어도 품질이 떨어집니다. 넘기는 비율과 넘긴 뒤의 정확도를 같이 재야 합니다(#14).
  • 한계 4 — 가격은 바뀝니다. 배수와 금액은 모델과 시기에 따라 바뀌므로, 설계 문서에 숫자를 고정해 두지 말고 사용량 로그로 판단해야 합니다.

내 프로젝트와 연결

  • 한끼 Agent는 명령과 도메인 계산은 규칙으로 처리하고, 자연어 해석⁠·​보조 도구 선택⁠·​답변 문장에만 모델을 씁니다. 모델 호출이 실패해도 규칙 경로로 추천이 이어지므로, 비용이 드는 호출을 꼭 필요한 곳으로 줄인 구조입니다. 다만 요청별 토큰 수는 기록하지 않아 비용을 수치로 비교하지는 못했습니다.
  • AI 챌린지 VQA에서 Qwen 4B와 27B의 차이가 1점 미만이었던 경험은, 모든 요청을 큰 모델로 보낼 필요가 없다는 위 라우팅의 근거와 같습니다.
  • 프롬프트 캐싱과 배치 처리는 써 보지 않았습니다. 사용량 로그로 캐시 적중률을 잰 적도 없습니다.

면접 질문

Q. LLM 서비스 비용이 예상보다 많이 나온다면 무엇부터 보겠습니까?

먼저 사용량 로그에서 어디서 토큰이 쓰이는지 나눠 보겠습니다. 요청마다 같은 긴 시스템 프롬프트나 문서를 보내고 있다면 프롬프트 캐싱을 적용하고, 바뀌는 부분을 뒤로 옮겨 캐시가 맞게 하겠습니다. 쉬운 요청이 많다면 작은 모델로 보내되, 넘기는 비율과 정확도를 같이 기록하겠습니다. 급하지 않은 평가나 분류 작업은 배치로 돌리겠습니다. 한끼 Agent에서 규칙으로 풀 수 있는 일은 모델을 부르지 않게 했는데, 토큰을 기록하지 않아 효과를 수치로 보지는 못했습니다. 캐싱도 써 보지 않았기 때문에 적용한다면 토큰 기록과 적중률부터 재겠습니다.

고치고, 테스트를 돌리는' 에이전트로 넘어온 흐름을 정리했습니다. 벤치마크 점수가 출처마다 엇갈리는 이유와, 사람의 일이 작성에서 검증으로 옮겨 가는 지점을 봅니다.에이전트 평가 — 점수가 높다는 것과 믿을 수 있다는 것에이전트는 답 하나가 아니라 과정 전체를 평가해야 합니다. 채점기의 세 종류, 한 번 성공과 매번 성공의 차이, 그리고 공개 벤치마크 점수가 오염으로 흔들리는 사례를 정리했습니다.가드레일과 프롬프트 인젝션 방어 — 모델이 읽는 모든 글이 공격 경로다프롬프트 인젝션이 왜 필터 하나로 막히지 않는지, 직접⁠·​간접 인젝션의 차이와 '탐지'에서 '권한 설계'로 옮겨 가는 방어 흐름을 정리했습니다.멀티 에이전트 오케스트레이션 — 나누면 빨라지지만 맥락이 끊긴다일을 여러 에이전트에게 나눠 맡기는 구조(지휘자-작업자, 핸드오프)의 장단점을 정리했습니다. 병렬 조사에서는 효과가 보고됐지만 토큰이 크게 늘고, 맥락이 쪼개져 생기는 실패가 따로 연구될 만큼 흔합니다.RAG에서 Agentic RAG로 — 검색을 한 번 할지, 에이전트가 여러 번 할지한 번 검색해 답하는 RAG와, 검색 여부⁠·​횟수⁠·​결과 품질을 스스로 판단하는 Agentic RAG의 차이를 정리했습니다. Self-RAG⁠·​CRAG⁠·​Adaptive-RAG가 각각 어느 판단을 추가했는지와, 반복이 늘 때 생기는 비용과 평가 문제를 봅니다.에이전트 메모리 — 대화가 끝나도 남는 것과 남기면 안 되는 것컨텍스트 창 안의 단기 기억과 대화 밖에 저장하는 장기 기억을 나누고, 무엇을 쓰고 언제 꺼내는지의 설계를 정리했습니다. 한 번 오염되면 세션이 끝나도 남는 메모리 포이즈닝도 함께 봅니다.ReAct와 Plan-and-Execute — 에이전트는 어떻게 계획하나한 걸음마다 다시 생각하는 ReAct와, 먼저 계획을 세우고 실행하는 Plan-and-Execute의 차이를 비용⁠·​속도⁠·​실패 방식으로 비교했습니다. ReWOO⁠·​LLMCompiler 같은 변형과 코딩 에이전트의 plan mode까지 이어서 봅니다.에이전트 간 통신 — A2A는 MCP와 무엇이 다른가MCP가 '에이전트와 도구'를 잇는다면 A2A는 '에이전트와 에이전트'를 잇습니다. Agent Card로 상대를 찾고, 상태가 있는 task로 일을 맡기는 구조와, 버전마다 바뀐 부분⁠·​엇갈리는 보도를 정리했습니다.MCP — 도구를 매번 새로 붙이지 않는 방법지난 회차의 tool use를 앱마다 다시 만들지 않도록 '도구 서버'를 표준 규격으로 분리한 MCP의 구조(호스트⁠·​클라이언트⁠·​서버, tools⁠·​resources⁠·​prompts)와 최근 사양 변화, 보안상 약한 고리를 정리했습니다.Tool use — 모델은 함수를 실행하지 않는다Function calling의 실제 동작(모델은 호출 '요청'만 만들고 실행은 내 코드가 한다), strict 스키마와 Structured Outputs의 관계, 도구를 쓸 때와 출력 형식만 고정할 때를 구분했습니다.AI 에이전트란 무엇인가 — LLM이 도구를 쥐고 반복할 때에이전트를 '도구를 쓰며 스스로 다음 단계를 정하는 LLM 루프'로 정의하고, 워크플로와 무엇이 다른지, 기업 도입 숫자가 왜 엇갈리는지 정리했습니다.
