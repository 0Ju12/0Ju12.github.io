모델 호출을 프록시 한곳에 모으고, 모델의 대답부터 의심하기

관통 7에서 Django와 AI 모델 사이에 FastAPI 프록시를 두며 정한 것들 — Guardrail이 고장 나면 막는 쪽으로, API마다 다른 이미지 응답을 한 모양으로, 로그에는 구조만 남기기.

FastAPILLMGuardrail설계

SSAFY 관통 프로젝트 7회차는 AI 기능을 별도 서버로 떼어 내는 것이었습니다. 지난 회차까지는 Django 뷰가 외부 AI를 직접 불렀는데, 이번에는 Django → FastAPI 프록시 → SSAFY GMS 순서로 요청이 지나가게 바꿨습니다.

2인 팀에서 FastAPI 프록시와 AI 연동, 테스트를 맡았습니다. 화면(Django)은 팀원이 맡았습니다.

Django (8080) ──▶ FastAPI 프록시 (8081) ──▶ GMS
                   ├─ Guardrail          (부적절한 요청은 생성 전에 403)
                   ├─ 라우트 결정        (텍스트 추천 / 표지 이미지)
                   ├─ 난이도별 모델      (간단 nano · 복잡 mini)
                   └─ 텍스트·분석·TTS는 OpenAI 호환 API, 이미지는 Gemini API

1. 키와 모델 선택을 한곳에

프록시를 두는 이유는 단순했습니다. GMS 키는 프록시의 .env에만 있고, 어떤 모델을 쓸지, 응답이 쓸 만한지 판단하는 코드도 프록시에만 있습니다. Django는 "추천해 줘", "표지 만들어 줘"라고 보내고 정해진 모양의 결과만 받습니다.

시간 제한도 층마다 따로 두었습니다. 프록시 → GMS는 120초, Django → 프록시는 180초입니다. 안쪽이 먼저 끊겨야 바깥에서 원인이 보이는 오류 화면을 띄울 수 있기 때문입니다.

2. Guardrail이 고장 나면 막는 쪽으로

Guardrail은 요청이 적절한지 모델에게 묻는 단계입니다. 답은 JSON Schema(strict)로 is_appropriate 불리언 하나만 받도록 했습니다.

고민한 건 모델이 엉뚱한 답을 줄 때였습니다. JSON이 깨지거나 불리언 대신 문자열이 오면, "판단 실패니까 그냥 통과"로 처리하면 Guardrail이 없는 것과 같습니다. 그래서 형식이 맞지 않으면 생성을 진행하지 않고 503을 돌려주도록 했습니다(fail-closed).

data = structured_answer(messages, "guardrail_response", {"is_appropriate": {"type": "boolean"}}, model)
if type(data["is_appropriate"]) is not bool:
    raise HTTPException(503, "model server error")

라우트 결정(enum 두 값), 점수(0~100 정수), 모델 등급(simple/complex)도 같은 방식입니다. 스키마로 한 번, 코드로 한 번 더 확인합니다. LLM 응답을 코드로 검증하던 관통 4·5의 원칙을 그대로 가져왔습니다.

3. 이미지 응답은 네 가지 모양이었다

표지 이미지는 처음에 명세서의 모델로 요청했는데 GMS에서 지원하지 않아 400이 났고, Gemini 이미지 모델로 바꿨습니다. 그러자 문제가 하나씩 드러났습니다.

  • Gemini는 OpenAI 호환 주소가 아니라 별도 게이트웨이로, Authorization: Bearer가 아니라 x-goog-api-key 헤더로 보내야 합니다.
  • 응답 안에서 이미지가 들어 있는 자리가 API·버전마다 달랐습니다. candidates 아래 inlineData, output_image, steps 아래 content, outputs 네 가지였습니다.
  • 받은 이미지는 PNG나 WEBP인데, Django는 .jpg로 저장하고 있었습니다.

그래서 네 형태를 모두 찾아보는 추출 함수를 두고, 찾은 이미지는 크기(20MB)·픽셀 수(2,500만) 제한을 확인한 뒤 Pillow로 실제 JPEG로 다시 인코딩해서 넘겼습니다. Django는 어느 API가 쓰였는지 몰라도 항상 같은 image_base64를 받습니다.

4. 디버깅 로그에도 비밀은 남기지 않는다

이미지가 왜 안 나오는지 보려면 GMS 응답을 봐야 했습니다. 하지만 응답을 그대로 찍으면 base64 이미지나 인증 관련 문자열이 로그에 남을 수 있습니다.

그래서 응답의 구조만 요약하는 함수를 따로 만들었습니다. 정해진 키 이름, 리스트 길이, 문자열 길이만 출력하고 값은 출력하지 않습니다.

[GMS 이미지 응답 구조] {"candidates": {"_list_length": 0, "_sample": []}, "_field_count": 1}

이 로그 덕분에 "인증은 통과했는데 이미지가 비어 있다"와 "인증부터 실패했다(401)"를 구분할 수 있었습니다.

5. 확인한 것과 못 한 것

테스트 20개는 GMS를 부르지 않고 mock으로 계약을 확인합니다. Guardrail true/false, 형식 오류 시 503, 거부되면 이미지 생성을 아예 호출하지 않는지(호출 1회), 라우트 2종, 난이도별 모델 선택, 점수 범위, 이미지 MIME 판별과 잘못된 base64(422), TTS, Gemini 게이트웨이 주소·헤더, PNG→JPEG 변환, 401을 안전한 503으로 바꾸는 것까지 다룹니다.

다만 실제 GMS에서 이미지 생성이 끝까지 성공하는 것은 확인하지 못했습니다. 응답에 이미지가 담기지 않은 사례가 있었고, 팀 README에도 미확인으로 남겼습니다.

저장소에는 직접 구현한 프록시 코드와 테스트만 올렸습니다. SSAFY가 제공한 GMS 호출 함수와 스키마 원본, 팀원이 맡은 Django 화면은 빼고, 빠진 자리는 공개용 대체 코드라고 표시했습니다.

정리

  • 모델 호출을 프록시 한곳에 모으면 키 관리·모델 선택·응답 검증이 한 파일에 모인다.
  • 안전장치가 판단을 못 하면 통과가 아니라 차단이 기본값이어야 한다.
  • 외부 API의 응답 모양이 여러 가지라면 그 차이는 프록시가 흡수하고, 뒤쪽에는 한 가지 모양만 넘긴다.
