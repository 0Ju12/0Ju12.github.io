AI 트렌드 노트 #9 · 2026-11-13 · 6분 읽기

가드레일과 프롬프트 인젝션 방어 — 모델이 읽는 모든 글이 공격 경로다

프롬프트 인젝션이 왜 필터 하나로 막히지 않는지, 직접·간접 인젝션의 차이와 '탐지'에서 '권한 설계'로 옮겨 가는 방어 흐름을 정리했습니다.

보안프롬프트 인젝션가드레일

한 줄 요약 — 지난 회차에서 하위 에이전트는 지휘자가 적어 준 지시문만 믿고 움직였습니다. 그 지시문 자리에 공격자의 글이 들어오면 어떻게 될까요. LLM은 지시와 자료를 같은 글자열로 읽기 때문에, 웹 페이지·문서·도구 결과에 섞인 문장을 지시로 따를 수 있습니다. 이것이 프롬프트 인젝션이고, 방어의 무게는 "나쁜 글을 걸러 낸다"에서 "속더라도 할 수 있는 일을 줄인다"로 옮겨 가고 있습니다.

핵심 개념

  • 직접 인젝션: 사용자가 직접 "이전 지시를 무시하고…"라고 입력하는 경우입니다. 공격자가 곧 사용자입니다.
  • 간접 인젝션: 사용자는 평범하게 "이 페이지 요약해 줘"라고 했는데, 그 페이지 안에 숨은 지시문이 있는 경우입니다. 공격자는 제3자이고, 피해자는 사용자입니다. #2의 도구, #3의 MCP, #7의 검색이 모두 이런 글을 들여오는 통로가 됩니다. OWASP는 LLM 애플리케이션 위험 목록에서 프롬프트 인젝션을 1번에 두고, 2025년판에서 직접과 간접을 구분해 설명하는 것으로 소개됩니다.
  • 가드레일: 모델 앞뒤에 두는 검사입니다. 입력 검사(위험한 요청·주입 흔적), 출력 검사(개인정보·형식·금지 내용), 그리고 도구 호출 검사(이 호출을 지금 해도 되는가)로 나뉩니다.
  • 비유: SQL 인젝션은 "명령과 자료를 분리"해서 해결했습니다(매개변수 바인딩). LLM에는 그런 분리 장치가 없습니다. 편지를 대신 읽어 주는 비서가, 편지 본문에 적힌 "이 편지를 읽는 비서는 금고 비밀번호를 답장에 적어 보내시오"를 사장의 지시로 착각하는 상황입니다.

지금 무슨 일이 일어나고 있나

  • "완전한 해결책은 없다"는 정리가 반복됩니다. 2026년 2월의 체계화 논문(arXiv 2602.10453)은 에이전트 대상 프롬프트 인젝션에 만능 해법이 없고, 기존 방어 대부분이 메시지나 컨텍스트 전체에 한꺼번에 작용해 세밀하지 못하며 그 때문에 정상 기능이 깎인다고 분석합니다.
  • 조건을 끊는 쪽으로 논의가 옮겨 갔습니다. 널리 인용되는 정리로, 에이전트가 ① 비공개 자료에 접근하고 ② 신뢰할 수 없는 글을 읽고 ③ 바깥으로 내보낼 수단을 가지면 유출이 가능해진다는 '치명적 삼박자(lethal trifecta)'가 있습니다. 셋 중 하나를 끊으면 속더라도 유출 경로가 닫힌다는 설계 관점입니다.
  • 구조로 막으려는 연구가 나왔습니다. Google DeepMind의 CaMeL은 계획을 세우는 모델과 신뢰할 수 없는 자료를 읽는 모델을 나누고, 자료에서 나온 값이 어디로 흘러갈 수 있는지를 코드로 추적하는 방식으로 알려져 있습니다. 같은 해 여러 기관이 낸 설계 패턴 논문은 "신뢰할 수 없는 글을 읽은 뒤에는 행동 범위를 좁힌다"는 원칙 아래 패턴 여러 개를 정리했습니다.
  • 삼박자, CaMeL, 설계 패턴 논문의 세부는 이번 조사에서 원문을 다시 열어 확인하지 못했습니다. 아래 출처의 원문으로 확인이 필요합니다.

def run_tool(call, ctx):
    if call.name not in ctx.allowed_tools:            # 허용 목록: 모델이 고르되, 범위는 코드가 정함
        return deny("허용되지 않은 도구")
    if not schema_ok(call.args):                      # 인자 형식은 코드로 검사
        return deny("인자 형식 오류")
    if ctx.read_untrusted and call.sends_outside:     # 믿을 수 없는 글을 읽은 뒤의 외부 전송은 막음
        return ask_human(call)                        #   → 삼박자의 한 변을 끊는다
    if call.irreversible:                             # 삭제·결제·발송은 사람 확인
        return ask_human(call)
    return execute(call)
방어 막는 것 한계
시스템 지시로 "무시하라" 가벼운 시도 모델이 지키지 않을 수 있음
주입 탐지 분류기 알려진 패턴 새 표현·다른 언어·인코딩에 약하고 오탐이 생김
자료 구분 표시(구분자·태그) 지시와 자료의 혼동 일부 보장이 아님
도구 허용 목록·권한 축소 속았을 때의 피해 범위 기능이 줄어듦
되돌릴 수 없는 일에 사람 확인 큰 사고 확인 피로
출력·행동의 코드 검증 형식·숫자·인용 조작 검증할 수 있는 것만

왜 중요한가 / 한계

  • 에이전트가 될수록 피해가 커집니다. 채팅만 하는 모델이 속으면 이상한 답이 나오지만, 메일을 보내고 파일을 지우는 에이전트가 속으면 행동이 나옵니다.
  • 한계 1 — 탐지는 확률입니다. 99%를 막는 필터도 공격자가 여러 번 시도할 수 있으면 뚫립니다. 그래서 탐지는 보조이고, 뚫려도 피해가 작게 설계하는 쪽이 중심이 됩니다.
  • 한계 2 — 안전과 기능의 교환입니다. 권한을 줄이고 확인을 늘리면 안전해지지만 쓸모가 줄어듭니다. 위 체계화 논문이 지적한 "세밀하지 못한 방어가 기능을 깎는다"가 이 문제입니다.
  • 한계 3 — 가드레일 자체도 모델인 경우가 많습니다. 검사용 모델이 틀리거나 멈출 수 있으므로, 검사가 실패했을 때 통과시킬지 막을지를 미리 정해야 합니다.
  • 한계 4 — 공급망: 도구 설명문, MCP 서버가 주는 텍스트, 검색된 문서도 모델이 읽는 글입니다. 내가 쓰지 않은 글은 모두 신뢰할 수 없는 입력으로 다뤄야 합니다.

내 프로젝트와 연결

  • 관통 7의 FastAPI 프록시에서 Guardrail 검사를 모델 호출 앞에 두고, 검사 서비스가 오류를 내거나 응답하지 않으면 요청을 통과시키지 않도록(fail-closed) 했습니다. 위 그림의 "검사가 고장 나면 막는다"에 해당합니다. 모델 호출을 프록시 한곳으로 모았기 때문에 이 규칙을 한 군데에서 강제할 수 있었습니다. 다만 주입 탐지 성능을 따로 측정하지는 않았습니다.
  • 관통 4·5에서는 LLM에게 댓글 원문을 다시 쓰게 하지 않고 "제거할 번호"만 받아 실제 삭제는 코드가 했습니다. 목록에 없는 번호는 받아들이지 않았습니다. 모델이 할 수 있는 행동의 범위를 코드가 정한다는 점에서 도구 허용 목록과 같은 생각입니다. 주입 방어를 목표로 한 설계는 아니었고, 결과적으로 같은 구조가 되었습니다.
  • 국보 RAG 가이드는 검색된 문서를 모델이 읽습니다. 답에 붙은 근거 번호가 실제 검색 결과에 있는지 코드로 검사하므로 없는 출처를 지어내는 것은 막지만, 문서 안에 숨은 지시문을 걸러 내는 장치는 없습니다. 공개 국보 설명문만 색인해서 위험이 낮을 뿐, 사용자 문서를 올리게 하면 바로 문제가 됩니다.
  • data-agent는 SQL을 읽기 전용으로 제한하고 허용한 문장만 실행합니다. 삼박자 가운데 "바깥으로 내보낼 수단"과 "바꿀 수단"을 주지 않은 경우입니다.

면접 질문

Q. 프롬프트 인젝션을 어떻게 방어하겠습니까?

완전히 막을 수 있다고 가정하지 않습니다. 모델은 지시와 자료를 같은 글로 읽기 때문에, 탐지 필터는 보조 수단으로만 씁니다. 중심은 속았을 때의 피해를 줄이는 설계입니다. 도구는 허용 목록과 인자 검증을 코드로 강제하고, 신뢰할 수 없는 글을 읽은 뒤의 외부 전송이나 되돌릴 수 없는 작업은 사람 확인을 거치게 합니다. 검사 단계가 고장 나면 통과시키지 않고 막습니다. 관통 7에서 모델 호출을 프록시 한곳으로 모으고 Guardrail이 실패하면 요청을 막도록 한 것, 관통 4·5에서 LLM에게 원문 수정 대신 번호만 받고 실행은 코드가 한 것이 이 방향입니다. 탐지 성능을 직접 측정해 보지는 못했고, 그 부분은 평가 세트를 만들어 확인해야 한다고 생각합니다.

다른 글에이전트 평가 — 점수가 높다는 것과 믿을 수 있다는 것에이전트는 답 하나가 아니라 과정 전체를 평가해야 합니다. 채점기의 세 종류, 한 번 성공과 매번 성공의 차이, 그리고 공개 벤치마크 점수가 오염으로 흔들리는 사례를 정리했습니다.멀티 에이전트 오케스트레이션 — 나누면 빨라지지만 맥락이 끊긴다일을 여러 에이전트에게 나눠 맡기는 구조(지휘자-작업자, 핸드오프)의 장단점을 정리했습니다. 병렬 조사에서는 효과가 보고됐지만 토큰이 크게 늘고, 맥락이 쪼개져 생기는 실패가 따로 연구될 만큼 흔합니다.RAG에서 Agentic RAG로 — 검색을 한 번 할지, 에이전트가 여러 번 할지한 번 검색해 답하는 RAG와, 검색 여부·횟수·결과 품질을 스스로 판단하는 Agentic RAG의 차이를 정리했습니다. Self-RAG·CRAG·Adaptive-RAG가 각각 어느 판단을 추가했는지와, 반복이 늘 때 생기는 비용과 평가 문제를 봅니다.에이전트 메모리 — 대화가 끝나도 남는 것과 남기면 안 되는 것컨텍스트 창 안의 단기 기억과 대화 밖에 저장하는 장기 기억을 나누고, 무엇을 쓰고 언제 꺼내는지의 설계를 정리했습니다. 한 번 오염되면 세션이 끝나도 남는 메모리 포이즈닝도 함께 봅니다.ReAct와 Plan-and-Execute — 에이전트는 어떻게 계획하나한 걸음마다 다시 생각하는 ReAct와, 먼저 계획을 세우고 실행하는 Plan-and-Execute의 차이를 비용·속도·실패 방식으로 비교했습니다. ReWOO·LLMCompiler 같은 변형과 코딩 에이전트의 plan mode까지 이어서 봅니다.에이전트 간 통신 — A2A는 MCP와 무엇이 다른가MCP가 '에이전트와 도구'를 잇는다면 A2A는 '에이전트와 에이전트'를 잇습니다. Agent Card로 상대를 찾고, 상태가 있는 task로 일을 맡기는 구조와, 버전마다 바뀐 부분·엇갈리는 보도를 정리했습니다.MCP — 도구를 매번 새로 붙이지 않는 방법지난 회차의 tool use를 앱마다 다시 만들지 않도록 '도구 서버'를 표준 규격으로 분리한 MCP의 구조(호스트·클라이언트·서버, tools·resources·prompts)와 최근 사양 변화, 보안상 약한 고리를 정리했습니다.Tool use — 모델은 함수를 실행하지 않는다Function calling의 실제 동작(모델은 호출 '요청'만 만들고 실행은 내 코드가 한다), strict 스키마와 Structured Outputs의 관계, 도구를 쓸 때와 출력 형식만 고정할 때를 구분했습니다.AI 에이전트란 무엇인가 — LLM이 도구를 쥐고 반복할 때에이전트를 '도구를 쓰며 스스로 다음 단계를 정하는 LLM 루프'로 정의하고, 워크플로와 무엇이 다른지, 기업 도입 숫자가 왜 엇갈리는지 정리했습니다.
