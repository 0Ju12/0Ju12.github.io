에이전트 평가 — 점수가 높다는 것과 믿을 수 있다는 것

에이전트는 답 하나가 아니라 과정 전체를 평가해야 합니다. 채점기의 세 종류, 한 번 성공과 매번 성공의 차이, 그리고 공개 벤치마크 점수가 오염으로 흔들리는 사례를 정리했습니다.

평가벤치마크에이전트

한 줄 요약 — 지난 회차 끝에서 "탐지 성능은 평가 세트를 만들어 확인해야 한다"고 적었습니다. 그 평가가 이번 주제입니다. 에이전트는 같은 질문에도 매번 다른 경로로 움직이므로, 최종 답만 채점해서는 부족합니다. 무엇을 볼지(결과·과정), 누가 채점할지(코드·모델·사람), 몇 번 중 몇 번을 성공으로 볼지를 정해야 하고, 공개 벤치마크 점수는 그 가운데 일부만 말해 줍니다.

핵심 개념

  • 결과와 과정: 결과(outcome)는 작업이 끝난 뒤 환경의 상태입니다. 테스트가 통과했는가, 예약이 실제로 들어갔는가. 과정(transcript)은 에이전트가 한 말과 호출한 도구의 기록입니다. 답은 맞았는데 금지된 방법으로 맞혔을 수 있고, 답은 틀렸는데 한 단계만 어긋났을 수 있습니다.
  • 채점기 세 종류
  • 코드 채점: 테스트 통과, 문자열·숫자 일치, 상태 비교. 빠르고 재현되지만 정해진 것만 봅니다.
  • 모델 채점(LLM-as-judge): 기준표를 주고 다른 모델이 채점합니다. 말투·충실도처럼 코드로 못 보는 것을 보지만, 채점 자체가 흔들립니다.
  • 사람 채점: 기준이 되지만 느리고 비쌉니다. 앞의 두 채점기가 맞는지 확인하는 용도로 씁니다.
  • 한 번 성공과 매번 성공: 같은 과제를 k번 시켰을 때 한 번이라도 성공하는 비율(pass@k)과 k번 모두 성공하는 비율(pass^k)은 다른 이야기를 합니다. 코드 후보를 여러 개 뽑아 고르는 일에는 앞의 것이, 고객 응대처럼 매번 맞아야 하는 일에는 뒤의 것이 맞습니다.
  • 비유: 운전면허 시험과 같습니다. 필기(지식 벤치마크) 점수가 높아도 도로 주행(과제 수행)은 따로 봐야 하고, 한 번 합격했다고 매일 사고 없이 운전한다는 뜻은 아닙니다.

지금 무슨 일이 일어나고 있나

  • 대표 코딩 벤치마크가 신뢰를 잃었습니다. OpenAI는 2026년 2월 SWE-bench Verified 점수를 더 보고하지 않겠다고 밝히고 SWE-bench Pro를 권했습니다. 공개 저장소에서 만든 문제라 학습 자료에 섞였을 가능성이 커졌다는 이유입니다. Epoch AI도 같은 벤치마크를 "결함 있음"으로 평가했습니다. 한 논문(arXiv 2512.10218)은 모델이 이 벤치마크에서 비슷한 다른 파이썬 과제보다 약 3배 높은 점수를 냈고, 맥락을 거의 주지 않아도 고칠 파일을 잘 찾았다고 보고하면서, 능력보다 기억일 가능성을 제기합니다.
  • 점수는 모델만의 것이 아닙니다. 같은 모델도 어떤 도구와 실행 틀(하네스)을 붙였는지에 따라 점수가 달라져, 순위표끼리 직접 비교하기 어렵다는 지적이 함께 나옵니다.
  • 자기 과제로 평가를 만들라는 안내가 늘었습니다. Anthropic은 2026년 1월 엔지니어링 글에서 채점기를 코드·모델·사람으로 나누고, 과정과 결과를 구분해 채점하며, 실행 기록을 직접 읽어 채점기가 공정한지 확인하라고 권했습니다. 새 능력을 재는 평가와, 이미 되던 것이 깨지지 않았는지 보는 회귀 평가를 구분하는 내용도 있습니다. 이 글의 세부는 2차 요약으로 확인했습니다.

동작 구조

과제 묶음 ─▶ 에이전트 실행 (과제마다 k번) ─▶ 실행 기록 + 최종 상태
                                                   │
               ┌───────────────────────────────────┼───────────────────────────┐
               ▼                                   ▼                           ▼
        코드 채점기                          모델 채점기                    사람 검토
   (테스트·상태·숫자·인용)              (기준표 → 점수 + 이유)           (표본 추출)
               │                                   │                           │
               └──────────────┬────────────────────┘        채점기끼리 얼마나 일치하나?
                              ▼                               어긋난 건을 읽고 기준표 수정
              과제별 성공률 · pass^k · 비용 · 단계 수 · 실패 유형

def evaluate(agent, tasks, k=5):
    rows = []
    for task in tasks:
        runs = [agent.run(task) for _ in range(k)]            # 같은 과제를 여러 번
        ok = [task.check_state(r.final_state) for r in runs]  # 결과: 코드로 확인
        rows.append({
            "task": task.id,
            "pass_any": any(ok),                               # 한 번이라도
            "pass_all": all(ok),                               # 매번
            "steps": mean(len(r.transcript) for r in runs),
            "cost": mean(r.tokens for r in runs),
            "violations": sum(broke_rule(r.transcript) for r in runs),   # 과정: 금지된 방법을 썼나
        })
    return rows
채점기 잘 보는 것 주의할 점
코드 정답이 정해진 것, 형식, 상태 맞는 답의 다른 표현을 틀렸다고 할 수 있음
모델 충실도·말투·설명의 질 길이·순서·자기 답에 대한 편향, 실행마다 흔들림
사람 기준 그 자체 느리고 비쌈, 사람끼리도 어긋남

왜 중요한가 / 한계

  • 평가가 없으면 바꾼 것이 나아졌는지 알 수 없습니다. 프롬프트 한 줄, 모델 교체, 도구 추가가 전체를 좋게 했는지 나쁘게 했는지는 느낌으로 판단되지 않습니다.
  • 한계 1 — 공개 벤치마크의 오염: 문제가 공개되는 순간부터 학습 자료에 들어갈 수 있습니다. 위 사례처럼 점수가 능력이 아니라 기억을 잴 수 있습니다.
  • 한계 2 — 채점기도 평가 대상입니다. 모델 채점은 사람 채점과 얼마나 일치하는지 먼저 확인해야 하고, 코드 채점은 옳은 답을 틀렸다고 하지 않는지 봐야 합니다.
  • 한계 3 — 평균이 숨기는 것: 성공률 90%는 열 번 중 한 번은 실패한다는 뜻입니다. 실패한 한 번이 무엇인지, 같은 과제에서 반복되는지를 따로 봐야 합니다.
  • 한계 4 — 내 과제와의 거리: 벤치마크 과제와 실제 업무가 다르면 순위가 뒤집힐 수 있습니다. 작더라도 내 과제로 만든 평가 세트가 필요합니다.

내 프로젝트와 연결

  • 국보 RAG 가이드의 평가 도구는 코드 채점기만 썼습니다. 인용 정밀도, 문장 인용률, 거절 정확도, 검색 재현율을 LLM 없이 계산하고, 근거와 겹침이 낮은 문장을 "사람이 먼저 볼 목록"으로 뽑습니다. 모델 채점은 넣지 않았습니다. 정답셋이 9문항이라 설정 사이의 차이를 결론 내리기에는 작습니다.
  • AI 챌린지 VQA에서는 정확도 하나로 모델을 고르지 않고, 새 후보가 기존에 틀리던 문항을 몇 개 고쳤고 맞히던 문항을 몇 개 망쳤는지(fixes−breaks)를 봤습니다. 위에서 말한 "평균이 숨기는 것"을 문항 단위로 본 것이고, 회귀 평가와 같은 생각입니다.
  • 설비 센서 이상 탐지에서는 무작위 분할로 0.99가 나오던 모델이 시간 구간으로 나누자 밸브에서 0.46이 되었습니다. 평가 자료가 학습 자료와 겹치면 점수가 부풀려진다는 점에서, 벤치마크 오염과 같은 종류의 문제를 작은 규모로 겪은 사례입니다.
  • data-agent는 답 속 숫자가 조회 결과에 있는지 코드로 대조하는 검사를 만들었지만, 실제 LLM을 붙여 과제 묶음으로 평가하지는 않았습니다. 이 글의 절차를 적용해야 할 첫 대상입니다.

면접 질문

Q. LLM 기능의 품질을 어떻게 평가하겠습니까?

먼저 내 과제로 작은 평가 세트를 만듭니다. 공개 벤치마크 점수는 학습 자료에 섞였을 수 있고 내 업무와 다를 수 있기 때문입니다. 채점은 코드로 확인할 수 있는 것부터 코드로 합니다. 형식, 숫자, 인용 번호, 최종 상태가 여기에 듭니다. 코드로 볼 수 없는 충실도 같은 것은 모델 채점을 쓰되, 사람 채점과 얼마나 일치하는지 표본으로 먼저 확인합니다. 그리고 평균만 보지 않고, 같은 과제를 여러 번 돌려 매번 성공하는지와, 변경 전후로 고친 건수와 망친 건수를 따로 봅니다. 국보 RAG 가이드에서 인용 정밀도와 거절 정확도를 코드로 계산한 것, VQA에서 fixes−breaks로 후보를 고른 것이 이 방식입니다. 정답셋이 9문항으로 작았던 점은 한계였습니다.

다른 글가드레일과 프롬프트 인젝션 방어 — 모델이 읽는 모든 글이 공격 경로다프롬프트 인젝션이 왜 필터 하나로 막히지 않는지, 직접·간접 인젝션의 차이와 '탐지'에서 '권한 설계'로 옮겨 가는 방어 흐름을 정리했습니다.멀티 에이전트 오케스트레이션 — 나누면 빨라지지만 맥락이 끊긴다일을 여러 에이전트에게 나눠 맡기는 구조(지휘자-작업자, 핸드오프)의 장단점을 정리했습니다. 병렬 조사에서는 효과가 보고됐지만 토큰이 크게 늘고, 맥락이 쪼개져 생기는 실패가 따로 연구될 만큼 흔합니다.RAG에서 Agentic RAG로 — 검색을 한 번 할지, 에이전트가 여러 번 할지한 번 검색해 답하는 RAG와, 검색 여부·횟수·결과 품질을 스스로 판단하는 Agentic RAG의 차이를 정리했습니다. Self-RAG·CRAG·Adaptive-RAG가 각각 어느 판단을 추가했는지와, 반복이 늘 때 생기는 비용과 평가 문제를 봅니다.에이전트 메모리 — 대화가 끝나도 남는 것과 남기면 안 되는 것컨텍스트 창 안의 단기 기억과 대화 밖에 저장하는 장기 기억을 나누고, 무엇을 쓰고 언제 꺼내는지의 설계를 정리했습니다. 한 번 오염되면 세션이 끝나도 남는 메모리 포이즈닝도 함께 봅니다.ReAct와 Plan-and-Execute — 에이전트는 어떻게 계획하나한 걸음마다 다시 생각하는 ReAct와, 먼저 계획을 세우고 실행하는 Plan-and-Execute의 차이를 비용·속도·실패 방식으로 비교했습니다. ReWOO·LLMCompiler 같은 변형과 코딩 에이전트의 plan mode까지 이어서 봅니다.에이전트 간 통신 — A2A는 MCP와 무엇이 다른가MCP가 '에이전트와 도구'를 잇는다면 A2A는 '에이전트와 에이전트'를 잇습니다. Agent Card로 상대를 찾고, 상태가 있는 task로 일을 맡기는 구조와, 버전마다 바뀐 부분·엇갈리는 보도를 정리했습니다.MCP — 도구를 매번 새로 붙이지 않는 방법지난 회차의 tool use를 앱마다 다시 만들지 않도록 '도구 서버'를 표준 규격으로 분리한 MCP의 구조(호스트·클라이언트·서버, tools·resources·prompts)와 최근 사양 변화, 보안상 약한 고리를 정리했습니다.Tool use — 모델은 함수를 실행하지 않는다Function calling의 실제 동작(모델은 호출 '요청'만 만들고 실행은 내 코드가 한다), strict 스키마와 Structured Outputs의 관계, 도구를 쓸 때와 출력 형식만 고정할 때를 구분했습니다.AI 에이전트란 무엇인가 — LLM이 도구를 쥐고 반복할 때에이전트를 '도구를 쓰며 스스로 다음 단계를 정하는 LLM 루프'로 정의하고, 워크플로와 무엇이 다른지, 기업 도입 숫자가 왜 엇갈리는지 정리했습니다.
