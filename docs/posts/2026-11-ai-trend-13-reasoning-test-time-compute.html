추론 모델과 test-time compute — 더 오래 생각하게 하면 무엇이 달라지나

답하기 전에 생각하는 데 계산을 더 쓰는 추론 모델의 원리와, '생각 예산'을 조절할 때 생기는 비용·지연·과잉 사고 문제를 정리했습니다.

추론 모델test-time compute비용

한 줄 요약 — 지난 두 회차의 에이전트(#11 코딩, #12 컴퓨터 사용)는 여러 단계를 이어 가며 일했습니다. 그 한 단계 안에서도 모델은 계산을 더 쓸 수 있습니다. 추론 모델은 답을 쓰기 전에 보이지 않는 중간 풀이를 길게 만들고, 그만큼 어려운 문제를 더 잘 풉니다. 학습 때가 아니라 답할 때 쓰는 계산(test-time compute) 을 늘리는 방식이고, 이제는 얼마나 생각할지를 사용자가 조절합니다.

핵심 개념

  • 두 종류의 계산: 모델의 능력은 학습 때 쓴 계산과 답할 때 쓰는 계산 양쪽에서 나옵니다. 예전에는 앞쪽을 키웠고, 추론 모델은 뒤쪽을 늘립니다.
  • 생각 토큰: 답 앞에 생성되는 중간 풀이입니다. 사용자에게는 요약만 보이거나 보이지 않지만 출력 토큰으로 과금되고, 그만큼 응답이 늦어집니다.
  • 생각 예산: 주요 모델들은 "노력 수준"이나 "생각 토큰 한도" 같은 조절 장치를 제공합니다. 모델이 문제마다 생각할지를 스스로 정하는 방식(적응형)도 있습니다.
  • 다른 형태의 test-time compute: 길게 생각하는 것만이 아닙니다. 같은 질문에 여러 번 답하게 해 다수결을 내거나, 후보를 여러 개 만들고 검증기로 고르거나, 입력을 여러 방식으로 보여 주고 결과를 합치는 것도 답할 때 계산을 더 쓰는 방법입니다.
  • 비유: 시험에서 암산으로 바로 답을 쓰는 것과 연습장에 풀이를 적는 것의 차이입니다. 연습장을 쓰면 어려운 문제의 정답률이 오르지만 시간이 듭니다. "1+1"에 연습장 한 장을 쓰면 낭비이고, 가끔은 길게 풀다가 오히려 틀립니다.

지금 무슨 일이 일어나고 있나

  • 조절 장치가 기본 기능이 되었습니다. 2026년 자료들은 OpenAI, Anthropic, Google, DeepSeek 등이 모두 노력 수준 조절을 제공한다고 정리합니다. 설계 문제는 "추론 모델을 쓸까"에서 "어느 요청에 얼마나 생각하게 할까"로 바뀌었습니다.
  • 과잉 사고가 보고됩니다. 쉬운 문제에 수천 토큰을 쓰는 사례, 생각을 길게 할수록 오히려 틀리게 되는 과제를 구성한 연구(Anthropic, 2025)가 인용됩니다. 후자는 단순한 세기 문제에서 모델이 관계없는 세부에 끌려가는 경우를 보였다고 소개됩니다.
  • 예산을 나눠 쓰는 능력은 별개입니다. 2026년 8월 논문 「Thinking Hard, Not Smart」는 여러 문제가 하나의 계산·시간 예산을 나눠 써야 할 때, 현재 추론 모델이 난이도와 가치에 맞게 예산을 배분하지 못한다고 보고합니다. 문제 하나씩 따로 평가해서는 드러나지 않는 능력이라는 지적입니다.
  • 점수 비교가 더 어려워졌습니다. 같은 달의 다른 논문은 벤치마크 점수가 평가에서 허용한 생각 예산에 따라 달라진다고 지적합니다. #10에서 본 "조건이 다르면 점수를 비교할 수 없다"에 변수가 하나 더 생긴 셈입니다.
  • 위 내용 가운데 개별 수치와 일부 연구의 세부는 2차 자료로 확인했습니다.

동작 구조

일반 모델:   질문 ─▶ 답
추론 모델:   질문 ─▶ [생각 …………] ─▶ 답        생각 토큰: 과금됨 · 지연됨 · 대개 보이지 않음

여러 번 답하기:   질문 ─┬▶ 답 A ─┐
                        ├▶ 답 B ─┼▶ 다수결 / 검증기로 선택 ─▶ 답
                        └▶ 답 C ─┘

def answer(question):
    level = route(question)                 # 쉬움 / 보통 / 어려움 — 규칙이나 작은 모델로 분류
    if level == "easy":
        return fast_model(question)                        # 생각 없이
    if level == "medium":
        return reasoning_model(question, effort="low")
    out = reasoning_model(question, effort="high", max_thinking=8000)
    if not verify(out):                     # 코드로 확인할 수 있으면 확인
        out = reasoning_model(question, effort="high", hint=verify.error)   # 실패 이유를 주고 한 번 더
    return out
선택 얻는 것 치르는 것
생각 없음·낮음 빠른 응답, 낮은 비용 여러 단계 추론에서 실수
생각 높음 어려운 문제의 정답률 지연(수 초~수십 초), 생각 토큰 비용, 쉬운 문제에서의 낭비
여러 번 답하기 흔들림 감소 호출 수만큼 비용
검증 후 재시도 확인 가능한 오류 제거 검증기를 만들 수 있는 문제에만

왜 중요한가 / 한계

  • 비용 구조가 바뀝니다. 같은 질문이라도 생각 수준에 따라 비용과 지연이 몇 배 달라집니다. 요청을 난이도로 나눠 보내는 일(#16에서 다룰 라우팅)이 필요해집니다.
  • 한계 1 — 어디에 쓸지 모델이 잘 모릅니다. 위 연구처럼 쉬운 문제에 많이 쓰고 어려운 문제에 덜 쓰는 일이 생깁니다. 배분을 사람이나 규칙이 정해야 하는 경우가 많습니다.
  • 한계 2 — 길게 생각한다고 항상 낫지 않습니다. 단순한 문제에서는 오히려 틀릴 수 있습니다.
  • 한계 3 — 보이는 풀이가 실제 과정이라는 보장이 없습니다. 모델이 적은 풀이가 실제 내부 계산을 그대로 반영하지 않을 수 있다는 연구들이 있습니다. 풀이가 그럴듯하다는 것을 답이 맞다는 근거로 삼으면 안 됩니다. 이 부분은 이번 조사에서 1차 자료를 다시 확인하지 못했습니다.
  • 한계 4 — 생각으로 지식을 만들 수는 없습니다. 모르는 사실은 오래 생각해도 모릅니다. 그런 문제는 검색(#7)이 답입니다.

내 프로젝트와 연결

  • AI 챌린지 VQA의 멀티뷰 앙상블은 답할 때 계산을 더 쓰는 방식이었습니다. 같은 이미지를 해상도와 자르기를 바꿔 여러 번 보여 주고 확률을 합쳤습니다. 위 표의 "여러 번 답하기"에 해당합니다. 추가한 관점이 실제로 도움이 되는지는 정확도가 아니라 고친 문항 수와 망친 문항 수(fixes−breaks)로 판단했고, 계산을 더 쓴다고 항상 나아지지 않는다는 것을 그때 확인했습니다. 추론 모델의 생각 예산을 조절해 본 것은 아닙니다.
  • 관통 7의 FastAPI 프록시에서는 요청 종류(텍스트·이미지)와 필요에 따라 모델 등급을 고르게 했습니다. 모든 요청을 가장 큰 모델로 보내지 않는다는 점에서 위 의사코드의 route와 같은 자리입니다. 다만 난이도를 자동으로 분류하지는 않았고, 호출하는 쪽이 등급을 정했습니다.
  • 국보 RAG 가이드의 근거 번호 검증은 "검증 후 재시도"의 앞 절반입니다. 없는 번호를 코드로 지우기만 하고, 실패 이유를 모델에 돌려줘 다시 쓰게 하지는 않았습니다.
  • 석사 연구에서 파수 상관 필터의 임계값을 정할 때, 계산을 더 들여 여러 값을 훑는 것과 한 값을 감으로 정하는 것 사이의 선택이 있었습니다. 모델이 아니라 사람의 분석이지만, "어디에 계산을 쓸지"를 먼저 정해야 한다는 점은 같았습니다.

면접 질문

Q. 추론 모델을 서비스에 쓴다면 어떻게 적용하겠습니까?

모든 요청에 쓰지 않고, 난이도로 나눠 보내겠습니다. 추론 모델은 답하기 전에 생각 토큰을 쓰는데, 이게 과금되고 응답을 늦춥니다. 쉬운 요청은 빠른 모델로, 여러 단계 추론이 필요한 요청만 생각 수준을 높여 보냅니다. 모델이 예산을 스스로 잘 배분하지 못한다는 보고가 있어, 배분은 규칙이나 분류기로 정하는 편이 안전하다고 봅니다. 그리고 생각 수준을 올린 것이 실제로 나아졌는지는 우리 과제로 확인합니다. VQA 챌린지에서 이미지를 여러 방식으로 보여 주고 확률을 합치는 방식을 썼는데, 관점을 추가할 때마다 고친 문항과 망친 문항을 세어 채택 여부를 정했습니다. 계산을 더 쓴다고 항상 좋아지지 않았기 때문입니다.

다른 글소형·온디바이스 모델 — 작은 모델로 충분한 일은 얼마나 되나수십억 개 이하 파라미터의 작은 모델을 기기 안에서 돌리는 흐름을 정리했습니다. 양자화가 무엇을 줄이는지, 큰 모델과 작은 모델을 섞어 쓰는 구조, 그리고 '작아도 된다'는 주장의 조건을 봅니다.컴퓨터 사용 에이전트 — 화면을 보고 클릭하는 모델API가 없는 프로그램을 사람처럼 화면으로 다루는 에이전트를 정리했습니다. 화면 캡처 → 좌표 → 행동의 루프, 벤치마크 점수가 사람 기준선을 넘었다는 보고와 그 점수를 그대로 믿기 어려운 이유를 봅니다.코딩 에이전트 — 코드를 쓰는 것보다 확인하는 것이 일이다자동 완성에서 '저장소를 읽고, 고치고, 테스트를 돌리는' 에이전트로 넘어온 흐름을 정리했습니다. 벤치마크 점수가 출처마다 엇갈리는 이유와, 사람의 일이 작성에서 검증으로 옮겨 가는 지점을 봅니다.에이전트 평가 — 점수가 높다는 것과 믿을 수 있다는 것에이전트는 답 하나가 아니라 과정 전체를 평가해야 합니다. 채점기의 세 종류, 한 번 성공과 매번 성공의 차이, 그리고 공개 벤치마크 점수가 오염으로 흔들리는 사례를 정리했습니다.가드레일과 프롬프트 인젝션 방어 — 모델이 읽는 모든 글이 공격 경로다프롬프트 인젝션이 왜 필터 하나로 막히지 않는지, 직접·간접 인젝션의 차이와 '탐지'에서 '권한 설계'로 옮겨 가는 방어 흐름을 정리했습니다.멀티 에이전트 오케스트레이션 — 나누면 빨라지지만 맥락이 끊긴다일을 여러 에이전트에게 나눠 맡기는 구조(지휘자-작업자, 핸드오프)의 장단점을 정리했습니다. 병렬 조사에서는 효과가 보고됐지만 토큰이 크게 늘고, 맥락이 쪼개져 생기는 실패가 따로 연구될 만큼 흔합니다.RAG에서 Agentic RAG로 — 검색을 한 번 할지, 에이전트가 여러 번 할지한 번 검색해 답하는 RAG와, 검색 여부·횟수·결과 품질을 스스로 판단하는 Agentic RAG의 차이를 정리했습니다. Self-RAG·CRAG·Adaptive-RAG가 각각 어느 판단을 추가했는지와, 반복이 늘 때 생기는 비용과 평가 문제를 봅니다.에이전트 메모리 — 대화가 끝나도 남는 것과 남기면 안 되는 것컨텍스트 창 안의 단기 기억과 대화 밖에 저장하는 장기 기억을 나누고, 무엇을 쓰고 언제 꺼내는지의 설계를 정리했습니다. 한 번 오염되면 세션이 끝나도 남는 메모리 포이즈닝도 함께 봅니다.ReAct와 Plan-and-Execute — 에이전트는 어떻게 계획하나한 걸음마다 다시 생각하는 ReAct와, 먼저 계획을 세우고 실행하는 Plan-and-Execute의 차이를 비용·속도·실패 방식으로 비교했습니다. ReWOO·LLMCompiler 같은 변형과 코딩 에이전트의 plan mode까지 이어서 봅니다.에이전트 간 통신 — A2A는 MCP와 무엇이 다른가MCP가 '에이전트와 도구'를 잇는다면 A2A는 '에이전트와 에이전트'를 잇습니다. Agent Card로 상대를 찾고, 상태가 있는 task로 일을 맡기는 구조와, 버전마다 바뀐 부분·엇갈리는 보도를 정리했습니다.MCP — 도구를 매번 새로 붙이지 않는 방법지난 회차의 tool use를 앱마다 다시 만들지 않도록 '도구 서버'를 표준 규격으로 분리한 MCP의 구조(호스트·클라이언트·서버, tools·resources·prompts)와 최근 사양 변화, 보안상 약한 고리를 정리했습니다.Tool use — 모델은 함수를 실행하지 않는다Function calling의 실제 동작(모델은 호출 '요청'만 만들고 실행은 내 코드가 한다), strict 스키마와 Structured Outputs의 관계, 도구를 쓸 때와 출력 형식만 고정할 때를 구분했습니다.AI 에이전트란 무엇인가 — LLM이 도구를 쥐고 반복할 때에이전트를 '도구를 쓰며 스스로 다음 단계를 정하는 LLM 루프'로 정의하고, 워크플로와 무엇이 다른지, 기업 도입 숫자가 왜 엇갈리는지 정리했습니다.
