11/19 Databricks Genie ZeroOps 공개 베타 — 실패한 파이프라인을 찾고 고침안까지 내는 에이전트

Databricks가 작업⁠·​파이프라인⁠·​테이블을 지켜보다가 실패와 품질 문제를 찾아 원인을 추적하고, 고친 코드를 PR로 제안하는 에이전트 Genie ZeroOps를 공개 베타로 열었습니다. 사람 승인 없이는 바꾸지 않는다는 조건과 베타의 범위를 정리했습니다.

이슈 분석데이터 엔지니어링데이터 품질

한 줄 요약 — #23에서는 운영 DB와 분석 저장소를 한 플랫폼에서 잇는 흐름을 봤고, #21에서는 에이전트의 동작을 테이블에 기록하는 방식을 봤습니다. 이번에는 방향이 반대입니다. 사람이 만든 데이터 파이프라인을 에이전트가 지켜보는 쪽입니다. Databricks는 11월 19일 블로그에서 Genie ZeroOps를 공개 베타로 열었다고 밝혔습니다. 작업이 실패하거나, 성공했는데 테이블이 비거나 오래된 경우를 찾아 원인을 추적하고, 고친 코드를 PR로 제안하되 사람이 승인하기 전에는 바꾸지 않는 에이전트입니다. #11(코딩 에이전트)과 #9(가드레일)가 데이터 운영에 들어온 사례입니다.

핵심 개념

  • 데이터 파이프라인 운영(on-call): 매일 도는 수집⁠·​변환 작업이 실패하면 누군가 로그를 보고 원인을 찾아 고칩니다. 실패가 오류로 드러나면 그나마 낫고, 더 까다로운 쪽은 작업은 성공했는데 결과 테이블이 비었거나 오래된 경우입니다.
  • 계보(lineage): 어떤 테이블이 어떤 테이블에서 만들어졌는지 잇는 정보입니다. 아래쪽 테이블이 이상할 때 위로 거슬러 올라가 원인을 찾는 데 씁니다.
  • 드라이 런(dry run): 실제 데이터를 바꾸지 않고, 고친 코드가 돌아가는지 격리된 환경에서 먼저 실행해 보는 것입니다.
  • 비유: 공장 생산 라인을 밤새 지켜보다가 불량이 나오면 어느 공정에서 생겼는지 거슬러 찾고, 고칠 방법을 시험대에서 먼저 돌려 본 뒤 반장에게 승인 요청서를 올리는 야간 점검원과 비슷합니다. 점검원이 라인을 직접 바꾸지는 않습니다.

지금 무슨 일이 일어나고 있나

  • 공개 베타. Databricks는 11월 19일 블로그 글("lessons from 80,000 customer issues")에서 Genie ZeroOps를 공개 베타로 열었고, 작업 공간 관리자가 Previews 페이지에서 켤 수 있다고 밝혔습니다. 11월 릴리스 노트에는 같은 기능이 11월 12일 자 'Beta'로 올라 있어 날짜가 엇갈립니다. 몇 주 전 Databricks 답변 페이지에는 아직 '비공개 미리보기'로 적혀 있습니다.
  • 무엇을 찾나. 공식 문서에 따르면 작업⁠·​파이프라인⁠·​테이블을 백그라운드에서 지켜보며 세 가지를 찾습니다.
  • 실패한 작업과 파이프라인
  • 성공했지만 오래되거나 불완전한 테이블을 만든 작업
  • 갱신이 멈췄거나 데이터가 빠진 테이블
  • 어떻게 처리하나. 블로그는 다섯 단계로 설명합니다. 찾기(detect) → 조사(investigate) → 검증(verify) → 알림(notify) → 고침(remediate)입니다. 검증 단계에서는 격리된 환경에서 단위 테스트와 드라이 런을 돌려 원인 가설을 확인한 뒤에 고침안을 냅니다.
  • 사람 승인. 문서는 "사용자의 직접 승인 없이는 코드나 데이터를 바꾸지 않는다"고 적습니다. PR은 열 수 있지만, 운영 코드와 데이터는 사람이 검토하기 전에 바뀌지 않습니다.
  • 권한과 공유. Unity Catalog 권한 안에서만 동작하고, 설정은 작업 공간 사용자 최대 25명과 공유할 수 있습니다. 그룹이나 서비스 주체(service principal)와는 공유할 수 없습니다.
  • 베타의 범위. 작업⁠·​파이프라인⁠·​테이블만 지켜보고, 모델이나 앱은 대상이 아닙니다. 성능이나 비용이 나빠지는 문제(회귀)도 찾지 않습니다.
  • 확인 범위. 위 내용은 Databricks 공식 도메인(databricks.com, docs.databricks.com)으로 범위를 제한한 검색 결과에 실린 블로그⁠·​문서⁠·​릴리스 노트 발췌로 확인했습니다.

동작 구조

작업·파이프라인·테이블 (Unity Catalog 권한 안)
   │  계속 지켜봄
   ▼
① 찾기 ── 실패 / 성공했지만 비거나 오래된 테이블 / 갱신 멈춤
   ▼
② 조사 ── 로그 + 계보를 거슬러 원인 후보
   ▼
③ 검증 ── 격리 환경에서 단위 테스트·드라이 런
   ▼
④ 알림 ── 담당자에게 원인과 근거
   ▼
⑤ 고침 ── PR 제안 ──▶ 사람 승인 ──▶ 반영   (승인 없으면 운영은 그대로)

"성공했지만 결과가 이상한" 경우를 찾는 규칙은 대체로 다음과 같은 모양입니다.

def check_table(t, now):
    issues = []
    if now - t.last_updated > t.expected_interval * 2:
        issues.append("stale")                      # 갱신이 멈춤
    if t.last_run.status == "success" and t.last_run.rows_written == 0:
        issues.append("empty_success")              # 성공했는데 쓴 행이 없음
    if t.row_count < t.rolling_median_rows * 0.5:
        issues.append("volume_drop")                # 평소의 절반 아래
    return issues

왜 중요한가 / 한계

  • '성공했지만 틀린' 실패를 기본으로 봅니다. 오류로 끝난 작업은 기존 알림으로도 잡힙니다. 데이터 쪽에서 오래 문제가 되는 것은 작업은 성공했는데 테이블이 비었거나 오래된 경우입니다. 이를 탐지 대상으로 명시했다는 점이 이 기능의 핵심입니다.
  • 고치는 권한은 사람에게 남깁니다. #11의 코딩 에이전트처럼 코드를 고치되, 운영 반영은 PR 승인을 거칩니다. #9에서 본 "행동 범위를 코드가 정한다"를 데이터 운영에 옮긴 형태이고, #20의 원격 MCP처럼 권한은 카탈로그 권한을 그대로 따릅니다.
  • 한계 1 — 베타 범위가 좁습니다. 모델⁠·​앱은 대상이 아니고, 성능⁠·​비용 회귀도 찾지 않습니다. 느려지거나 비싸지는 문제는 여전히 따로 봐야 합니다.
  • 한계 2 — 공유 단위. 그룹이나 서비스 주체와 공유할 수 없어, 팀 단위 당번 체계에 바로 붙이기는 어렵습니다.
  • 한계 3 — 고침안의 품질은 아직 외부 수치가 없습니다. "고객 문제 8만 건에서 얻은 교훈"이라는 설명은 Databricks의 것이고, 고침안이 얼마나 맞았는지 외부에서 잰 결과는 찾지 못했습니다.

내 프로젝트와 연결

  • API Watch는 공개 API 22개를 정기 점검하면서, HTTP 200을 받아도 자료가 오래됐거나 비었거나 구조가 바뀐 경우를 따로 판정합니다. 연속 실패는 이슈 한 건으로 모읍니다. ZeroOps가 "성공했지만 오래되거나 불완전한 테이블"을 찾는 것과 같은 문제의식입니다. 다만 저는 원인 추적과 고침안 제안까지는 만들지 않았습니다.
  • 공개 데이터 웨어하우스에는 지진 목록이 14일 넘게 갱신되지 않으면 실패가 아닌 경고를 내는 테스트, 채용 공고 수집 구간에 빈틈이 생기면 경고하는 테스트를 두었습니다. 위 의사코드의 stale·volume_drop에 해당합니다.
  • 한끼 에이전트의 로깅 에이전트는 모델 없이 규칙으로 중복 호출⁠·​연속 실패⁠·​재계획 상한 도달을 판정합니다. ZeroOps도 판정과 고침안을 나누고, 고침은 사람 승인 뒤에 반영하는 구조입니다.

면접 질문

Q. 데이터 파이프라인에서 '작업은 성공했는데 결과가 틀린' 문제를 어떻게 잡겠습니까?

작업 상태와 별개로 결과 테이블을 검사하겠습니다. 마지막 갱신 시각이 예상 주기의 두 배를 넘었는지, 쓴 행이 0인지, 행 수가 평소 중앙값의 절반 아래로 떨어졌는지를 보는 규칙을 두고, 실패가 아닌 경고로 먼저 알리겠습니다. API Watch에서 HTTP 200이어도 오래된 자료를 따로 판정했고, 웨어하우스에서는 지진 목록 갱신이 14일 넘게 멈추면 경고하게 했습니다. 자동으로 고치는 단계를 붙인다면, 고침안은 PR로만 내고 반영은 사람이 승인하게 하겠습니다.

수명과 가격 배수, 그리고 캐시가 맞지 않는 구조를 봅니다.파인튜닝 vs 프롬프트 vs RAG — 모델을 바꿀지, 입력을 바꿀지같은 문제를 프롬프트로 풀지, 검색(RAG)으로 풀지, 파인튜닝으로 풀지를 정하는 기준을 정리했습니다. 세 방법은 각각 지시⁠·​지식⁠·​행동을 바꾸고, 고르는 순서보다 평가 기준을 먼저 세우는 것이 중요합니다.소형⁠·​온디바이스 모델 — 작은 모델로 충분한 일은 얼마나 되나수십억 개 이하 파라미터의 작은 모델을 기기 안에서 돌리는 흐름을 정리했습니다. 양자화가 무엇을 줄이는지, 큰 모델과 작은 모델을 섞어 쓰는 구조, 그리고 '작아도 된다'는 주장의 조건을 봅니다.추론 모델과 test-time compute — 더 오래 생각하게 하면 무엇이 달라지나답하기 전에 생각하는 데 계산을 더 쓰는 추론 모델의 원리와, '생각 예산'을 조절할 때 생기는 비용⁠·​지연⁠·​과잉 사고 문제를 정리했습니다.컴퓨터 사용 에이전트 — 화면을 보고 클릭하는 모델API가 없는 프로그램을 사람처럼 화면으로 다루는 에이전트를 정리했습니다. 화면 캡처 → 좌표 → 행동의 루프, 벤치마크 점수가 사람 기준선을 넘었다는 보고와 그 점수를 그대로 믿기 어려운 이유를 봅니다.코딩 에이전트 — 코드를 쓰는 것보다 확인하는 것이 일이다자동 완성에서 '저장소를 읽고, 고치고, 테스트를 돌리는' 에이전트로 넘어온 흐름을 정리했습니다. 벤치마크 점수가 출처마다 엇갈리는 이유와, 사람의 일이 작성에서 검증으로 옮겨 가는 지점을 봅니다.에이전트 평가 — 점수가 높다는 것과 믿을 수 있다는 것에이전트는 답 하나가 아니라 과정 전체를 평가해야 합니다. 채점기의 세 종류, 한 번 성공과 매번 성공의 차이, 그리고 공개 벤치마크 점수가 오염으로 흔들리는 사례를 정리했습니다.가드레일과 프롬프트 인젝션 방어 — 모델이 읽는 모든 글이 공격 경로다프롬프트 인젝션이 왜 필터 하나로 막히지 않는지, 직접⁠·​간접 인젝션의 차이와 '탐지'에서 '권한 설계'로 옮겨 가는 방어 흐름을 정리했습니다.멀티 에이전트 오케스트레이션 — 나누면 빨라지지만 맥락이 끊긴다일을 여러 에이전트에게 나눠 맡기는 구조(지휘자-작업자, 핸드오프)의 장단점을 정리했습니다. 병렬 조사에서는 효과가 보고됐지만 토큰이 크게 늘고, 맥락이 쪼개져 생기는 실패가 따로 연구될 만큼 흔합니다.RAG에서 Agentic RAG로 — 검색을 한 번 할지, 에이전트가 여러 번 할지한 번 검색해 답하는 RAG와, 검색 여부⁠·​횟수⁠·​결과 품질을 스스로 판단하는 Agentic RAG의 차이를 정리했습니다. Self-RAG⁠·​CRAG⁠·​Adaptive-RAG가 각각 어느 판단을 추가했는지와, 반복이 늘 때 생기는 비용과 평가 문제를 봅니다.에이전트 메모리 — 대화가 끝나도 남는 것과 남기면 안 되는 것컨텍스트 창 안의 단기 기억과 대화 밖에 저장하는 장기 기억을 나누고, 무엇을 쓰고 언제 꺼내는지의 설계를 정리했습니다. 한 번 오염되면 세션이 끝나도 남는 메모리 포이즈닝도 함께 봅니다.ReAct와 Plan-and-Execute — 에이전트는 어떻게 계획하나한 걸음마다 다시 생각하는 ReAct와, 먼저 계획을 세우고 실행하는 Plan-and-Execute의 차이를 비용⁠·​속도⁠·​실패 방식으로 비교했습니다. ReWOO⁠·​LLMCompiler 같은 변형과 코딩 에이전트의 plan mode까지 이어서 봅니다.에이전트 간 통신 — A2A는 MCP와 무엇이 다른가MCP가 '에이전트와 도구'를 잇는다면 A2A는 '에이전트와 에이전트'를 잇습니다. Agent Card로 상대를 찾고, 상태가 있는 task로 일을 맡기는 구조와, 버전마다 바뀐 부분⁠·​엇갈리는 보도를 정리했습니다.MCP — 도구를 매번 새로 붙이지 않는 방법지난 회차의 tool use를 앱마다 다시 만들지 않도록 '도구 서버'를 표준 규격으로 분리한 MCP의 구조(호스트⁠·​클라이언트⁠·​서버, tools⁠·​resources⁠·​prompts)와 최근 사양 변화, 보안상 약한 고리를 정리했습니다.Tool use — 모델은 함수를 실행하지 않는다Function calling의 실제 동작(모델은 호출 '요청'만 만들고 실행은 내 코드가 한다), strict 스키마와 Structured Outputs의 관계, 도구를 쓸 때와 출력 형식만 고정할 때를 구분했습니다.AI 에이전트란 무엇인가 — LLM이 도구를 쥐고 반복할 때에이전트를 '도구를 쓰며 스스로 다음 단계를 정하는 LLM 루프'로 정의하고, 워크플로와 무엇이 다른지, 기업 도입 숫자가 왜 엇갈리는지 정리했습니다.
