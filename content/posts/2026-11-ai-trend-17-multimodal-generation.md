> **한 줄 요약** — 지난 회차까지는 모델이 글자를 만드는 경우만 다뤘습니다. 이미지·음성·영상을 **만드는** 모델은 출력의 크기와 형태가 달라서 구조도, 비용도, 평가 방식도 달라집니다. 2026년에는 영상과 소리를 **한 번에** 만들고, 글·이미지·음성·영상을 섞어 지시하는 모델이 잇달아 나왔습니다.

## 핵심 개념

- **이해와 생성은 다릅니다**: 이미지를 보고 답하는 모델(이미지 → 글)과 이미지를 만드는 모델(글 → 이미지)은 다른 문제입니다. 앞쪽은 출력이 짧은 글이고, 뒤쪽은 출력이 수백만 개의 픽셀입니다.
- **확산(diffusion) 방식**: 잡음에서 시작해 조금씩 잡음을 걷어 내며 이미지를 만듭니다. 영상은 여기에 시간 축이 더해집니다.
- **토큰 방식**: 이미지·소리를 작은 조각(토큰)으로 바꿔 글처럼 이어서 생성합니다. 언어 모델과 같은 구조를 쓸 수 있다는 장점이 있습니다.
- **잠재 공간**: 원본 픽셀이 아니라 압축된 표현 위에서 생성한 뒤 마지막에 복원합니다. 계산량을 줄이는 핵심 장치입니다.
- **비유**: 글 생성이 원고를 쓰는 일이라면 영상 생성은 촬영·녹음·편집을 한꺼번에 하는 일입니다. 원고는 한 줄씩 고칠 수 있지만, 영상은 한 장면만 고쳐도 앞뒤 장면과 소리가 맞아야 합니다.

## 지금 무슨 일이 일어나고 있나

- **소리까지 함께 만드는 영상 모델.** ByteDance Seed 팀은 2026년 2월 Seedance 2.0을 공개하며 글·이미지·소리·영상을 섞은 입력과 소리·영상 동시 생성을 소개했습니다. MiniMax는 7월 말 H3를 발표하며 글·이미지·영상·소리를 함께 이해하고 소리가 들어간 영상을 최대 2K, 15초까지 만든다고 밝혔습니다. 예전에는 영상을 만든 뒤 소리를 따로 입히는 방식이 많았습니다.
- **여러 입력을 섞는 모델.** Google은 5월 I/O에서 글·이미지·소리·영상을 섞어 영상을 만들고 고치는 Gemini Omni 계열을 발표한 것으로 보도됐습니다. 이번 조사에서는 Google 원문이 아니라 2차 보도로만 확인했습니다.
- **공개 가중치 약속과 실제의 차이.** 일부 회사는 가중치 공개를 예고했지만, 조사 시점에는 API로만 쓸 수 있는 경우가 있었습니다. 성능 수치도 대부분 회사가 직접 낸 것이라, 독립적인 비교는 아직 부족합니다.

## 동작 구조

```
입력 (글 · 참고 이미지 · 소리 · 영상)
   │ 인코더: 각 입력을 같은 표현 공간으로
   ▼
잠재 공간에서 생성 (확산 또는 토큰을 이어 붙이는 방식)
   │  영상 프레임 + 소리 파형을 함께 → 입 모양과 소리가 맞아야 함
   ▼
디코더: 픽셀·파형으로 복원 ─▶ 결과 영상 (+ 생성물 표시·워터마크)
```

```python
def make_clip(prompt, ref_image=None):
    job = video_api.create(prompt=prompt, image=ref_image, seconds=8, audio=True)
    while job.status == "running":                 # 글과 달리 수십 초~수 분 걸리는 비동기 작업
        sleep(5); job = video_api.get(job.id)
    clip = job.result
    checks = {
        "length_ok": abs(clip.seconds - 8) < 0.5,  # 요청한 조건은 코드로 확인
        "has_audio": clip.audio is not None,
        "labeled": clip.metadata.get("ai_generated") is True,
    }
    return clip, checks                            # 내용이 맞는지는 사람이 본다
```

| | 글 생성 | 이미지·영상·음성 생성 |
|---|---|---|
| 출력 크기 | 수백~수천 토큰 | 수백만 픽셀, 초당 수십 프레임 |
| 응답 방식 | 바로 흘려보냄 | 비동기 작업, 수십 초 이상 |
| 비용 단위 | 토큰 | 장 수 · 초 · 해상도 |
| 자동 평가 | 정답 비교 가능한 경우 많음 | 어려움 (사람 평가·선호 비교 위주) |
| 출처 표시 | 근거 문서 인용 | 생성물 표시·워터마크 |

## 왜 중요한가 / 한계

- **서비스 설계가 달라집니다.** 결과가 바로 나오지 않으므로 작업 대기열, 진행 상태 표시, 실패 시 재시도가 필요합니다. 관통 5에서 30초 넘는 작업의 진행 상황을 흘려보낸 것과 같은 문제를 더 크게 겪게 됩니다.
- **한계 1 — 평가가 어렵습니다.** "이 영상이 지시를 잘 따랐나"는 정답이 하나가 아닙니다. 길이·해상도·소리 유무처럼 코드로 확인할 수 있는 것과, 사람이 봐야 하는 것을 나눠야 합니다(#10).
- **한계 2 — 일관성.** 같은 인물·물체가 장면마다 바뀌거나 물리적으로 맞지 않는 움직임이 생기는 문제가 여전히 보고됩니다.
- **한계 3 — 비용과 시간.** 몇 초짜리 영상도 글 답변보다 훨씬 많은 계산을 씁니다. 캐싱처럼 재사용할 방법도 제한적입니다(#16).
- **한계 4 — 진위와 권리.** 실제와 구분하기 어려운 결과물이 나오므로 생성물 표시, 초상권·저작권 문제가 따라옵니다. 다음 회차의 규제와 직접 이어집니다.

## 내 프로젝트와 연결

- **AI 챌린지 VQA**는 이미지와 질문을 함께 보고 답을 고르는 **멀티모달 이해** 과제였습니다. 생성은 아니지만, 같은 이미지를 해상도와 자르기를 바꿔 여러 번 보여 주고 확률을 합친 경험이 있습니다. 이미지 입력은 보여 주는 방식에 따라 결과가 달라진다는 것을 그때 확인했습니다.
- **관통 7의 FastAPI 프록시**에서는 텍스트 요청과 표지 이미지 요청을 나눠 라우팅했습니다. 입력 종류에 따라 모델과 처리 경로를 나누는 구조는 생성 모델을 붙일 때도 같은 자리에 들어갑니다.
- **포트폴리오의 여정 영상**에서 그림풍 장면 일부는 생성형 이미지로 만들었고, 영상 안에 AI 생성 이미지라고 표시했습니다. 영상 생성 모델을 직접 학습시키거나 서비스에 붙인 적은 없습니다.

## 면접 질문

**Q. 이미지·영상 생성 기능을 서비스에 넣는다면 무엇을 먼저 설계하겠습니까?**

> 결과가 바로 나오지 않는다는 점부터 설계하겠습니다. 작업을 대기열에 넣고 진행 상태를 보여 주며, 실패하면 재시도하거나 사용자에게 알리는 흐름이 필요합니다. 품질은 길이·해상도·소리 유무처럼 코드로 확인할 수 있는 항목과 사람이 봐야 하는 항목을 나눠 관리하겠습니다. 그리고 결과물에는 AI 생성물이라는 표시를 남기겠습니다. VQA 챌린지에서 이미지를 보여 주는 방식에 따라 결과가 달라지는 것을 겪었기 때문에, 입력 조건을 기록해 두고 같은 조건으로 비교할 수 있게 하겠습니다.
