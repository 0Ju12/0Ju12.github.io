> **한 줄 요약** — 지난 회차에서 본 SWE-bench 논란은 코딩 에이전트의 점수를 둘러싼 것이었습니다. 이번에는 그 에이전트 자체를 봅니다. 코딩 에이전트는 #5의 루프를 저장소 안에서 돌립니다. **파일을 읽고, 고치고, 명령을 실행해 결과를 보고, 다시 고칩니다.** 코드를 만드는 속도가 빨라질수록, 그 코드가 맞는지 확인하는 장치가 병목이 됩니다.

## 핵심 개념

- **세 단계의 변화**: 자동 완성(다음 줄 제안) → 대화형 수정(선택한 코드를 설명·고침) → 에이전트(목표를 주면 여러 파일을 읽고 고치고 테스트까지 실행). 앞의 둘은 사람이 매 단계 받아들이지만, 셋째는 여러 단계를 스스로 이어 갑니다.
- **에이전트가 쓰는 도구**: 파일 읽기·검색, 편집, 셸 명령 실행(테스트·빌드·린트), 버전 관리. #2에서 본 도구 호출이 개발 환경에 연결된 형태입니다.
- **되먹임이 품질을 정합니다.** 에이전트는 테스트 실패 메시지, 컴파일 오류, 린트 경고를 읽고 다음 수정을 정합니다. 이런 신호가 없는 저장소에서는 맞는지 모른 채 "완료했다"고 말하게 됩니다.
- **비유**: 손이 매우 빠른 신입 개발자와 같습니다. 지시가 분명하고 테스트가 있으면 많은 일을 해내지만, 요구가 모호하거나 확인 수단이 없으면 그럴듯하게 틀린 코드를 빠르게 많이 만듭니다.

## 지금 무슨 일이 일어나고 있나

- **주요 도구가 모두 에이전트 방식을 기본으로 삼았습니다.** 터미널에서 도는 것(Claude Code, Codex CLI), 편집기에 들어간 것(Cursor), 클라우드에서 따로 돌며 변경 요청을 올리는 것으로 형태가 나뉩니다. 한 사람이 여러 에이전트에 일을 나눠 맡기는 방식(#8)도 제품에 들어왔습니다.
- **점수는 출처마다 엇갈립니다.** 이번 조사에서 SWE-bench 계열 점수를 여러 2차 자료로 봤는데, 같은 시기의 "1위"와 수치가 글마다 달랐습니다. 측정 날짜, 변형 벤치마크(Verified·Pro), 붙인 실행 틀이 다르기 때문입니다. #10에서 본 대로 Verified는 오염 논란이 있어, 이 글에서는 특정 수치를 인용하지 않습니다. 순위를 인용하려면 벤치마크 운영 측의 순위표에서 날짜와 조건을 함께 확인해야 합니다.
- **생산성 효과도 한 방향이 아닙니다.** METR의 2025년 무작위 대조 실험은 익숙한 오픈소스 저장소에서 일하는 숙련 개발자들이 AI 도구를 쓸 때 작업 시간이 오히려 약 19% 길어졌다고 보고한 것으로 알려져 있습니다. 참가자들은 자신이 빨라졌다고 느꼈다는 점이 함께 보고됐습니다. 이 실험은 당시 도구와 특정 조건의 결과이고, 이번 조사에서는 2차 자료로만 확인했습니다.

## 동작 구조

```
목표 ("결제 취소 시 재고가 복구되지 않는 버그 수정")
   │
   ▼
① 탐색: 관련 파일 검색 · 읽기 ─────────────┐
② 계획: 어디를 어떻게 고칠지              │  컨텍스트 창에 들어가는 것은
③ 편집: 파일 수정                          │  읽은 파일 일부 + 명령 출력
④ 확인: 테스트 · 빌드 · 린트 실행 ◀── 되먹임 │
   ├─ 실패 → 출력 읽고 ③으로
   └─ 통과 → ⑤ 변경 요약 + 사람 검토
```

```python
def coding_agent(goal, repo, max_steps=40):
    notes = repo.read("AGENTS.md")              # 저장소 규칙: 빌드·테스트 방법, 건드리면 안 되는 곳
    for _ in range(max_steps):
        action = model.next(goal, notes, history)
        if action.kind == "edit" and not repo.allowed(action.path):
            history.add("거부: 허용되지 않은 경로")   # 권한은 코드가 정함 (#9)
            continue
        result = run(action)                    # 읽기 · 편집 · 셸
        history.add(action, result)
        if action.kind == "finish":
            break
    return repo.diff(), run("pytest -q")        # 끝났다는 말이 아니라, 테스트 결과로 판단
```

| 사람의 일 | 에이전트 이전 | 에이전트 이후 |
|---|---|---|
| 요구 정리 | 머릿속에 두고 바로 작성 | 글로 분명히 적어야 함 |
| 코드 작성 | 대부분의 시간 | 일부 |
| 확인 | 작성하며 자연히 | 따로 시간을 내서: 테스트, 검토, 실행 |
| 저장소 정비 | 선택 | 필요: 테스트·린트·문서가 되먹임이 됨 |

## 왜 중요한가 / 한계

- **작성 비용이 내려가면 병목이 옮겨 갑니다.** 무엇을 만들지 정하는 일과, 만든 것이 맞는지 확인하는 일이 남습니다.
- **한계 1 — 그럴듯한 오답**: 테스트가 없는 부분의 변경은 확인되지 않은 채 남습니다. 에이전트가 테스트를 고쳐서 통과시키는 경우도 있어, 테스트 변경은 따로 봐야 합니다.
- **한계 2 — 이해의 공백**: 직접 쓰지 않은 코드는 덜 이해하게 됩니다. 장애가 났을 때 고칠 사람이 그 코드를 모르는 상태가 됩니다.
- **한계 3 — 권한과 보안**: 에이전트는 셸을 실행합니다. 저장소의 문서나 의존성 안의 글이 지시로 읽히면(#9) 원치 않는 명령이 실행될 수 있어, 실행 범위와 비밀값 접근을 제한해야 합니다.
- **한계 4 — 측정의 어려움**: 위에서 본 대로 벤치마크 점수는 엇갈리고, 체감 속도와 실제 속도가 다를 수 있습니다. 자기 팀의 과제로 재야 합니다(#10).

## 내 프로젝트와 연결

- **확인 장치를 먼저 만든 경험**이 있습니다. 포트폴리오 사이트는 빌드할 때 국문·영문 항목 수 일치, 깨진 링크, 화면 넘침(46개 페이지를 두 가지 폭으로)을 스크립트로 점검하고, 통과하지 못하면 배포하지 않습니다. 최근 통계 페이지를 추가했을 때 링크 표기 하나가 이 점검에 걸려 배포가 막혔고, 고친 뒤에 올라갔습니다. 누가 코드를 썼든 같은 기준으로 걸러 내는 장치입니다.
- **깨끗한 환경에서만 드러나는 실패**도 겪었습니다. 데이터 웨어하우스 프로젝트에서 Airflow 작업이 내 환경에서는 통과하고 CI에서만 실패했는데, 원인은 처음 실행 때 폴더가 없다는 것이었습니다. 이후 "산출물을 지우고 다시 돌리기"와 그 경우의 테스트를 추가했습니다. 에이전트가 "통과했다"고 말해도 CI 결과로 판단해야 하는 이유와 같습니다.
- **SWEA 풀이 저장소**를 정리하며 풀이 36개에 테스트 37개를 붙였고, 그 과정에서 버그 6개를 찾아 고쳤습니다. 테스트를 붙이기 전에는 "맞게 푼 줄 알았던" 코드였습니다.
- **관통 4·5**의 원칙인 "LLM에는 판단만 맡기고 결과는 코드로 검증한다"는 코딩 에이전트에도 그대로 적용됩니다. 다만 팀 단위로 코딩 에이전트를 운영해 본 경험은 없습니다.

## 면접 질문

**Q. AI 코딩 도구를 어떻게 쓰고, 품질은 어떻게 보장합니까?**

> 작성은 맡기되 확인은 사람이 책임지는 구조로 씁니다. 먼저 요구를 글로 분명히 적고, 테스트와 린트처럼 에이전트가 스스로 결과를 볼 수 있는 장치를 저장소에 갖춥니다. 완료 여부는 에이전트의 말이 아니라 CI 결과로 판단하고, 테스트 파일이 바뀐 변경은 따로 검토합니다. 실행 권한과 비밀값 접근은 최소로 둡니다. 포트폴리오 사이트에서 빌드 때 링크와 화면 넘침을 자동 점검해 통과하지 못하면 배포를 막는 것, 웨어하우스 프로젝트에서 내 환경에서는 통과했지만 CI에서 실패한 경우를 테스트로 추가한 것이 이 방식입니다. 벤치마크 점수는 출처마다 엇갈리므로, 도구 선택은 우리 과제로 직접 재서 정하겠습니다.
