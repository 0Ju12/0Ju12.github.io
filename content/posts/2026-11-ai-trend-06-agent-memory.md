> **한 줄 요약** — 지난 회차에서 ReAct는 걸음마다 "지금까지의 기록"을 다시 읽는다고 했습니다. 그 기록이 에이전트의 **단기 기억**이고, 컨텍스트 창이 차면 사라집니다. 메모리 설계는 무엇을 창 밖에 **써 둘지**, 언제 다시 **꺼낼지**, 그리고 써 둔 것을 **믿어도 되는지**를 정하는 일입니다.

## 핵심 개념

- **단기 기억**: 한 대화(스레드) 안의 메시지와 도구 결과입니다. 모델은 호출 사이에 아무것도 기억하지 않으므로, 앱이 매번 기록을 다시 넣어 줍니다.
- **장기 기억**: 대화가 끝나도 남도록 밖에 저장한 것입니다. 연구(CoALA, Sumers 외 2023)의 분류를 따라 보통 셋으로 나눕니다. 사실(**의미** 기억: "사용자는 Python을 쓴다"), 겪은 일(**일화** 기억: "지난번 이 방법은 실패했다"), 일하는 방법(**절차** 기억: 지침·규칙).
- **비유**: 단기 기억은 책상 위입니다. 넓지 않아서 일이 길어지면 치워야 합니다. 장기 기억은 서랍과 수첩입니다. 무엇을 수첩에 적을지, 언제 다시 펼칠지를 정해야 하고, 누가 수첩에 몰래 적어 넣을 수 있는지도 따져야 합니다.
- **RAG와의 차이**: RAG(#7)는 주로 사람이 준비한 문서를 읽기만 합니다. 메모리는 에이전트가 **스스로 쓰기도** 합니다. 쓰기가 있다는 점이 뒤에서 볼 보안 문제의 출발점입니다.

## 지금 무슨 일이 일어나고 있나

- **OS에서 빌린 구조**: MemGPT(Packer 외, 2023)는 컨텍스트 창을 RAM처럼, 외부 저장소를 디스크처럼 보고 모델이 도구 호출로 정보를 넣고 빼게 했습니다. 이 프로젝트는 이후 Letta로 이름이 바뀌었습니다.
- **프레임워크의 기본 구성이 되었습니다.** LangGraph는 스레드 단위 체크포인트(단기)와, 스레드를 넘나드는 저장소(장기, 네임스페이스로 구분)를 따로 둡니다. Mem0·Zep 같은 전용 메모리 계층도 사용자·에이전트·작업 단위로 기억을 나누는 기능을 제공합니다.
- **모델 제공사도 도구로 내놓았습니다.** Anthropic은 모델이 메모리 디렉터리의 파일을 만들고 읽고 고치는 메모리 도구와, 오래된 도구 결과를 컨텍스트에서 덜어 내는 컨텍스트 편집을 소개했습니다. 파일 작업 자체는 앱이 자기 저장소에서 실행하는 구조로 알려져 있습니다. 이 부분은 2차 자료로 확인한 내용이라, 쓰기 전에 공식 문서로 현재 사양을 확인해야 합니다.
- **보안 항목으로 분리되었습니다.** OWASP의 에이전트 애플리케이션 Top 10은 메모리·컨텍스트 오염을 독립 항목(ASI06)으로 둡니다. 2026년 연구들은 공격자가 메모리 저장소에 직접 접근하지 못해도, 평범한 질문만으로 에이전트가 악성 내용을 스스로 기억에 쓰게 만들 수 있다고 보고합니다(MINJA 등). 기억을 적극적으로 쓰고 꺼낼수록 긴 작업 성능은 좋아지지만 공격 면도 넓어진다는 분석도 있습니다.

## 동작 구조

```
            ┌───────────── 컨텍스트 창 (단기) ─────────────┐
사용자 ───▶ │ 시스템 지침 + [꺼낸 기억] + 최근 대화 + 도구 결과 │ ───▶ 모델
            └──────────────────────────────────────────────┘
                 ▲ ③ 꺼내기 (검색·필터)            │ ① 쓸지 판단
                 │                                 ▼
            ┌──────────── 장기 저장소 ─────────────┐   ② 쓰기 전 검사
            │ 의미(사실) · 일화(경험) · 절차(지침)  │ ◀── 출처·형식·민감 정보
            │ 사용자·작업 단위로 분리               │
            └───────────────────────────────────────┘
창이 차면: 오래된 도구 결과 덜어내기 / 요약으로 바꾸기 (④ 정리)
```

```python
def turn(user_msg, thread, store, user_id):
    memories = store.search(ns=("user", user_id), query=user_msg, k=5)   # ③ 꺼내기
    memories = [m for m in memories if m.source == "user_confirmed"]      #    출처로 거름
    reply = llm(system + render(memories) + thread.recent(20) + user_msg)

    for fact in extract_candidates(user_msg, reply):                      # ① 쓸 후보
        if not passes_write_policy(fact):                                 # ② 쓰기 검사
            continue                     # 도구 결과·웹 문서에서 온 '지시문'은 쓰지 않음
        store.put(ns=("user", user_id), value=fact, source=fact.origin, ts=now())

    if thread.tokens() > LIMIT:                                           # ④ 정리
        thread.replace_old_with(summarize(thread.old()))
    return reply
```

설계에서 정해야 하는 것은 네 가지입니다. **무엇을 쓰나**(모든 대화가 아니라 다시 쓸 사실만), **누가 쓰나**(사용자가 말한 것과 외부 문서에서 읽은 것을 구분), **언제 꺼내나**(매번 전부가 아니라 관련된 것만), **언제 지우나**(낡은 사실, 사용자의 삭제 요청).

## 왜 중요한가 / 한계

- **긴 작업의 전제입니다.** 컨텍스트 창은 유한하고, 길어질수록 비용이 늘고 앞부분을 놓치기 쉽습니다. 덜어 내고 요약하는 정리가 없으면 긴 작업은 중간에 흐트러집니다.
- **한계 1 — 요약은 정보를 잃습니다.** 무엇이 중요한지 요약 시점에는 모를 수 있습니다. 원문을 밖에 남겨 두고 요약에는 위치만 적는 방식이 대안입니다.
- **한계 2 — 낡은 기억**: "사용자는 학생이다"는 언젠가 틀린 사실이 됩니다. 기억에 시각과 출처를 붙이고, 충돌하면 최근 것을 우선하거나 다시 묻는 규칙이 필요합니다.
- **한계 3 — 오염은 세션을 넘어 남습니다.** 프롬프트 인젝션은 대화가 끝나면 사라지지만, 기억에 쓰인 지시문은 다음 대화에서 신뢰받는 내용으로 다시 들어옵니다. 방어는 쓰기 쪽에 둡니다. 외부에서 읽은 내용은 사실로만 저장하고 지시로 실행하지 않기, 출처를 함께 저장해 꺼낼 때 거르기, 쓰기 기록 남기기입니다. 기존 메모리 계층은 사용자별 분리는 잘 지원하지만 "누가 쓸 수 있는가"의 통제는 아직 거칠다는 지적이 있습니다.
- **한계 4 — 개인정보**: 기억은 곧 저장된 개인 데이터입니다. 무엇을 기억하는지 보여 주고 지울 수 있게 해야 합니다.

## 내 프로젝트와 연결

- 에이전트의 장기 기억을 직접 만든 적은 없습니다. 가까운 경험은 **국보 RAG 가이드**의 ChromaDB입니다. 수집한 문서를 조각내 저장하고 질문마다 관련 조각만 꺼내 넣었는데, 이는 읽기 전용이라 위에서 말한 쓰기 문제는 없었습니다. 대신 꺼낸 조각을 답이 실제로 인용했는지를 근거 번호로 검증했습니다. 메모리에서도 "꺼낸 기억을 답이 어떻게 썼는지"를 같은 방식으로 확인할 수 있다고 봅니다.
- **관통 7 프록시**에서는 Guardrail 판정 형식이 깨지면 통과시키지 않고 막았습니다(fail-closed). 메모리 쓰기 검사도 같은 원칙이 맞다고 봅니다. 검사를 통과하지 못했거나 검사 자체가 실패하면 쓰지 않는 쪽이 기본값이어야 합니다.
- 이 포트폴리오의 **면접 준비 앱**은 연습 기록을 브라우저에 저장하고, 다른 기기와 합칠 때 같은 항목은 더 최근 시각의 것을 남깁니다. LLM 메모리는 아니지만, 한계 2의 "시각을 붙이고 충돌하면 최근 것 우선"을 실제로 구현해 본 사례입니다. 사용자가 지운 기록이 동기화로 되살아나지 않게 삭제 목록을 따로 두어야 했던 것도 같은 종류의 문제였습니다.

## 면접 질문

**Q. 에이전트에 장기 메모리를 붙인다면 무엇을 가장 먼저 설계하겠습니까?**

> 쓰기 규칙부터 정하겠습니다. 무엇을 저장할지보다 누가 쓴 내용인지가 먼저입니다. 사용자가 직접 말한 사실과, 에이전트가 웹이나 도구 결과에서 읽은 내용을 출처로 구분해 저장하고, 외부에서 온 문장은 지시로 다루지 않습니다. 한 번 잘못 쓰인 기억은 세션이 끝나도 남아서 다음 대화에 신뢰받는 내용으로 들어오기 때문입니다. 그다음에 시각을 붙여 낡은 기억을 정리하는 규칙과, 사용자가 기억을 보고 지울 수 있는 기능을 둡니다. 검사에 실패하면 저장하지 않는 것을 기본값으로 하겠습니다. 관통 7에서 Guardrail 형식이 깨지면 막도록 했던 것과 같은 원칙입니다.
