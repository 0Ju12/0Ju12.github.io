> **한 줄 요약** — 지난 회차의 코딩 에이전트는 파일과 셸이라는 **글자로 된 환경**에서 일했습니다. 세상의 많은 프로그램은 API도 명령줄도 없고 화면만 있습니다. 컴퓨터 사용 에이전트는 **화면을 캡처해 보고, 마우스 좌표와 키 입력을 내는** 방식으로 그런 프로그램을 다룹니다. 도구를 하나하나 정의해 주던 #2·#3과 달리, 화면 자체가 범용 도구가 됩니다.

## 핵심 개념

- **행동 공간이 사람과 같습니다.** 클릭(x, y), 입력(글자), 스크롤, 키 조합, 대기. 여기에 화면 캡처가 관찰로 들어옵니다.
- **두 가지 접근**
  - 화면 기반: 캡처한 그림만 보고 좌표를 정합니다. 어떤 프로그램이든 다루지만 느리고, 작은 버튼을 빗맞힐 수 있습니다.
  - 구조 기반: 웹의 DOM이나 운영체제의 접근성 트리처럼 화면 요소의 목록을 받습니다. 정확하고 빠르지만 그런 구조를 주는 프로그램에서만 됩니다. 실제 제품은 둘을 섞습니다.
- **기존 자동화와의 차이**: 매크로나 테스트 스크립트는 "이 버튼을 누른다"를 사람이 미리 적어 둡니다. 화면이 바뀌면 깨집니다. 컴퓨터 사용 에이전트는 목표만 받고 그때그때 화면을 보고 정하므로 바뀐 화면에도 대응하지만, 그만큼 매번 다르게 움직일 수 있습니다.
- **비유**: 전화로 부모님께 컴퓨터 사용법을 알려 드리는 상황과 비슷합니다. "지금 화면에 뭐가 보여요?"를 묻고, 한 번에 한 동작씩 말하고, 결과를 다시 확인합니다. 느리지만 어떤 프로그램이든 됩니다.

## 지금 무슨 일이 일어나고 있나

- **벤치마크 점수가 빠르게 올랐습니다.** OSWorld는 실제 운영체제에서 파일 관리·문서 편집·웹 작업 같은 과제를 시키는 벤치마크입니다. 2025년 초 OpenAI Operator가 공개될 때 자체 보고한 점수는 30%대였는데, 2026년 순위표들은 상위 모델을 80%대 중반으로 적고 있습니다. 사람 기준선은 자료에 따라 약 70~72%로 인용됩니다.
- **수치는 자료마다 다릅니다.** 이번 조사에서 본 순위 모음 사이트들은 1위 모델과 점수를 서로 다르게 적고 있었고, 갱신 시점도 달랐습니다. 자체 보고 점수는 허용 단계 수, 운영체제 이미지, 도구 권한이 달라 직접 비교하기 어렵다는 주의가 순위표에도 붙어 있습니다.
- **점수가 몰리자 더 긴 과제가 나왔습니다.** 상위 모델들이 1점 남짓한 차이로 붙어 있어 벤치마크가 포화에 가깝다는 평가가 있고, 더 긴 과제를 다루는 OSWorld 2.0처럼 새 규약이 나왔습니다. 두 결과는 서로 바꿔 쓸 수 없다고 안내됩니다. 다른 환경에서는 점수가 크게 떨어진다는 보고도 있어, 높은 점수가 실제 업무에서의 신뢰성을 보장하지는 않습니다(#10).

## 동작 구조

```
목표 ("지난달 청구서 PDF를 내려받아 '2026-10' 폴더에 넣기")
   │
   ▼
┌─▶ ① 관찰: 화면 캡처 (+ 가능하면 요소 목록)
│   ② 판단: 지금 어디에 있고 다음 한 동작은 무엇인가
│   ③ 행동: click(812, 344) · type("2026-10") · scroll · key("Enter")
│   ④ 대기: 화면이 바뀔 때까지
└── ⑤ 확인: 기대한 화면인가?  아니면 되돌아가거나 다른 길
        │
        └─ 결제·삭제·전송 같은 동작 앞에서는 사람에게 확인
```

```python
def computer_use(goal, max_steps=50):
    for step in range(max_steps):
        shot = screen.capture()
        act = model.decide(goal, shot, history)          # {"type": "click", "x": 812, "y": 344}
        if act.type == "done":
            return verify(goal)                           # 끝났다는 말이 아니라 결과 상태로 확인
        if risky(act, shot):                              # 결제 · 삭제 · 외부 전송 · 로그인 정보 입력
            if not ask_human(act, shot):
                continue
        screen.perform(act)
        history.add(act, shot)
    return "단계 한도 초과"
```

|---|---|---|
| 준비 | 도구마다 정의 필요 | 화면만 있으면 됨 |
| 속도·비용 | 빠르고 쌈 | 느리고 비쌈 (동작마다 캡처·판단) |
| 정확도 | 높음 (형식이 정해짐) | 빗맞힘·잘못된 화면 인식 가능 |
| 되돌리기 | 설계하기 쉬움 | 어려움 (이미 눌렀음) |
| 맞는 곳 | API가 있는 모든 일 | API가 없는 옛 시스템, 화면 검증 |

## 왜 중요한가 / 한계

- **API가 없는 일을 맡길 수 있게 됩니다.** 오래된 사내 시스템, 웹 양식 작성, 여러 프로그램을 오가는 사무 작업이 대상입니다.
- **한계 1 — 화면이 곧 공격 경로입니다.** 웹 페이지에 적힌 글이 지시로 읽힐 수 있습니다(#9). 브라우저를 다루는 에이전트는 로그인된 계정을 그대로 쓰므로, 속았을 때의 피해가 큽니다.
- **한계 2 — 되돌릴 수 없는 동작**: 전송, 결제, 삭제는 누르면 끝입니다. 이런 동작 앞의 사람 확인과, 권한이 제한된 별도 환경이 필요합니다.
- **한계 3 — 느리고 비쌉니다.** 사람이 10초에 하는 일을 여러 번의 캡처와 판단으로 합니다. API가 있으면 API가 낫습니다.
- **한계 4 — 긴 작업에서의 누적 오차**: 한 동작의 성공률이 높아도 50단계를 이어 가면 전체 성공률은 크게 떨어집니다. 벤치마크의 높은 점수와 실제 긴 업무 사이의 차이가 여기서 납니다.

## 내 프로젝트와 연결

- 컴퓨터 사용 에이전트를 만들거나 운영한 경험은 없습니다. 가장 가까운 것은 **스크립트로 적어 둔 브라우저 자동화**입니다. 포트폴리오 사이트의 화면 점검은 Playwright로 46개 페이지를 휴대폰·데스크톱 폭으로 열어 가로 넘침과 겹침을 확인하고, 잠금 화면을 풀어 탭이 열리는지 봅니다. 요소를 선택자로 지정하는 구조 기반 방식이고, 무엇을 누를지는 사람이 미리 정했다는 점에서 에이전트와 다릅니다.
- 이 점검을 운영하며 겪은 문제는 위 한계와 닿아 있습니다. 화면이 다 그려지기 전에 확인해서 틀린 결과가 나오는 일이 있었고, 기다리는 조건을 명시해야 했습니다. 위 그림의 "④ 대기"가 빠지면 생기는 문제입니다.
- **국보 RAG 가이드**의 시연 화면은 실제로 서버를 띄워 캡처했습니다. 디자인 시안이 아니라 실행 화면만 쓴다는 원칙은, 에이전트의 "완료했다"는 말이 아니라 결과 상태를 확인한다는 것과 같은 생각입니다.

## 면접 질문

**Q. 화면을 조작하는 에이전트와 API 연동 중 무엇을 택하겠습니까?**

> API가 있으면 API를 씁니다. 빠르고 싸고 형식이 정해져 있어 검증하기 쉽습니다. 화면 조작 에이전트는 API가 없는 옛 시스템이나 여러 프로그램을 오가는 작업처럼 다른 방법이 없을 때 씁니다. 도입한다면 권한이 제한된 별도 환경에서 돌리고, 결제·삭제·전송 같은 되돌릴 수 없는 동작 앞에는 사람 확인을 두고, 완료 여부는 에이전트의 보고가 아니라 결과 상태로 확인하겠습니다. 벤치마크 점수가 사람 기준선을 넘었다는 보고가 있지만 자료마다 수치와 조건이 달라, 우리 업무의 긴 과제로 직접 재 봐야 한다고 생각합니다. 저는 에이전트 방식은 아니지만 Playwright로 사이트 화면 점검을 자동화해 운영했고, 화면이 다 그려지기 전에 판단하면 틀린다는 점을 그때 배웠습니다.
