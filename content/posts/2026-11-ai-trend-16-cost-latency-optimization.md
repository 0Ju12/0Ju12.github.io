> **한 줄 요약** — 지난 회차는 모델을 바꿀지 입력을 바꿀지의 문제였습니다. 이번에는 같은 품질의 답을 **더 싸고 빠르게** 받는 방법입니다. 매번 반복해서 보내는 긴 앞부분은 **캐시**로 다시 읽고, 쉬운 요청은 **작은 모델로 라우팅**하고(#13·#14), 급하지 않은 작업은 **배치**로 모아 보냅니다.

## 핵심 개념

- **프롬프트 캐싱**: 시스템 프롬프트·도구 설명·긴 문서처럼 요청마다 똑같은 **앞부분(prefix)** 을 제공자 쪽에 잠깐 저장해 두고, 다음 요청에서는 처음부터 계산하지 않고 다시 읽습니다. 다시 읽은 토큰은 훨씬 싸게 과금되고 첫 토큰까지의 시간도 줄어듭니다.
- **모델 라우팅**: 요청의 난이도나 종류를 보고 작은 모델과 큰 모델 중 하나로 보냅니다. #13의 생각 예산 조절, #14의 소형 모델 분기와 같은 자리입니다.
- **배치 처리**: 즉시 답이 필요 없는 대량 작업(분류, 요약, 평가)을 모아서 보내고 몇 시간 안에 결과를 받습니다. 대신 할인을 받습니다.
- **비유**: 도서관 열람실에서 매번 같은 참고서를 서고에서 꺼내 오지 않고 책상 옆 선반에 잠깐 두는 것이 캐싱입니다. 선반에 둔 책은 일정 시간 안 보면 서고로 돌아갑니다. 간단한 질문은 안내 데스크에서, 어려운 질문은 전문 사서에게 보내는 것이 라우팅입니다.

## 지금 무슨 일이 일어나고 있나

- **캐시 수명과 가격이 공식 문서에 명시돼 있습니다.** Anthropic 문서 기준으로 캐시는 기본 5분 동안 유지되고, 다시 쓸 때마다 수명이 무료로 갱신됩니다. 1시간 수명도 고를 수 있습니다. 캐시를 쓰는 요청은 기본 입력 가격의 1.25배(5분) 또는 2배(1시간), 캐시를 읽는 요청은 대부분의 모델에서 0.1배이고 모델에 따라 더 낮습니다.
- **제공자마다 기본값이 다릅니다.** OpenAI 문서는 기본 캐시 수명을 30분으로 두고, 일부 API에서 12시간 수명을 더 높은 쓰기 가격에 제공한다고 적고 있습니다. 같은 "프롬프트 캐싱"이라도 수명·가격·최소 길이가 다르므로 쓰는 제공자의 문서를 직접 확인해야 합니다.
- **2차 자료의 수치는 믿기 어렵습니다.** 캐싱 가격을 비교한다는 글이 많지만, 같은 사이트의 비슷한 글이 반복되거나 확인할 수 없는 주장이 섞여 있었습니다. 이 글의 가격 배수는 공식 문서에서 확인한 것만 적었고, 금액은 모델·시기에 따라 바뀌므로 쓰지 않았습니다.
- **비용 최적화 안내서에서 캐싱·라우팅·배치는 함께 다뤄집니다.** Anthropic의 비용·지능 최적화 문서는 모델 선택, 캐싱, 배치 처리를 같은 문서에서 다룹니다. 라우팅은 별도 제품이 아니라 애플리케이션이 직접 설계하는 부분입니다.

## 동작 구조

```
요청 = [시스템 프롬프트 · 도구 설명 · 긴 문서]  +  [이번 질문]
        └──────── 매번 같음 → 캐시 ────────┘     └ 매번 다름 ┘

첫 요청:  앞부분 계산 + 캐시에 쓰기 (쓰기 가격: 기본 입력보다 비쌈)
5분 안:   앞부분 캐시에서 읽기 (읽기 가격: 기본 입력보다 훨씬 쌈) → 수명 갱신
5분 넘게 안 쓰면: 캐시 사라짐 → 다음 요청은 다시 쓰기
```

```python
def handle(req):
    if not req.urgent:
        return batch_queue.add(req)                  # 할인 · 몇 시간 안에 결과
    model = "small" if is_easy(req) else "large"     # 라우팅 기준은 규칙 · 분류기 · 실패 시 승격
    messages = [
        {"role": "system", "content": SYSTEM, "cache": True},   # 바뀌지 않는 앞부분
        {"role": "user", "content": DOCS, "cache": True},
        {"role": "user", "content": req.question},              # 바뀌는 부분은 맨 뒤
    ]
    out = call(model, messages)
    log(model=model, cache_read=out.usage.cache_read, latency=out.latency)
    return out
```

| 장치 | 줄이는 것 | 맞는 경우 | 안 맞는 경우 |
|---|---|---|---|
| 캐싱 | 입력 비용, 첫 토큰 지연 | 긴 앞부분이 반복되고 요청 간격이 수명보다 짧음 | 앞부분이 매번 바뀜, 요청이 드묾 |
| 라우팅 | 출력·입력 비용, 생성 지연 | 쉬운 요청 비중이 큼 | 난이도 분류가 자주 틀림 |
| 배치 | 비용 | 몇 시간 기다려도 되는 대량 작업 | 사용자가 기다리는 요청 |

## 왜 중요한가 / 한계

- **에이전트에서 효과가 큽니다.** 에이전트는 한 작업에서 같은 시스템 프롬프트와 도구 설명을 수십 번 다시 보냅니다(#3·#11). 이 앞부분이 캐시되면 호출 수가 많아도 입력 비용이 덜 늘어납니다.
- **한계 1 — 순서가 바뀌면 캐시가 깨집니다.** 캐시는 앞부분이 글자 단위로 같아야 맞습니다. 시스템 프롬프트 안에 현재 시각이나 사용자 이름을 넣으면 매번 달라져 캐시가 맞지 않습니다. 바뀌는 내용은 뒤로 보내야 합니다.
- **한계 2 — 드문 요청에서는 오히려 비쌉니다.** 쓰기 가격이 기본보다 비싸기 때문에, 수명 안에 다시 읽히지 않으면 손해입니다. 캐시 적중률을 기록해 봐야 압니다.
- **한계 3 — 라우팅은 품질 위험을 옮깁니다.** 작은 모델로 보낸 요청이 틀리면 비용은 줄어도 품질이 떨어집니다. 넘기는 비율과 넘긴 뒤의 정확도를 같이 재야 합니다(#14).
- **한계 4 — 가격은 바뀝니다.** 배수와 금액은 모델과 시기에 따라 바뀌므로, 설계 문서에 숫자를 고정해 두지 말고 사용량 로그로 판단해야 합니다.

## 내 프로젝트와 연결

- **관통 7의 FastAPI 프록시**에서 요청 종류(텍스트·이미지)와 필요에 따라 모델 등급을 고르게 했습니다. 위 의사코드의 라우팅과 같은 자리입니다. 다만 난이도를 자동으로 판단하지는 않았고 호출하는 쪽이 등급을 정했습니다.
- 같은 프록시에서 Gemini 응답을 정규화해 Django 쪽이 응답 형식을 신경 쓰지 않게 했습니다. 모델을 바꿔 라우팅하려면 이렇게 **응답 형식이 같아야** 하므로, 라우팅의 전제 조건을 만든 셈입니다.
- 프록시의 Guardrail은 검사에 실패하면 막는(fail-closed) 방식이었습니다. 비용을 줄이려고 검사를 건너뛰는 선택은 하지 않았습니다.
- **프롬프트 캐싱과 배치 처리는 써 보지 않았습니다.** 관통 7은 요청마다 짧은 입력을 보내는 구조라 캐시할 긴 앞부분이 없었고, 사용량 로그로 캐시 적중률을 잰 적도 없습니다.

## 면접 질문

**Q. LLM 서비스 비용이 예상보다 많이 나온다면 무엇부터 보겠습니까?**

> 먼저 사용량 로그에서 어디서 토큰이 쓰이는지 나눠 보겠습니다. 요청마다 같은 긴 시스템 프롬프트나 문서를 보내고 있다면 프롬프트 캐싱을 적용하고, 바뀌는 부분을 뒤로 옮겨 캐시가 맞게 하겠습니다. 쉬운 요청이 많다면 작은 모델로 보내되, 넘기는 비율과 정확도를 같이 기록하겠습니다. 급하지 않은 평가나 분류 작업은 배치로 돌리겠습니다. 관통 7 프록시에서 모델 등급을 고르게 하고 응답 형식을 하나로 맞춘 것이 라우팅의 기반이었는데, 캐싱은 써 보지 않았기 때문에 적용한다면 적중률부터 재겠습니다.
