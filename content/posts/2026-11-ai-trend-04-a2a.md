> **한 줄 요약** — 지난 회차의 MCP는 에이전트가 **도구**를 쓰는 규격이었습니다. A2A(Agent2Agent)는 다른 회사·다른 프레임워크로 만든 **에이전트에게 일을 맡기는** 규격입니다. 도구는 부르면 결과가 오지만, 에이전트에게 맡긴 일은 시간이 걸리고 중간에 되물을 수도 있어서 "작업 상태"가 규격의 중심이 됩니다.

## 핵심 개념

- **MCP와 나눈 역할**: Google은 A2A를 발표하면서 "도구에는 MCP, 에이전트에는 A2A"를 권했습니다. 내 에이전트 안쪽에서 DB·검색을 붙일 때는 MCP, 내 에이전트가 다른 팀의 여행 예약 에이전트에게 일을 넘길 때는 A2A라는 구분입니다.
- **비유**: MCP가 사무실 안 공구함이라면, A2A는 다른 회사 담당자에게 일을 맡기는 업무 요청서입니다. 요청서에는 "지금 진행 중 / 추가 자료 필요 / 완료 / 실패" 같은 상태가 붙고, 결과물은 따로 첨부됩니다.
- **경계는 흐릿합니다**: 비판하는 쪽에서는 상태를 가진 MCP 서버는 사실상 에이전트이고, 단순한 에이전트는 도구로 볼 수도 있다고 지적합니다. 구분 기준은 "상대가 스스로 판단하며 오래 걸리는 일을 하는가"에 가깝습니다.

## 지금 무슨 일이 일어나고 있나

- **출발과 이관**: Google이 2025년 4월 공개했고, 2025년 6월 Linux Foundation으로 프로젝트가 옮겨졌습니다. 발표 당시 Salesforce·SAP·ServiceNow 등 50곳 넘는 파트너가 참여했지만 Anthropic·OpenAI는 명단에 없었다는 점이 당시 화제였습니다.
- **버전이 바뀌며 이름도 바뀌었습니다.** 초기 문서는 Agent Card를 `/.well-known/agent.json`에, 메서드를 `tasks/send`로 설명하지만, 이후 버전과 SDK는 `agent-card.json`, `message/send`·`message/stream`을 씁니다. 글마다 경로와 메서드가 다른 이유이므로, 구현할 때는 대상 버전의 공식 사양을 먼저 확인해야 합니다.
- **2026년 상태는 보도가 엇갈립니다.** 여러 글이 v1.0(서명된 Agent Card, 멀티 테넌시)이 나왔고 A2A가 MCP와 같은 AAIF로 들어갔다고 쓰지만, 날짜와 지원 기관 수가 글마다 다르고 대부분 2차 자료입니다. 이 글에서는 확정된 사실로 쓰지 않고, 공식 저장소(a2aproject)와 Linux Foundation 발표로 확인할 대상으로 남깁니다.

## 동작 구조

```
① 찾기:  내 에이전트 ── GET Agent Card ──▶ 상대 에이전트
         (이름, 할 수 있는 일(skills), 주소, 인증 방식이 적힌 JSON)

② 맡기기: message/send (JSON-RPC 2.0 over HTTPS)
          ──▶ task 생성: submitted → working → (input-required) → completed / failed

③ 받기:  짧은 일 → 응답으로 바로
         긴 일   → SSE 스트리밍으로 상태·중간 결과, 또는 webhook 푸시
         결과물   → artifact (텍스트·파일·데이터 part 묶음)
```

```python
card = fetch_agent_card(base_url)                 # skills·인증 방식 확인
if "translate_document" not in card.skill_ids:    # 할 수 있는 일인지 먼저 확인
    return fallback()
task = a2a.send_message(card.url, parts=[TextPart("이 계약서를 영어로"), FilePart(doc)])
while task.state in ("submitted", "working"):     # 상대는 '도구'가 아니라 오래 걸리는 '일'
    task = a2a.get_task(task.id)
if task.state == "input-required":                # 상대가 되묻는 경우를 처리해야 함
    task = a2a.send_message(card.url, task_id=task.id, parts=[TextPart(answer)])
verify(task.artifacts)                            # 받은 결과도 내 쪽에서 다시 검증
```

## 왜 중요한가 / 한계

- **중요한 이유**: 한 회사 안에서도 팀마다 다른 프레임워크로 에이전트를 만듭니다. 서로의 내부 구현(프롬프트·도구·메모리)을 몰라도 일을 주고받을 수 있게 하는 것이 목적입니다. 상대의 내부를 보지 않는다는 점이 기업 간 협업에서는 오히려 장점입니다.
- **한계 1 — 신뢰**: Agent Card에 적힌 "할 수 있는 일"은 자기소개일 뿐입니다. 상대가 누구인지(카드 서명·인증)와 결과가 맞는지(검증)는 맡긴 쪽이 따로 확인해야 합니다.
- **한계 2 — 책임과 디버깅**: 일이 여러 에이전트를 거치면 어디서 틀렸는지 추적하기 어렵습니다. task id 단위로 로그를 이어 붙이지 않으면 원인을 찾기 힘듭니다.
- **한계 3 — 성숙도**: 위에서 본 것처럼 경로·메서드 이름이 버전마다 바뀌었고, 최신 상태에 대한 보도도 엇갈립니다. 실제 서비스에서는 한 버전에 고정하고 호환성을 시험해야 합니다.

## 내 프로젝트와 연결

- A2A를 써 본 적은 없습니다. 가장 가까운 경험은 **관통 7의 서비스 분리**입니다. Django → FastAPI 프록시 → GMS로 나누고, 서비스 사이를 JSON Schema로 정한 계약으로만 주고받았습니다. 상대가 계약과 다른 형식을 돌려주면 통과시키지 않고 503으로 막았는데, A2A에서 받은 artifact를 그대로 믿지 않고 검증하는 것과 같은 원칙입니다.
- **관통 5**에서 30초 넘게 걸리는 분석 작업의 진행 상황을 NDJSON 스트리밍으로 보내면서 "회사 없음·댓글 없음·LLM 실패"를 서로 다른 상태로 구분해 안내했습니다. A2A task가 working·input-required·failed를 구분하고 SSE로 상태를 보내는 구조와 같은 고민입니다.
- **AI 챌린지 VQA**에서 여러 모델의 결과를 합칠 때, 새 모델은 단독 정확도가 아니라 기존 결과를 고친 수와 망친 수(fixes−breaks)로 채택했습니다. 여러 에이전트의 답을 합치는 오케스트레이션(#8)에서도 "추가된 에이전트가 전체를 실제로 낫게 하는가"를 같은 방식으로 따질 수 있다고 봅니다.

## 면접 질문

**Q. MCP와 A2A의 차이를 설명하고, 둘 중 무엇을 써야 할지 어떻게 정하나요?**

> MCP는 에이전트가 도구와 데이터에 붙는 규격이고, A2A는 에이전트가 다른 에이전트에게 일을 맡기는 규격입니다. 기준은 상대가 부르면 바로 결과가 오는 기능인지, 스스로 판단하면서 오래 걸리고 중간에 되물을 수 있는 작업자인지입니다. 앞은 MCP 도구로, 뒤는 A2A task로 다룹니다. 어느 쪽이든 상대가 돌려준 결과를 그대로 믿지 않고 형식과 내용을 검증해야 합니다. 관통 7에서 서비스 간 응답을 JSON Schema 계약으로 받고, 형식이 깨지면 막았던 것과 같은 원칙입니다.
